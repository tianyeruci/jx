# AI 管理服务项目目录结构

> 本文同时说明当前状态与 V2 目标状态。目标目录尚需通过特征测试保护后逐步重构，不得将本文件视为已完成证明。

## 1. 当前问题

当前 `ai_management/main.py`、`conversations.py`、`cleaning.py`、`tasks.py` 等文件同时承担路由、业务、持久化和外部调用，修改影响面大。V2 保持 `ai_management.main:app` 等公开入口兼容，但按领域和层次拆分。

## 3. 分层约束

- `main.py` 目标约 100 行，只装配应用；不得包含业务 SQL、Redis 或 Dify 流程。
- Router 只处理协议、鉴权、校验和响应转换，调用 Service。
- Service 实现事务与业务规则，不依赖 FastAPI 或 Streamlit。
- Integration 隔离远端协议，提供超时、错误映射和可测试接口。
- Persistence 只定义模型、查询和事务辅助，不反向依赖 Router。
- Worker Task 只做调度、租约和重试；核心逻辑调用 Service，便于单测。
- UI 只调用公开/内部 API，不直连数据库、Redis 或 Dify。

允许依赖方向：`api/ui/workers → services → persistence/integrations`。禁止反向依赖和跨层循环引用。

## 4. 兼容与迁移顺序

1. 为当前 API、SSE、任务名和 CLI 增加特征测试。
2. 创建新包和适配层，先移动无副作用模型与工具。
3. 按商业会话、课程、清洗、运维顺序逐域迁移。
4. 保留旧导入路径的薄兼容导出，直到调用方和测试全部迁移。
5. 最后缩减 `main.py`、`tasks.py` 和旧模块；每一阶段 API 响应与任务名不变。

## 5. 版本库边界

应提交：源码、迁移、DSL、Prompt、合成测试数据、V2 文档和脱敏验收摘要。

不得提交：`.env`、真实 Key/Token、`ai_management.db`、上传文件、日志、缓存、`build/`、`dist/`、wheelhouse、原始未脱敏报告和真实用户数据。
