# 清洗策略接入说明

> 当前可见范围（2026-08-16，ADR-036）：测试页的“文件清洗管理”固定使用 `general` 知识库；`GET /cleaning-strategies` 和 `GET /admin/knowledge-bases/course/cleaning-strategies` 不展示 `course_information`、`learning_route`、`course_route_catalog`。这只隐藏策略发现和页面入口，不删除旧数据，也不改变显式课程上传接口对既有策略的兼容校验。

> 新增策略的字段设计先遵循 [清洗策略接入与编写规范](../清洗策略接入与编写规范.md#6-metadata-分层dify-投影与-chatflow-边界) 第 6 节；面向商业顾问 `general` 知识库时，再遵循 [AI 商业顾问 RAG 全链路运行规范](../AI商业顾问RAG全链路执行计划.md#4-metadata-契约过滤与关键风险)。本文件说明当前服务怎样冻结、保存、投影和回读这些字段。

## 目标

当前版本已经落地的目标是：

1. 一个上传批次选择一种代码策略。
2. 多个源文件独立清洗、独立记状态。
3. 一个文件可以拆成多个逻辑条目；条目可独立查询和复核，每个逻辑条目独立创建 Dify 文档，但失败补偿和批次聚合仍以源文件为边界。
4. 成功条目必须通过 Dify 索引、父子块和 Metadata 校验。
5. Redis 可查询批次摘要和文件清单。
6. 成功源文件删除；失败源文件按保留期暂存。

当前仍不建设：

- 策略表
- 脚本上传
- 可视化 ETL
- 动态插件平台

## 新批次的非空 Markdown 降级与状态边界

当前上传链路不再把“模型复核/模型技术失败”作为几十万份文档的人工阻塞点。服务端在创建 `cleaned` 批次时保存 `_cleaning_review_policy` 快照；除 `course_route_catalog` 外，新批次只要已经得到非空的、完成表格清洗的最终 Markdown，就允许忽略模型返回值，使用该 Markdown 继续发布。历史批次没有该快照时保持旧逻辑，避免被新 Worker 静默改写。

状态含义如下：

| 状态 | 含义 | 新批次处理 |
| --- | --- | --- |
| `review_required` | 仍需人工作语义、安全或目录结构决定，不能证明有可安全发布的源内容 | 内容策略的非空模型复核不再停留在此；旧批次和 `course_route_catalog` 保留此状态 |
| `failed` | 空正文、转换失败、模型任务失败且没有可用源 Markdown、Dify 契约/索引/Metadata 失败且重试耗尽 | 非空模型失败先恢复源 Markdown；源为空才保持失败 |
| `pending` / `shard_pending` | 已有可入库 Markdown，等待普通文档或文章分片发布 | 进入专用 `ai_publication` 单并发队列 |
| `succeeded` | Dify 创建、索引终态、父子块结构和 Metadata 回读全部通过 | 文件/批次聚合收敛 |

这里的“源 Markdown”是 PDF/DOCX 转换后的 Markdown、上传的 Markdown，经过统一表格清洗和最终无表格门禁后的本地正文；不是模型输出。模型失败时保留失败原因和“模型输出未采用”的内部审计，但不把正文写入日志。

资料钩子和书籍等不调用模型的策略只保存源 Markdown，由发布 Worker 按保存的父子块分隔符交给 Dify 处理；本地清洗阶段不能预先把 `<<<DIFY_PARENT>>>` / `<<<DIFY_CHILD>>>` 写进正文，否则边界校验会把内部控制符误判为用户正文并反复重试。

## jx 指定目录的个人商业咨询模型清洗脚本

`personal_business_consultation` 提供一个不入库、不发布 Dify 的一次性脚本：它读取 jx 指定目录下的直接子级 `.md` 文件，逐个调用与线上相同的模型客户端和咨询契约，保存模型原始 JSON，继续执行语义、隐私、Markdown 表格和 Dify 分隔符验证；模型无响应、契约失败、`review` 或最终校验失败时，按线上规则恢复清洗后的源 Markdown。模型明确 `exclude` 时不降级。

脚本入口为 `scripts/jx_consultation_model_cleaning.py`。服务器输入目录固定使用 `/opt/ai-management/tmp/pdf-markdown-refine/output/` 时，建议把运行产物放到独立目录 `/opt/ai-management/var/jx-consultation-model-cleaning/`，不要放回输入目录。每次运行默认生成新的 `run_id`；显式复用已有 `run_id` 时只允许覆盖带有匹配 `RUN_MARKER.json` 的同一运行目录。

每个运行目录均带有统一清理标记，结构如下：

```text
<output-root>/runs/<run_id>/
├── RUN_MARKER.json       # 清理识别标记，不含正文
├── manifest.json         # 每个文件的状态、错误码、降级原因、输出相对路径
├── run.log               # JSONL 详细阶段日志；每次验证都立即刷盘并输出
├── input-map.json        # 私有映射：item_id 到原始文件名，权限受保护
├── source/               # 清洗后的源 Markdown 快照
├── model/                # 模型完整 JSON 返回值，按 item_id 保存
├── validated/            # 模型通过语义/隐私/边界校验后的 Markdown
└── final/                # 最终选中的 Markdown；模型成功或源 Markdown 降级
```

`run.log` 和 `manifest.json` 只记录哈希、item 编号、阶段、状态、错误码、模型尝试次数、token 用量和文件相对路径，不把源正文或模型正文打印到普通日志；模型完整返回值在私有的 `model/*.json` 中查看。关键阶段包括 `source_privacy_validation`、`semantic_validation`、`model_privacy_validation`、`final_markdown_validation`、`dify_boundary_validation` 和 `fallback`，失败项的 `error_code`、`reason_code` 与 `selected` 一起说明“在哪里、为什么降级”。

脚本默认读取 `JX_ACCEPTANCE_CLEANING_BUDGET_MAX_YUAN`，也可用 `--max-cost-yuan` 覆盖；预算预估超限时不发起模型调用，直接逐项记录 `MODEL_RUN_BUDGET_EXCEEDED` 并使用源 Markdown。该脚本只调用模型，不启动清洗队列、不写业务数据库、不调用 Dify 发布接口。

## 单个源文件包含多篇内容时的拆分边界

`wechat_public_account_cognition` 的一个 `.txt` 可以包含多篇公众号文章，`xiaobot_post` 的一个 `.md/.markdown` 可以包含多个帖子。策略必须先按已识别的文章/帖子结构边界拆成多个 `CleaningDocument`，再分别执行模型、Metadata、父子块和发布流程；不能把整个上传文件当成一个知识条目。

每个拆出的逻辑条目对应一个独立的 Dify `create-by-text` 文档，因此同一源文件的多个文章/帖子不会只作为一个远端文档中的多个父块存在。Dify 返回的 `batch` 只用于该单文档索引轮询，不是多文档创建批次；多个上传文件也按本地发布队列逐条调用，不拼接正文、不超过单条请求的 Dify 数量和字节限制。

模型返回多个证据化知识单元时，每个知识单元也生成独立本地条目和 Dify 文档；帖子模型 `keep/review` 只返回来源块筛选而没有知识单元时，视为模型契约不合格；模型结果不合格或失败时，忽略模型结果，使用对应文章/帖子的表格清洗后源 Markdown 继续入库。

## 从上传到知识库的实际顺序

1. 用户选择策略和知识库，提交一个外部批次；服务端固定策略、Metadata、父子块分隔符/上限和 review policy 快照。外部 HTTP/SSE 接口和字段不变。
2. PDF/DOCX 转成 Markdown，上传 Markdown/TXT 规范化为 Markdown；统一清洗 Markdown 表格。正文为空直接 `failed`，不伪造占位内容。
3. 策略拆分出条目，写入本地 `CleaningDocument`，保存最终 Markdown、Metadata、chunking、SHA 和内部审计。新批次的非空 review/model 异常恢复为 `pending` 或文章策略的 `shard_pending`。
4. 多文件批次在本地按文件/条目排队；普通 Dify 写入统一进入 `ai_publication`，由 `publication-worker` 单并发执行。每个逻辑条目单独调用一次 `create-by-text`，返回的 `batch` 只用于该文档索引轮询；不调用未确认的多文档创建接口，也不把多个文件拼成一个正文。
5. 文章策略的每个拆分条目独立创建、等待索引、验证父子块、写入并回读允许的 Metadata。`DIFY_SHARD_MAX_BYTES` 仍作为单条正文硬上限；`DIFY_SHARD_MAX_ITEMS` 只保留为配置兼容和防御性校验，不再把多个文章/帖子合并为一个远端文档。任一条目失败会刷新条目、分片、文件和批次状态，重试耗尽才为 `failed`。
6. 定时看门狗每 5 分钟回收长期未更新的 `pending`、模型处理和 Dify 分片任务，重新入队或按源 Markdown 降级；因此页面不依赖人工逐条点击才能继续。

## 策略接口

在 `ai_management/cleaning.py` 中实现：

```python
class MyStrategy:
    code = "my_strategy"
    display_name = "我的策略"
    supported_extensions = {".md", ".docx"}
    sensitive = False

    def clean(self, file_path, original_filename):
        return [
            CleanedDocument(
                markdown="# 标题\n\n正文",
                title="标题",
                metadata={"document_type": "example"},
                chunking=ChunkingConfig(
                    parent_mode="paragraph",
                    parent_separator="<<<DIFY_PARENT>>>",
                    parent_max_tokens=1000,
                    child_separator="<<<DIFY_CHILD>>>",
                    child_max_tokens=300,
                ),
            )
        ]
```

再把实例加入 `STRATEGY_REGISTRY`。策略定义不会写数据库；批次只记录 `strategy_code` 和 `build_version`。

每个正式策略必须同时提交：

- 至少一个正常样本。
- 空文档、异常格式或缺失字段样本。
- 清洗后 Markdown 预期结果或关键断言。
- 敏感文件名和敏感正文的处理决定。

## 输入文件的固定规则

- `.txt` 保留文本读取路径。
- `.docx`、`.md`、`.markdown`、`.pdf` 按各自解析器转成 Markdown 语义结果。
- `.pdf` 只接受当前明确支持的场景；扫描件/OCR 不稳定时进入失败或人工复核，不静默猜测。
- `personal_business_consultation` 同时接受 `.docx` 与 `.pdf`；手机号、邮箱、微信、证件号、地址、机构和可识别人物必须先脱敏。
- `.txt` 编码探测使用增量解码，不能因为 64 KiB 探测边界截断一个 GB18030 多字节字符而误判文件损坏。
- `book` 策略在转换后的 Markdown 大于 `10MB` 时必须拆分。

### 当前策略输入格式矩阵

清洗模式先按所选策略的 `supported_extensions` 校验扩展名，因此不是任意策略都接受 `.docx`、`.markdown`、`.md`、`.pdf`、`.txt` 五种格式。通过校验后，DOCX/PDF 解析为内部 Markdown，Markdown/TXT 读取为文本，再进入策略自己的拆分、语义分类、脱敏和发布门禁。

| 策略 | `.docx` | `.markdown` / `.md` | `.pdf` | `.txt` |
|---|---:|---:|---:|---:|
| `standard_document` | 支持 | 支持 | 支持 | 支持 |
| `test_markdown` | 支持 | 支持 | 不支持 | 支持 |
| `personal_business_consultation` | 支持 | 不支持 | 支持 | 不支持 |
| `wechat_public_account_cognition` | 不支持 | 不支持 | 不支持 | 支持 |
| `zsxq_post` / `xiaobot_post` | 不支持 | 支持 | 不支持 | 不支持 |
| `lead_magnet` / `book` | 支持 | 支持 | 支持 | 支持 |
| `course_information` / `learning_route`（兼容） | 支持 | 支持 | 不支持 | 支持 |
| `course_route_catalog` | 不支持 | 不支持 | 不支持 | 不支持 |

`course_route_catalog` 另有独立输入契约：仅接受 `.xlsx`，不把 `.txt` 或其它文本扩展名当作课程目录。

### 扫描 PDF 的 OCR 开关与处理边界

当日志出现“PDF 缺少可用文字层，OCR 已禁用”时，原因是 `PDF_OCR_ENABLED=false` 或 OCR 运行时门禁未满足。jx 测试服务器的配置由发布脚本写入 `.env`，关键值如下；不要只在 API 容器内临时安装包：

共享 PDF 分类还允许一个多页文字型文件的首页或末页出现少量、无图片的文字（其余页面必须全部有可用文字层）。该场景记录 `PDF_BOUNDARY_LOW_TEXT_WARNING` 和 `pdf_boundary_low_text` 本地审计，但不进入硬阻断；中间低文字页、低文字含图、混合扫描、纯扫描 OCR 失败、空正文和隐私残留仍必须复核或失败。该规则由共享转换核心统一执行，不能仅为 `lead_magnet` 单独放宽。

```dotenv
PDF_OCR_ENABLED=true
PDF_OCR_MAX_PAGES=50
PDF_OCR_TASK_TIMEOUT_SECONDS=3600
PDF_OCR_RENDER_DPI=200
PDF_OCR_RETRY_DPI=300
PDF_OCR_AUTO_CONFIDENCE=0.90
PDF_OCR_MIN_CONFIDENCE=0.75
PDF_OCR_MAX_LOW_CONF_RATIO=0.10
PDF_OCR_BACKEND=rapidocr_onnxruntime
PDF_OCR_IDLE_SECONDS=600
PDF_OCR_CPU_THREADS=2
PDF_OCR_MODEL_ROOT=/app/var/ocr-models/rapidocr
PDF_OCR_MODEL_MANIFEST=/app/var/ocr-models/rapidocr/manifest.json
AI_OCR_IMAGE=jx-now-ai-management-ocr:<release-id>
```

在当前策略 `supported_extensions` 允许的范围内，PDF/DOCX 先转换为内部 Markdown，Markdown/TXT 读取并规范化为 Markdown，再进入所选策略；策略输出和模型/人工复核结果在本地落库、Dify `create-by-text` 前还会再次执行同一最终门禁。可靠的 GFM/简单 HTML 表格转换为语义句；坏行按表聚合审计；结构无法可靠对齐的表格不猜列关系，保留线性单元格文本并只写内部 `table_review` 审计，不出现在用户告警中。最终进入知识库的正文必须是 Markdown 文本且不含 Markdown/HTML 表格。手工调用 `scripts/pdf_markdown_refine.py` 时可加 `--clean-tables` 复现 PDF 转换后的阶段；`raw` 也执行统一转换和表格清洗，但不执行具体策略语义处理。

启用条件是 RapidOCR 专用离线镜像、ONNX Runtime、pypdfium2、系统共享库和模型清单均已校验；模型清单按 SHA-256 校验，缺失或篡改时 OCR Worker 拒绝启动。配置生效后，文字层可用的 PDF 仍走普通解析，不会重复 OCR；缺少文字层的 PDF 才进入独立 `ai_ocr` 队列。格式、表格和 OCR 低置信度告警会写入公共 SystemEventLog 的 PDF 问题中心并尽量继续处理；混合/无法分类、OCR 失败、页数超限、无正文或下游 Dify 契约失败仍保持 `failed`/必要的 `review_required`，不得伪造成功。模型复核或模型技术失败只要有非空源 Markdown，则按新批次降级规则继续发布。

PDF 异常统一查询：`GET /internal/v1/admin/pdf-conversion-issues`（支持 `kb_code`、时间范围、`status=open|resolved`、`severity=warning|blocked`、分页）；人工处理后调用 `POST /internal/v1/admin/pdf-conversion-issues/{issue_id}/resolve`。问题中心复用 `SystemEventLog`，不新增业务表；`open` 的 PDF 事件不受普通 30 天日志清理影响。事件只记录脱敏代码、页数、后端和内部文件 ID，不记录正文、原始文件名或密钥。

OCR Worker 由 jx 的 systemd timer 每 60 秒检查：队列出现任务时按需启动；队列、Celery active/reserved/scheduled 均为空并连续 10 分钟后停止。空闲时不保留 OCR Worker 容器运行，不占用其 CPU/内存；API、普通清洗 Worker 和数据库/Redis不受此按需策略影响。Worker 启动失败时任务保留在队列，脚本记录 systemd 日志并退避重试，不会以失败结果自动发布。

本次启用只涉及离线软件/模型、Compose、systemd、部署脚本和文档配置，不修改 OCR 业务 Python 代码；今后如果修改 `ai_management/`、`knowledge_cleaner/` 或接口语义，仍须按完整发布和清洗契约流程验收。

当前测试页与策略发现只验收 `general` 策略：`recent_activity`、`personal_business_consultation`、`wechat_public_account_cognition`、`zsxq_post`、`xiaobot_post`、`lead_magnet`；`book` 保持独立通用知识策略。`course_information`、`learning_route`、`course_route_catalog` 都是后端显式调用的历史管理兼容策略，不在测试页展示，也不属于商业顾问新数据的页面验收范围。

`raw` 上传模式是独立路径，只做允许类型和文件签名校验，不代表相应清洗策略支持该格式；它仍按统一输入规范完成 PDF/DOCX→Markdown、Markdown 表格清洗和最终无表格门禁，但不执行具体策略的拆分、模型、脱敏或目录处理。

## 名称和来源

- 原始名称保存在受保护的 `original_filename`，用于内部追踪、审计和 Dify 管理。
- 磁盘使用 `{file_id}.{扩展名}`。
- Dify 使用 `{确定性截断后的原主名}.md`；同一源文件产生多个文档时使用 `{原主名}__{三位序号}.md`，例如 `访谈记录.md`、`访谈记录__001.md`。
- 系统来源字段在合并 Metadata 时最后写入，策略或调用方不能覆盖。
- 本地 Metadata 对所有策略保存完整 `source_filename`、文件 ID、扩展名、SHA、批次 ID、策略、序号和构建版本。
- Dify 只写入该策略声明的 `dify_metadata_fields`；系统来源字段和人名映射不写入 Dify 自定义 Metadata。
- 原文件名、Dify 管理名和人名映射不得进入商业顾问公开回答、SSE 引用或历史消息。

### 上传去重与重新上传

- 去重保护单位是知识库内的源文件记录；同一规范化文件名或同一源内容 SHA-256 任一命中，都不会再次入库，文件以 `excluded/duplicate_noop` 记录原因。
- 同名不同内容也必须先删除，不能用新上传覆盖旧源；同内容换名同样不能绕过保护。
- 重新上传前必须通过管理员源文件删除入口，按精确 `file_id` 和完整原文件名确认，删除该源产生的全部 Dify 分片，并核对 `source_deleted_at`、`dedupe_released_at` 和批次聚合已收敛。仅删除单个 Dify 文档、按名称模糊删除或直接改数据库都不能释放保护。
- 成功删除后才允许重新上传；删除接口必须同时刷新没有活动文件的批次，避免页面停留在 `processing`。

## 成功条件

一个原文件可能生成多个 Dify 条目和多个 Dify 文档。成功条件分两层：

### 文件级成功

- 文件拆分出的全部应发布条目都完成 Dify 创建、索引、父子块和 Metadata 回读校验。
- 文件状态进入 `succeeded` 或 `excluded`。
- 成功文件源文件已删除。
- `course_route_catalog` 和仍需源级结构一致性的兼容策略中，任何 `review_required` 条目阻止同源其他条目发布；新批次四个内容模型策略的非空模型复核/技术失败会先降级为源 Markdown 发布，真正的空源或下游硬失败才会阻止对应文件。
- 任何发布失败触发同源 Dify 文档补偿；补偿失败写入 `external_deletion_task`，文件保持失败状态。

### 条目级成功

必须同时满足：

1. 本地最终正文已记录 Markdown 字节数和 SHA-256，且通过无 Markdown/HTML 表格门禁；随后使用 `create-by-text` 发送该正文并保存文档 ID。
2. 索引状态到达 completed。
3. 父子块结构校验通过。
4. Metadata 写入成功并回读一致。

严格源级策略中，任何一个条目失败或待复核时，新的发布链路不会保留同源部分成功结果。新批次内容模型策略先把非空模型失败/复核恢复为清洗源 Markdown，再进入同一发布校验；仍然失败的文件才进入终态。文件可能进入：

- `failed`
- `review_required`
- `mixed`（内容模型策略存在成功条目和失败/待复核条目时的正常聚合状态）

系统行为：

- 文件级清洗自动重试一次。
- 任一子文档发布失败时，整文件补偿后自动重试一次。
- 历史批次的待复核条目必须先人工复核；不能直接走条目重试。新批次内容模型策略的非空模型契约失败、无响应或模型 `review` 会保留审计原因并使用清洗源 Markdown；Dify 发布失败仍按硬约束重试，耗尽后进入 `failed`。
- 已创建的同源远端文档会全部删除或停用；不能补偿的精确文档 ID 进入外部删除任务。
- 课程/路线子文档全部远端验证后，目录记录才在一个数据库事务中提交；旧远端副本在事务成功后再清理。

## 复核与重试

- 文件重试接口：重新清洗并发布整个失败文件；如果文件下只有待复核条目，返回 `409`。
- 条目重试接口：仍以失败条目作为入口，但发布器会重新检查并处理同一源文件的全部待发布条目；待复核条目返回 `409`，必须先复核。
- 模型调用规则：只有没有可用响应（网络/超时/空响应）才在同一文档内重试一次；第二次仍无响应记录 `MODEL_NO_RESPONSE`。新批次只要源 Markdown 非空，契约错误、模型 `review`、隐私/来源复核或任务级异常均保留审计原因并忽略模型输出，恢复源 Markdown 发布；没有源正文才进入 `failed`。
- 模型契约精确重试接口：仅针对唯一 realtime 模型任务中 `MODEL_CONTRACT_INVALID`/`MODEL_NO_RESPONSE` 的单个失败条目重新排队；保持严格契约和不切换 Batch，其他状态返回 `409`。
- `GET /internal/v1/admin/knowledge-bases/{kb_code}/upload-batches/{batch_id}/failed-items` 提供失败条目的分页 JSON 和全量 CSV；字段包含原文件名、策略、错误码、失败原因、模型尝试次数和是否可重试，默认失败记录保留 7 天。
- `CLEANING_REVIEW_REQUIRED_ENABLED` 仍写入服务端策略快照，供历史兼容和审计使用；新批次的 `source_markdown_fallback_enabled` 由服务端固定为“除 `course_route_catalog` 外开启”，不受客户端 Metadata 控制。已创建批次不受后续改配置影响。
- 新批次四个内容模型策略的非空短文本、隐私/来源复核和模型 `review` 不再阻塞后续链路；原复核原因写入内部审计，模型返回数据不写入最终正文。文章和咨询策略均使用表格清洗后的源 Markdown；没有可用源正文进入 `failed`。
- 模型调用受服务器每日模型预算控制，默认 `CLEANING_DAILY_BUDGET_YUAN=10`。预算不足时整批不发起模型调用；有非空源 Markdown 的条目直接排入降级发布，没有源正文的条目进入明确 `failed`，不保留 `awaiting_model` 悬挂状态。
- 清洗文件、模型任务和 Dify 发布错误的内部事件记录批次 ID、文件/任务/分片 ID、策略、阶段、错误码、异常消息和脱敏堆栈；不记录正文、密钥或原始敏感文件名。
- 该降级不绕过空源文件、清洗后为空、模型输出为空且没有源快照、Dify 文件/子文档长度硬约束、父子块/Metadata 回读、隐私硬阻断或发布补偿。`course_route_catalog` 不受该降级影响。
- 条目复核接口支持：
  - `approve`
  - `replace_and_approve`
  - `exclude`
- 复核必须带 `expected_revision`，防止多人覆盖。
- `exclude` 完成后必须立即刷新文件和批次聚合状态。
- 只有严格源级策略和 `course_route_catalog` 保留“同源一项待复核、其余条目一起阻断”的原子门禁；新批次内容模型策略按非空源 Markdown 自动继续，管理员可通过失败记录接口按页或 CSV 导出真正的失败项。

## 部署注意

- PDF/DOCX 的“转换后、策略处理前 Markdown”是否落盘只由 `SAVE_CONVERSION_MARKDOWN` 控制；关闭时不写新文件，并由 API 启动和夜间维护删除旧产物。
- 产物目录必须是名为 `conversion-markdown` 的专用目录。jx 容器路径为 `/app/var/conversion-markdown`，宿主机路径为 `/opt/ai-management/var/conversion-markdown`；API 和清洗 Worker 必须挂载同一目录。
- 开启后文件命名为 `批次ID__文件ID__规范化原文件名.md`，跨重启保留，默认 7 天清理。该正文可能尚未脱敏，只能通过 SSH 查看，不得增加公共下载接口或写入普通日志。
- 该开关只影响开启后新上传或正式重试的 PDF/DOCX，不扫描数据库回填历史文件。
- 服务器离线构建使用 `Dockerfile.offline` + `wheelhouse` 安装运行时代码。
- 发布清洗策略相关代码时，必须先替换 `wheelhouse/jx_now_ai_management-0.2.1-py3-none-any.whl`，再重建 API / Worker / Scheduler 镜像。
- API、Worker、Scheduler 必须使用同一核心镜像；测试页使用由同一 wheel 构建的 UI 镜像。
- 只把本地源码同步到 `/opt/ai-management` 而不替换 wheel，不会让容器跑到新代码。

## 当前明确不要做的事

- 不根据扩展名猜测“万能清洗规则”。
- 不把失败文件伪装成成功。
- 不把 Dify HTTP 200 当作最终成功。
- 不把原始文件长期保存为正式资产。

## 历史课程与路线管理的权威关系（不适用于新商业顾问聊天）

- PostgreSQL/数据库是课程、路线、状态、正式链接和阶段关系的权威源；Dify 只保存检索副本；Redis 的 `ai:course:snapshot` 只保存 `enabled=true` 且 `review_status=approved` 的有效推荐快照。
- 管理页上传成功后先完成数据库与 Dify 写入，再重建 Redis；同一文件内有前置课程时按拓扑顺序发布，避免并发竞态。每天 Asia/Shanghai 02:00 从数据库全量重建 Redis，使用临时键后原子替换。
- 课程 Metadata 至少包含 `document_type=course`、`course_id`、`direction`、`stage`、`source_platform`、可选 `series_name` 和 `status`；路线 Metadata 至少包含 `document_type=learning_route`、`route_id`、`direction` 和 `status`。这些字段仅服务于历史目录管理，不能写入 `general` 后期待被当前 Chatflow 使用。
- 新商业顾问不生成 `course_recommendation_note`、课程卡片或路线结构；相关历史消息仅按兼容读取，不能作为新增清洗策略或 Metadata 的设计依据。
