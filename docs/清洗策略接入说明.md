# 清洗策略接入说明

## 目标

首版只需要做到：一个上传批次选择一种代码策略，多个文件独立清洗，生成 Markdown 和 Metadata，写入指定 Dify 知识库，并让每个文件最终进入成功或失败状态。

不建设策略表、脚本上传、可视化 ETL 或动态插件平台。

## 策略接口

在 `ai_management/cleaning.py` 中实现：

```python
class MyStrategy:
    code = "my_strategy"
    display_name = "我的策略"
    supported_extensions = {".md", ".docx"}
    sensitive = False

    def clean(self, file_path, original_filename):
        return [
            CleanedDocument(
                markdown="# 标题\n\n正文",
                title="标题",
                metadata={"document_type": "example"},
                parent_separator="\n# ",
                parent_max_tokens=1000,
                child_separator="\n\n",
                child_max_tokens=300,
            )
        ]
```

再把实例加入 `STRATEGY_REGISTRY`。策略定义不会写数据库；批次只记录 `strategy_code` 和 `build_version`。

每个正式策略必须同时提交：

- 至少一个正常样本。
- 空文档、异常格式或缺失字段样本。
- 清洗后 Markdown 预期结果或关键断言。
- 敏感文件名和敏感正文的处理决定。

## 名称和来源

- 原始名称保存在 `original_filename`，仅用于内部追踪和状态展示。
- 磁盘使用 `{file_id}.{扩展名}`。
- Dify 使用 `{缩短原主名}__{SHA256前8位}__{序号}.md`。
- 系统来源字段在合并 Metadata 时最后写入，策略或调用方不能覆盖。
- `sensitive=True` 时不把完整原始文件名写入 Dify Metadata。

## 成功条件

一个原文件可能生成多个 Dify 文档。必须全部满足：

1. `create-by-text` 成功并保存文档 ID。
2. 索引状态到达 completed。
3. 分块数大于0。
4. Metadata 写入成功。

任何一个失败，文件都是 `failed`，并尽量删除本次已创建的远程文档。自动重试一次；手动重试继续使用原策略和原文件。

## 当前策略

- `test_markdown`：支持 Markdown、TXT、DOCX，用于打通链路。
- `personal_business_consultation`：复用现有咨询案例 PDF 转换能力，按敏感策略处理来源名称。

正式业务策略仍需真实样本确认；不要根据文件扩展名猜测“万能清洗规则”。
