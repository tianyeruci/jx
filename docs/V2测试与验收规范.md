# AI 管理服务 V2 测试与验收规范

> 本规范定义“通过”的证据。P1、P2、H 中的历史通过声明不得直接计入 V2 验收；V2 为唯一基线。ADR-036 对商业顾问新增了“无课程/路线依赖、无课程 SSE”的硬门槛。

## 1. 状态与证据

每个需求只能标记：未实现、已实现未验证、验证失败、验证通过、已接受限制。验证通过必须有时间、环境、源码提交、镜像 ID、迁移版本、命令、脱敏原始结果和断言。原始结果存放忽略提交的 `var/reports/v2/<release-id>/`；版本库只提交脱敏摘要。

缺陷记录至少包含需求/用例 ID、重现步骤、request/task ID、期望、实际、严重级、修复提交、镜像和复测结果。

## 2. 本地门禁

| 层级 | 必测内容 | 通过条件 |
|---|---|---|
| 静态 | Ruff、导入、DSL/YAML、JSON/JSONL、无密钥扫描 | 零阻断错误；合成数据可解析；无真实秘密。 |
| 单元 | 鉴权/HMAC、上下文游标、摘要、推荐校验、点击、清洗文件头、日志脱敏 | 全部通过；新增/修改核心分支有测试。 |
| 特征 | 当前 API、SSE、Celery 任务名、CLI 和关键响应 | 模块拆分前后行为一致。 |
| 数据库 | Alembic upgrade/downgrade/重复 upgrade、约束、索引、并发游标 | 临时 PostgreSQL 成功；SQLite 不能替代此门禁。 |
| Redis | 锁 token/续租/fail-closed、点击原子写、dirty 日期和幂等落库 | 并发与故障用例无重复写、无静默降级。 |
| 构建 | wheel、不可变镜像、Compose 服务解析 | API/Worker/Scheduler 使用同一镜像。 |

建议命令以项目实际脚本为准，至少执行：

```powershell
python -m pytest -q
python -m pytest --cov=ai_management --cov-report=term-missing --cov-report=xml
python -m ruff check .
docker compose -f docker-compose.ai.yml config --services
```

## 3. 关键功能用例

### 会话与摘要

- `CONV-001`：两个用户、多会话隔离，新建/续聊/重命名/反馈/删除完整生命周期。
- `CONV-002`：同会话并发返回 409，不同会话可并行；Redis 不可用时写操作 fail-closed。
- `CONV-003`：第二轮动态 inputs 不重复历史，Dify Memory 关闭。
- `CONV-004`：同日复用 Dify 段，跨日新建段，本地会话连续。
- `CONV-005`：超过 50 条及字符预算时，SQL 与最终上下文均受限且顺序正确。
- `CONV-006`：摘要成功推进游标；超时、无效 JSON、游标竞争均不删消息、不覆盖新摘要。
- `CONV-007`：客户端断开/主动停止后，本地终态、Dify 停止、锁释放和摘要任务一致。
- `CONV-008`：7 天清理只删除已摘要覆盖消息；gap 和失败项保留并记录事件。
- `CONV-009`：测试页首轮保存本地 `conversation_id`，同一用户第二轮自动复用；新建会话、选择其他历史会话或切换用户后状态正确切换。
- `CONV-010`：当前轮、最近未摘要历史、会话摘要和画像出现冲突时，严格按规定优先级取值；新聊天不得读取路线进度，低优先级信息不得覆盖明确用户证据。
- `ADMIN-CONV-001`：管理会话列表/详情返回原始 `user_id` 且不返回 `user_hash`；历史缺失 ID 返回空值。列表取最近助手消息，详情逐消息返回推荐课程、专业见解、token 与耗时；兼容 `recommendation_note` 恒为空字符串。

### 课程、路线和点击

- `COURSE-001`：合成种子 dry-run 输出与 expected JSON 一致；缺链接、重复 ID、错误引用、停用/未审核样本行为正确。
- `COURSE-002`：停用、未审核或删除的历史目录项完成 Dify 对账；独立签名跳转不得指向不可用课程。
- `BUSINESS-COURSE-001`：新聊天请求路径对课程/路线 Redis、数据库和 Dataset 的访问均为 0；不生成课程候选、卡片或路线进度更新。
- `BUSINESS-COURSE-002`：每轮新聊天 SSE 只允许六种事件；`learning_route`、`course_cards`、`course_recommendation_note` 均为 0 次，`entry-config.business_advisor.course_recommendation=false`。
- `CLICK-001`：有效链接点击 N 次 PV 增加 N；同一匿名用户同日 UV 只增加 1。
- `CLICK-002`：无效/过期/停用课程签名不计数。
- `CLICK-003`：落库任务中断后继续处理旧 dirty 日期；重复执行不翻倍；DB 与实时 Redis 合并正确。
- `CLICK-004`：按课程/日期分页、累计、趋势和排行正确；明确标注每日 UV 之和不是跨日去重人数。

### 工具、清洗和日志

- `TOOL-001`：朋友圈/写作强类型字段、长度、未知字段和 Workflow SSE/终态。
- `CLEAN-001`：单文件 200MB、每批 10 个/500MB 边界；流式读取、伪 PDF/DOCX、二进制伪文本、路径穿越、中文超长名和重复名。
- `CLEAN-002`：多文件部分失败、自动重试一次、人工重试、Worker 重启和幂等。
- `CLEAN-003`：索引成功、零分块、Metadata、补偿成功/失败与外部删除积压。
- `CLEAN-OCR-001`：有文字层 PDF 不进入 OCR；无文字层 PDF 进入独立 `ai_ocr` 队列，模型清单和共享库校验失败时 Worker 拒绝启动。
- `CLEAN-OCR-002`：jx OCR Worker 按需启动；队列与 active/reserved/scheduled 连续 10 分钟为空后停止；启动失败保留队列任务并记录 systemd 错误，不误发布。
- `CLEAN-OCR-003`：OCR 质量、置信度、隐私、Metadata、索引和 Dify 回读全部通过才允许自动发布；页数超限、低置信度或下游门禁失败进入 `review_required`/`failed`。
- `LOG-001`：会话删除、反馈、发布、清洗、补偿、夜间任务和未处理错误均产生事件。
- `LOG-002`：按时间/等级/组件/request ID/资源筛选分页正确；普通 Token 无权访问。
- `LOG-003`：正文、用户 ID、文件敏感名、Token、Key、URL 口令不进入 stdout、事件表或页面。

## 4. Dify、RAG 与全链路

目标 Dify 1.13.3 必测：四个应用导入/发布、模型插件、动态 inputs、每日段、停止/反馈/删除、商业顾问 `general` Dataset、create-by-text、父子分块、Metadata、索引状态、零分块和补偿。普通与案例检索必须验证 `record_type` 静态过滤及分支互斥；写知识库测试只允许使用版本化 V2 测试 Dataset。

RAG 门槛：

- 40 条黄金问题全部执行；关键问题 Hit@5 ≥ 90%，全量 Recall@5 ≥ 80%。
- 引用完整率 ≥ 90%，无依据回答率 ≤ 5%。
- 课程/路线资料误入 `general`、错误 `record_type`、课程/路线 SSE 事件和虚构引用均为 0。
- 每次发布至少人工复核 10 条完整回答并记录理由。

商业全链路覆盖普通商业问题、明确咨询案例、拒答、无证据回答、跨会话续聊和当前轮/历史/摘要/画像优先级冲突；每种路径均断言不访问课程/路线依赖、不产生课程事件。记录首 Token、总耗时、Dify ID 和本地 request ID。

## 5. 性能、故障和服务器门禁

- 20 个不同会话并发流式请求持续 10 分钟；错误率、首 Token和总耗时保留分位数。
- 服务自身发出首个 SSE 状态事件 p95 < 200ms，不包含模型生成。
- 故障注入覆盖 Dify 超时/限流、Redis、PostgreSQL、Worker、客户端断流和外部删除失败。
- Redis/PostgreSQL/Dify 恢复后不得出现重复路线推进、重复点击落库、丢失已完成消息或卡死锁。
- 在当前服务器按运行手册完成备份恢复验证、不可变镜像发布、健康检查、回滚演练，并确认 Streamlit 保持回环绑定、可经 Dify 现有 Nginx 路径测试；测试结束后移除该临时路由。

## 6. 严重级与验收门槛

- **P0**：泄密、数据不可恢复、越权、错误课程正式链接；任何一个存在即停止发布。
- **P1**：核心入口不可用、消息丢失、摘要误删、锁失效、点击明显错计、清洗污染正式知识库；必须修复。
- **P2**：非核心功能或可绕过的运维问题；须有负责人和期限。
- **P3**：显示或文档问题；可排期但须记录。

正式验收条件：P0/P1 为 0；P2 有明确接受人和期限；所有功能、RAG、并发、故障、服务器、备份和回滚门禁通过；静态 Demo 与产品基线一致；验收报告由产品、开发/测试和运维共同确认。未达任一条件时只能标记“已实现未验收”。
