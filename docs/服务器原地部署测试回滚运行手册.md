# AI 管理服务 V2 服务器原地部署、测试与回滚运行手册

> 用途：由获授权运维人员在当前测试服务器执行 V2 原地更新。  
> 风险：会造成短时维护窗口，并写 PostgreSQL、Redis、Docker、Dify 测试知识库和服务器文件。执行前必须取得发布授权。  
> 基线：V2 是唯一有效基线；P1、P2、H 和旧部署文档仅作历史参考。  
> 禁止：粘贴真实密钥、打印 `.env`、删除卷、容器内热改、未验证备份即迁移、测试失败后继续放量。

## 1. 环境与占位符

支持目标：Linux x86_64、Bash、Docker Engine 与 Compose v2、Python 3.11 镜像、PostgreSQL 15、Redis 6、Dify 1.13.3。命令默认由具有项目目录和 Docker 权限的非 root 发布用户在服务器执行；仅文件权限确需时单独使用 `sudo`。

服务器 Bash 先设置非敏感变量（按实际值替换尖括号内容）：

```bash
export APP_DIR="/opt/ai-management"
export RELEASE_ID="<yyyyMMdd-HHmmss>-<git-short-sha>"
export NEW_IMAGE="jx-now-ai-management:${RELEASE_ID}"
export FIXED_IMAGE="jx-now-ai-management:0.1.0"
export BACKUP_DIR="${APP_DIR}/var/backups/${RELEASE_ID}"
export REPORT_DIR="${APP_DIR}/var/reports/v2/${RELEASE_ID}"
export COMPOSE_FILE="docker-compose.ai.yml"
```

必须具备：目标发布物及 SHA256、项目 `.env`（已配置但不输出）、数据库和 Redis 可用、Dify 内网可达、足够磁盘、测试 Dataset 写权限、维护窗口、回滚负责人。原始测试证据写入 `var/reports/v2/`，脱敏摘要再提交仓库。

## 2. 预检与停止条件

```bash
set -euo pipefail
cd "$APP_DIR"
test "$(pwd -P)" = "$APP_DIR"
test -f "$COMPOSE_FILE"
test -f .env
docker version --format '{{.Server.Version}}'
docker compose version
docker compose -f "$COMPOSE_FILE" config --services
docker compose -f "$COMPOSE_FILE" ps
df -h "$APP_DIR"
docker system df
mkdir -p "$BACKUP_DIR" "$REPORT_DIR"
```

只检查必需配置键是否存在，不输出值：

```bash
required_keys='INTERNAL_API_TOKEN ADMIN_API_TOKEN USER_HMAC_SECRET AI_POSTGRES_DB AI_POSTGRES_USER AI_POSTGRES_PASSWORD AI_REDIS_PASSWORD DATABASE_URL REDIS_URL DIFY_BASE_URL DIFY_KNOWLEDGE_BASE_URL DIFY_BUSINESS_APP_API_KEY DIFY_MOMENTS_APP_API_KEY DIFY_WRITING_APP_API_KEY DIFY_SUMMARY_PROFILE_APP_API_KEY DIFY_GENERAL_DATASET_ID DIFY_COURSE_DATASET_ID'
: > "$REPORT_DIR/config-keys-present.txt"
: > "$REPORT_DIR/config-keys-missing.txt"
for key in $required_keys; do
  if grep -Eq "^[[:space:]]*${key}=.+" .env; then
    printf '%s\n' "$key" >> "$REPORT_DIR/config-keys-present.txt"
  else
    printf '%s\n' "$key" >> "$REPORT_DIR/config-keys-missing.txt"
  fi
done
test ! -s "$REPORT_DIR/config-keys-missing.txt"
```

该检查只保存键名、不保存值；`config-keys-missing.txt` 非空会立即停止。然后检查当前迁移与健康状态：

```bash
docker compose -f "$COMPOSE_FILE" exec -T api alembic current | tee "$REPORT_DIR/alembic-before.txt"
curl --fail --silent --show-error http://127.0.0.1:8000/health/live | tee "$REPORT_DIR/health-live-before.json"
curl --fail --silent --show-error http://127.0.0.1:8000/health/ready | tee "$REPORT_DIR/health-ready-before.json"
```

立即停止发布的条件：目录不符、磁盘余量不足以同时容纳备份和新镜像、服务已处于未知故障、必需配置缺失、目标 Dataset 无法确认是测试库、存在另一个构建/迁移/发布进程、无法创建或验证备份、迁移没有评审过的兼容/回滚结论。

## 3. 备份与备份验证

进入维护窗口，停止会产生业务写入的服务，保留 PostgreSQL 和 Redis：

```bash
cd "$APP_DIR"
docker compose -f "$COMPOSE_FILE" stop api worker scheduler test-ui 2>/dev/null || true
docker compose -f "$COMPOSE_FILE" ps
```

加载 `.env` 只为当前 Shell 提供变量；禁止执行 `env` 或 `docker compose config` 全量输出：

```bash
set -a
. ./.env
set +a
```

保存发布元数据、Compose 和数据库逻辑备份：

```bash
docker image inspect "$FIXED_IMAGE" --format '{{.Id}}' | tee "$BACKUP_DIR/old-image-id.txt"
docker tag "$FIXED_IMAGE" "jx-now-ai-management:rollback-${RELEASE_ID}"
cp -a "$COMPOSE_FILE" "$BACKUP_DIR/"
cp -a docker-compose.ui.yml "$BACKUP_DIR/" 2>/dev/null || true
docker compose -f "$COMPOSE_FILE" exec -T postgres \
  pg_dump -U "$AI_POSTGRES_USER" -d "$AI_POSTGRES_DB" -Fc \
  > "$BACKUP_DIR/postgres.dump"
test -s "$BACKUP_DIR/postgres.dump"
docker compose -f "$COMPOSE_FILE" exec -T postgres \
  pg_restore -l < "$BACKUP_DIR/postgres.dump" \
  > "$BACKUP_DIR/postgres-contents.txt"
test -s "$BACKUP_DIR/postgres-contents.txt"
sha256sum "$BACKUP_DIR/postgres.dump" > "$BACKUP_DIR/SHA256SUMS"
```

验证可恢复性必须使用临时数据库，而不是覆盖当前库：

```bash
export VERIFY_DB="ai_restore_check_${RELEASE_ID//-/_}"
docker compose -f "$COMPOSE_FILE" exec -T postgres \
  createdb -U "$AI_POSTGRES_USER" "$VERIFY_DB"
docker compose -f "$COMPOSE_FILE" exec -T postgres \
  pg_restore -U "$AI_POSTGRES_USER" -d "$VERIFY_DB" --no-owner --no-privileges \
  < "$BACKUP_DIR/postgres.dump"
docker compose -f "$COMPOSE_FILE" exec -T postgres \
  psql -U "$AI_POSTGRES_USER" -d "$VERIFY_DB" -Atc \
  "select count(*) from information_schema.tables where table_schema='public';" \
  | tee "$BACKUP_DIR/restore-table-count.txt"
docker compose -f "$COMPOSE_FILE" exec -T postgres \
  dropdb -U "$AI_POSTGRES_USER" "$VERIFY_DB"
```

表数必须大于 0。Redis 点击存在未落库实时值时，先触发项目提供的幂等点击落库任务；若该任务尚未实现或失败，停止发布。随后保存 Redis 持久化快照：

```bash
REDISCLI_AUTH="$AI_REDIS_PASSWORD" docker compose -f "$COMPOSE_FILE" exec -T -e REDISCLI_AUTH redis redis-cli BGSAVE
until [ "$(REDISCLI_AUTH="$AI_REDIS_PASSWORD" docker compose -f "$COMPOSE_FILE" exec -T -e REDISCLI_AUTH redis redis-cli LASTSAVE)" != "0" ]; do sleep 1; done
redis_container="$(docker compose -f "$COMPOSE_FILE" ps -q redis)"
docker cp "${redis_container}:/data/dump.rdb" "$BACKUP_DIR/redis-dump.rdb"
test -s "$BACKUP_DIR/redis-dump.rdb"
sha256sum "$BACKUP_DIR/redis-dump.rdb" >> "$BACKUP_DIR/SHA256SUMS"
```

上传卷若含不可重建文件，使用独立临时容器只读打包命名卷：

```bash
docker run --rm -v ai-management_ai_uploads:/source:ro -v "$BACKUP_DIR:/backup" alpine:3.20 \
  tar -C /source -czf /backup/uploads.tar.gz .
test -s "$BACKUP_DIR/uploads.tar.gz"
sha256sum "$BACKUP_DIR/uploads.tar.gz" >> "$BACKUP_DIR/SHA256SUMS"
sha256sum -c "$BACKUP_DIR/SHA256SUMS"
```

如果实际卷名不同，先用 `docker volume ls` 确认并替换精确名称；不得猜测或使用通配删除。Dify DSL 有改动时，另行从 Dify 控制台导出当前已发布 DSL并记录 App、Dataset、发布时间和文件哈希。

## 4. 构建或导入不可变镜像

发布物必须来自已通过本地门禁的源码提交。服务器构建方式：

```bash
cd "$APP_DIR"
ps -ef | grep '[d]ocker build\|[d]ocker compose.*build' && exit 1 || true
docker build --pull=false -f Dockerfile.offline -t "$NEW_IMAGE" .
docker image inspect "$NEW_IMAGE" --format '{{.Id}}' | tee "$REPORT_DIR/new-image-id.txt"
docker tag "$NEW_IMAGE" "$FIXED_IMAGE"
```

若使用离线镜像包，先在本地记录 SHA256，上传后在服务器校验再执行 `docker load -i <IMAGE_TAR>`；不得使用可变远端 `latest`。构建或导入失败最多在排除明确瞬态原因后重试两次，禁止并发重复构建。

## 5. 迁移与发布

先启动依赖与新 API，执行迁移：

```bash
cd "$APP_DIR"
docker compose -f "$COMPOSE_FILE" up -d postgres redis api
docker compose -f "$COMPOSE_FILE" exec -T api alembic upgrade head | tee "$REPORT_DIR/alembic-upgrade.txt"
docker compose -f "$COMPOSE_FILE" exec -T api alembic current | tee "$REPORT_DIR/alembic-after.txt"
```

迁移报错立即停止；不得反复执行有副作用的手工 SQL。迁移成功后同步重建三个进程：

```bash
docker compose -f "$COMPOSE_FILE" up -d --no-build --force-recreate api worker scheduler
docker compose -f "$COMPOSE_FILE" ps | tee "$REPORT_DIR/compose-ps.txt"
docker compose -f "$COMPOSE_FILE" logs --tail=200 api worker scheduler > "$REPORT_DIR/startup.log"
```

确认日志无密钥后才允许保存或分享。最后按需启动只绑定回环地址的 UI：

```bash
docker compose -f "$COMPOSE_FILE" -f docker-compose.ui.yml --profile test up -d --no-build test-ui
docker ps --filter name=test-ui --format '{{.Names}} {{.Ports}} {{.Status}}' | tee "$REPORT_DIR/ui-binding.txt"
```

若输出含 `0.0.0.0:8501` 或 `[::]:8501`，立即停止 `test-ui` 并修复绑定。

## 6. 发布后验证

### 6.1 健康和版本

```bash
curl --fail --silent --show-error http://127.0.0.1:8000/health/live | tee "$REPORT_DIR/health-live.json"
curl --fail --silent --show-error http://127.0.0.1:8000/health/ready | tee "$REPORT_DIR/health-ready.json"
docker compose -f "$COMPOSE_FILE" exec -T api python -c "import ai_management; print('${RELEASE_ID}')" | tee "$REPORT_DIR/release.txt"
```

### 6.2 自动与契约测试

只在已经确认的 V2 测试知识库执行带写入的契约测试：

```bash
docker compose -f "$COMPOSE_FILE" exec -T api python scripts/dify_contract_check.py | tee "$REPORT_DIR/dify-contract.txt"
docker compose -f "$COMPOSE_FILE" exec -T api python scripts/live_business_lifecycle.py | tee "$REPORT_DIR/business-lifecycle.txt"
docker compose -f "$COMPOSE_FILE" exec -T api python scripts/live_stop_check.py | tee "$REPORT_DIR/stop-check.txt"
docker compose -f "$COMPOSE_FILE" exec -T api ai-rag-eval test_data/rag/golden_questions.jsonl --top-k 5 --output var/reports/rag.json
docker compose -f "$COMPOSE_FILE" exec -T api python scripts/evaluate_business_e2e.py test_data/rag/business_e2e_cases.jsonl --base-url http://127.0.0.1:8000 --output var/reports/business-e2e.json
```

`--write-knowledge` 仅在测试 Dataset ID 已人工复核后执行，并确认临时文档已删除。随后按 `V2测试与验收规范.md` 验证：三个入口和 SSE、多用户/跨日/摘要、停用课程、签名跳转与 PV、日志后台权限、清洗成功/失败/补偿、20 并发 10 分钟、依赖故障和 Worker 重启。

### 6.3 UI 访问

在本地 PowerShell 使用占位 SSH 主机：

```powershell
ssh -N -L 127.0.0.1:8501:127.0.0.1:8501 <ssh-host-alias>
```

打开 `http://127.0.0.1:8501`，验证日志筛选、错误详情、点击累计与趋势、清洗重试及测试页面。不得把 Admin Token 写入截图或报告。

## 7. 修复闭环

发现缺陷后：停止受影响测试 → 保存 request ID、事件 ID、版本和脱敏日志 → 在本地修复并补回归测试 → 构建新的 `RELEASE_ID` 和不可变镜像 → 重复本手册预检、备份增量确认、发布和受影响测试 → 再跑基础冒烟。禁止在服务器容器或挂载源码中热改。

## 8. 回滚

回滚触发条件：健康检查失败超过 5 分钟、数据写入/迁移异常、错误率显著上升、核心入口/SSE/课程跳转失败、日志泄密、无法确认点击或摘要数据一致性。出现泄密先隔离访问并轮换凭据，再恢复服务。

### 8.1 仅应用回滚（迁移向后兼容）

```bash
cd "$APP_DIR"
docker tag "jx-now-ai-management:rollback-${RELEASE_ID}" "$FIXED_IMAGE"
docker compose -f "$COMPOSE_FILE" up -d --no-build --force-recreate api worker scheduler
curl --fail --silent --show-error http://127.0.0.1:8000/health/live
curl --fail --silent --show-error http://127.0.0.1:8000/health/ready
```

### 8.2 数据库回滚（仅评审确认不兼容时）

优先使用已经测试过的 Alembic downgrade。若必须从备份恢复，先停止所有写入者并再次备份故障现场：

```bash
cd "$APP_DIR"
docker compose -f "$COMPOSE_FILE" stop api worker scheduler test-ui 2>/dev/null || true
docker compose -f "$COMPOSE_FILE" exec -T postgres pg_dump -U "$AI_POSTGRES_USER" -d "$AI_POSTGRES_DB" -Fc > "$BACKUP_DIR/failed-state.dump"
docker compose -f "$COMPOSE_FILE" exec -T postgres dropdb -U "$AI_POSTGRES_USER" --if-exists "$AI_POSTGRES_DB"
docker compose -f "$COMPOSE_FILE" exec -T postgres createdb -U "$AI_POSTGRES_USER" "$AI_POSTGRES_DB"
docker compose -f "$COMPOSE_FILE" exec -T postgres pg_restore -U "$AI_POSTGRES_USER" -d "$AI_POSTGRES_DB" --no-owner --no-privileges < "$BACKUP_DIR/postgres.dump"
docker tag "jx-now-ai-management:rollback-${RELEASE_ID}" "$FIXED_IMAGE"
docker compose -f "$COMPOSE_FILE" up -d --no-build --force-recreate api worker scheduler
```

这一步会覆盖数据库，只能由已授权管理员在确认备份哈希和恢复点后执行。上传卷/Redis 恢复仅在明确发生相应数据损坏时执行；不得为应用缺陷盲目覆盖。Dify 与应用独立版本化，DSL 回滚后必须重跑契约和业务 E2E。

## 9. 完成标准与已知限制

发布只有在健康、迁移、核心冒烟、日志权限、点击计数、Dify 契约、RAG、清洗和回滚点均有脱敏证据时完成。任何核心门禁失败均保持“未验收”。

已知限制：不保存逐次点击事件，因此 Redis 与其持久化同时损坏时无法逐条重放；原地更新存在维护窗口；数据库恢复会丢弃备份点后的写入，所以维护窗口内必须停止业务写入。
