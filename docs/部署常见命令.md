# 部署常见命令

本文件记录 jx 服务器上常用的、已验证的部署命令。执行前确认当前目录为 `/opt/ai-management`，并遵守对应部署手册中的备份、回滚和验证要求。

## 更新DSL重新构建服务

适用场景：只修改服务器 `.env` 中已有 Dify Chatflow/DSL 应用访问 Key，例如 `DIFY_BUSINESS_APP_API_KEY`、`DIFY_MOMENTS_APP_API_KEY`、`DIFY_WRITING_APP_API_KEY` 或 `DIFY_SUMMARY_PROFILE_APP_API_KEY`。

这不会重新构建 wheel 或镜像，也不会重新发布 Dify DSL；它只强制重新创建会读取 `.env` 的 jx 核心服务。

```bash
cd /opt/ai-management

docker compose -f docker-compose.ai.yml \
  up -d --no-deps --force-recreate api worker scheduler
```

执行后验证：

```bash
docker compose -f docker-compose.ai.yml ps api worker scheduler

docker compose -f docker-compose.ai.yml exec -T api \
  python -c "import urllib.request; print(urllib.request.urlopen('http://127.0.0.1:8000/health/ready', timeout=10).read().decode())"
```

预期 `/health/ready` 返回 `status=ready`，并且 `dify_reachable=true`。必要时再使用目标 Chatflow 的 `/parameters` 或一次真实请求验证访问 Key 映射。

### 判断三个服务是否重建成功

下面的命令会逐个检查 `api`、`worker`、`scheduler`：容器必须存在、状态必须为 `running`，并且三个服务必须使用同一个镜像。任一条件不满足时返回非零退出码；全部通过时输出 `PASS`。

```bash
set -e

services="api worker scheduler"
image=""

for service in $services; do
  container="ai-management-${service}-1"
  state=$(docker inspect --format '{{.State.Status}}' "$container" 2>/dev/null || true)
  current_image=$(docker inspect --format '{{.Config.Image}}' "$container" 2>/dev/null || true)

  test "$state" = "running" || {
    echo "FAIL: $service state=$state"
    exit 1
  }
  test -n "$current_image" || {
    echo "FAIL: $service image is missing"
    exit 1
  }

  if [ -z "$image" ]; then
    image="$current_image"
  elif [ "$current_image" != "$image" ]; then
    echo "FAIL: $service image=$current_image, expected=$image"
    exit 1
  fi

  echo "PASS: $service state=$state image=$current_image"
done

echo "PASS: api worker scheduler are running with image=$image"
```

如果还需要确认本次确实读取了新 Key，可在不输出 Key 明文的前提下比较 `.env` 与三个容器中目标变量的哈希：

```bash
key="DIFY_MOMENTS_APP_API_KEY"
env_hash=$(grep -E "^[[:space:]]*${key}=" .env | sha256sum | cut -c1-12)

for service in api worker scheduler; do
  container="ai-management-${service}-1"
  container_hash=$(docker inspect --format '{{range .Config.Env}}{{println .}}{{end}}' "$container" \
    | grep -E "^${key}=" | sha256sum | cut -c1-12)
  test "$container_hash" = "$env_hash" || {
    echo "FAIL: $service does not match .env for $key"
    exit 1
  }
  echo "PASS: $service $key hash=$container_hash"
done
```

### 注意事项

- 推荐在修改 `.env` 前先复制一份带时间戳的备份。
- 不要用 `docker compose restart` 代替 `--force-recreate`；普通重启不会重新读取修改后的 `env_file`。
- 仅修改 Chatflow App Key 时，不要运行 `scripts/jx_quick_deploy.sh`，不要制作或上传 `ai_management.zip`。
- 修改 `DIFY_BASE_URL`、知识库地址或知识库 Key 时，按实际消费者扩大重建范围。
- 修改本地 DSL 内容时，还必须在 Dify 控制台重新导入、保存并发布；本命令不会发布本地 DSL。
- 不要执行 `docker compose down -v` 或未经确认的 `--remove-orphans`，避免影响数据库、Redis、上传卷或历史回滚容器。

详细流程见：[V2 从开发到服务器部署与回滚手册](V2从开发到服务器部署与回滚手册.md)第 0.1 节，以及排障条目 [DEPLOY-013](troubleshooting/deployment.md#deploy-013修改-chatflow-env-后必须强制重建读取配置的服务)。
