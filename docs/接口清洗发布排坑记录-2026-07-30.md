# 接口清洗发布排坑记录

日期：2026-07-30  
对应发布：`0.2.1-contract-cleaning-90a23f26-r3`

本文记录本轮基线、统一修复、发布和远端回归中出现的问题。所有问题均在完整基线结束后统一处理。

## 1. 测试配置误触生产校验

触发条件：在本地 shell 直接导入应用，测试环境变量、数据库地址或设置缓存没有在应用导入前完成隔离。

错误表现：

- 配置校验按生产口径提前执行。
- 测试可能连接错误的数据库/Redis，或在 fixture 生效前失败。
- 结果容易被误判为业务接口失败。

定位过程：

1. 对比 pytest、迁移命令和 Compose 容器内实际加载的 `APP_ENV`、数据库类型及服务地址。
2. 确认设置对象存在进程级缓存，导入顺序会影响测试配置是否生效。
3. 将本地测试与远端验证的执行边界分开。

解决方式：

- 本地测试只使用隔离测试配置和临时数据库。
- 迁移测试单独使用临时 SQLite。
- 远端测试在已部署容器内加载服务器 `.env`，不把生产密钥复制到本地或报告。

防复发：

- 测试配置必须在应用模块导入前就绪。
- 不用一次本地失败推断远端生产配置错误。
- 报告只记录配置指纹和连接状态，不记录密钥。

## 2. jx 主机回环地址不可用

触发条件：直接在 jx 主机调用 `127.0.0.1:8000`，但 API 端口只在 Compose 网络内提供，没有绑定到宿主机回环地址。

错误表现：宿主机请求连接失败，而容器实际健康。

定位过程：

1. 检查 Compose 端口和容器状态。
2. 在 API 容器内访问 `127.0.0.1:8000/health/ready` 成功。
3. 一次性测试容器通过 `http://api:8000` 成功。

解决方式：

- 健康和迁移检查使用 `docker compose exec api`。
- 一次性 runner 使用 Compose 服务名 `api:8000`。
- 不为测试临时开放公网或宿主机端口。

防复发：远端脚本统一封装容器内健康检查，不把宿主机回环失败判为服务故障。

## 3. 接口 runner 权限与异步等待误判

触发条件：首次 runner 没有完全复用容器内鉴权上下文，且对异步清洗文件的等待上限偏短。

错误表现：

- 首轮接口权限检查失败。
- 后续出现 `36/37`，但后台任务稍后进入正确终态。

定位过程：

1. 将接口日志、任务终态和 runner 超时点对齐。
2. 使用专项停止生成脚本验证服务行为正常。
3. 确认失败来自 runner 权限/等待口径，而非接口字段或状态机。

解决方式：

- runner 使用正式的内部/管理员请求头。
- 异步文件等待上限提高并轮询到明确终态。
- 每个测试组单独记录退出码，不因单项失败中断证据收集。

验证：r3 远端 8 组退出码全部为 `0`，接口 `37/37`。

防复发：接口 runner 必须区分“请求失败”“任务仍在处理”和“任务终态失败”。

## 4. 清洗验收把 Dify 内建 Metadata 当成泄露

触发条件：验收脚本比较了 Dify 返回的全部 Metadata，而 Dify 会附带内建字段。

错误表现：首轮报告显示 `0/15`，与实际文档索引和分块状态不一致。

定位过程：

1. 分别查看策略声明的 `dify_metadata_fields` 和 Dify 原始响应。
2. 确认失败字段属于 Dify 内建元数据，不是服务上传的自定义来源字段。

解决方式：只对策略允许的自定义 Metadata 做等值/最小化断言，Dify 内建字段不参与“过度暴露”判定。

验证：修正验收口径后，真实服务问题仍被独立检出；最终 r3 为 `15/15`。

防复发：验收脚本按“服务提交字段”和“平台内建字段”分别检查。

## 5. 咨询 DOCX 缺失，隐私门禁被写成文件失败

触发条件：上传个人商业咨询 DOCX，或 PDF 无法可靠提取/脱敏。

错误表现：

- DOCX 不在支持扩展名。
- PDF 残留隐私或版面不确定时抛出普通清洗异常。
- 调用方无法区分“文件坏了”和“需要人工复核”。

定位过程：比较策略支持扩展名、PDF 转换结果的 `needs_review`/`residual_pii` 与清洗状态聚合逻辑。

解决方式：

- 增加 DOCX Markdown 提取和同一套匿名化逻辑。
- 对无法自动发布的 DOCX/PDF生成 `review_required` 条目。
- 空正文使用安全占位，只用于复核展示，不进入自动发布。

验证：真实 DOCX 成功、真实 PDF 待复核；安全合成 DOCX/PDF 成功；残留隐私 DOCX 被门禁。

防复发：每个敏感策略必须同时有成功、待复核和无正文/异常格式用例。

## 6. 公众号、小报童、知识星球身份信息残留

触发条件：身份出现在标题、正文、作者行、昵称、笔名或个人账号称呼中。

错误表现：正文已做部分清洗，但标题或 Metadata 仍可暴露身份；不同来源策略行为不一致。

定位过程：

1. 对清洗后标题、正文和业务 Metadata 统一序列化扫描。
2. 将解析器给出的作者与正文中发现的身份候选合并。
3. 检查别名映射是否错误写入 Dify。

解决方式：

- 增加统一身份发现和稳定别名替换。
- 标题、正文、来源语境和业务 Metadata 同时替换。
- 别名映射只保存在本地受保护审计数据中。

验证：小报童 `3+3`、公众号 `29+84`、知识星球 1 份样本均通过身份扫描。

防复发：新策略必须声明身份来源并运行统一公开文本扫描。

## 7. SSE 跨分片、历史消息与引用泄露

触发条件：

- 一个姓名或文件名跨两个 `answer_delta` 分片。
- Dify 在 `retriever_resources` 中返回原文件名、管理名或 URL。
- 历史消息直接返回旧的未过滤内容。

错误表现：逐分片简单替换无法命中完整词；刷新历史后仍可能看到受保护来源。

定位过程：构造跨分片姓名，分别检查实时 SSE、持久化消息和历史查询。

解决方式：

- 引入带尾部缓冲的跨分片词过滤器。
- 回答流先做身份/来源替换，再做 URL 过滤。
- `retriever_resources`、会话标题、消息正文和历史推荐统一经过公开输出过滤。
- 课程卡签名 `redirect_url` 单独保留。

验证：本地跨分片契约通过，jx 公开聊天与引用 `3/3`。

防复发：任何新增公开输出字段都必须进入同一个 redaction 边界。

## 8. Dify 管理名与公开引用边界混淆

触发条件：拆分文档使用管理名称，Dify 又把该名称作为检索来源返回。

错误表现：

- 旧名称为 `主体__SHA前8位__序号.md`，不符合已确认格式。
- 管理端需要原文件语义，但小程序引用不应显示原文件名。

定位过程：分别确认“管理员可追踪”和“普通用户不可见”两套边界，不能用删除管理名称解决公开泄露。

解决方式：

- 管理名改为 `主体__NNN.原扩展名`，超长名称确定性截断。
- 管理端保留原始追踪字段。
- 公开引用将原文件名和 Dify 管理名替换为受保护来源。

验证：127 个成功子文档名称回读通过，公开引用已知名称 0 泄露。

防复发：管理字段和公开字段分开建模，禁止直接转发 Dify 原始资源对象。

## 9. 同源子文档部分发布

触发条件：一个源文件拆分多个文档，其中后续文档在创建、索引、分块或 Metadata 校验时失败。

错误表现：

- 前面的文档已留在 Dify。
- 文件可能显示 `mixed`。
- 课程/路线目录与 Dify 状态不一致。

定位过程：

1. 在本地受控客户端中让指定子文档 Metadata 回读失败。
2. 记录已创建远端 ID、数据库事务和 Redis 快照变化。
3. 确认旧实现按子项并发提交，缺少源级补偿。

解决方式：

- 同源条目先预检，再串行远端验证。
- 任一失败补偿删除全部本轮同源文档。
- 补偿失败建立外部删除任务。
- 课程/路线目录使用一个数据库事务提交，Redis 在事务成功后重建。

验证：本地故障注入通过；84 子文档真实源完整提交；远端测试结束能按报告精确删除全部 127 个成功文档。

防复发：禁止在子项成功时提前提交目录或刷新成功状态。

## 10. Dify Metadata 过度写入

触发条件：本地完整来源 Metadata 与 Dify 可检索 Metadata 使用同一个字典。

错误表现：原文件名、文件 ID、SHA、批次 ID 或审计映射可能进入 Dify。

解决方式：

- 本地保留完整 Metadata。
- Dify 只从策略 `dify_metadata_fields` 构建最小字典。
- 写入后逐字段回读校验。

验证：真实样本 15/15；验收脚本未发现策略外自定义 Metadata。

防复发：新策略必须显式声明 Dify 字段白名单，空白名单表示不写自定义字段。

## 11. 大 GB18030 文件被误判损坏

触发条件：读取文件前 64 KiB 做严格解码，采样末尾恰好截断 GB18030 多字节字符。

错误表现：84 篇公众号样本在内容正常时报告签名/编码无效。

定位过程：对比完整文件解码和 64 KiB 样本解码，确认错误只发生在采样边界。

解决方式：使用增量解码器，采样阶段 `final=False`，允许末尾保留未完成字符；后续完整读取仍执行严格校验。

验证：公众号 `29+84` 稳定拆分并通过。

防复发：多字节编码的前缀探测不得把“样本末尾不完整”当作“完整文件损坏”。

## 12. raw 父块数为 0 被真值逻辑覆盖

触发条件：raw 模式明确期望父块数为 `0`，旧代码使用 `expected or default`。

错误表现：合法的 `0` 被替换为默认值，远端验证误报。

解决方式：只在值为 `None` 时使用默认值，`0` 作为有效期望保留。

验证：raw 合成样本 1/1 通过。

防复发：计数类配置区分 `None` 和 `0`，不使用通用真值回退。

## 13. 只修改 DSL/提示词不会更新已发布 Dify 工作流

触发条件：本地 `dify/dsl` 和提示词文件已更新，但线上 Chatflow 未重新导入发布。

错误表现：代码仓库看似已有隐私指令，线上模型输入实际仍是旧版本。

定位过程：检查现有工作流已使用动态 `business_output_style` 输入，但本地文件同步不会改变已发布应用。

解决方式：

- 服务端在 `business_output_style` 中追加隐私指令。
- 保留输出端跨分片与资源过滤作为强制防线。
- 不为此导入新应用或轮换 API key。

验证：本地测试捕获 Dify inputs 并确认指令存在；r3 远端接口 `37/37`、公开引用 `3/3`。

防复发：涉及线上 Dify 行为的改动必须明确区分“仓库文件已改”和“已发布工作流实际收到”。

## 14. RAG 通用库清空后的假失败

触发条件：测试前按要求清空通用测试文档，但 golden set 仍包含 10 个通用检索问题。

错误表现：通用 Recall@5 为 `0`，聚合仅 `0.6414`；课程库仍为 `0.9203`。

解决方式：

- RAG runner 临时创建一份与 golden set 对应的通用验收资料。
- 等索引与 Metadata 完成后评测。
- 无论评测成功或异常，都在 `finally` 删除该文档。

验证：通用 `1.0`、课程 `0.9203`、聚合 `0.9444`；最终通用库文档数为 `0`。

防复发：检索评测必须声明 fixture 生命周期，不能把“空知识库”误判为检索算法退化。

## 15. 源码已同步但容器仍运行旧 wheel

触发条件：只把源码复制到 `/opt/ai-management`，离线镜像仍从 `wheelhouse` 安装旧 wheel。

错误表现：服务器文件是新代码，API/Worker/Scheduler 行为仍旧。

解决方式：

1. 构建唯一 wheel 并核验 SHA-256。
2. 替换 `wheelhouse` 中的固定 wheel。
3. 离线重建核心与 UI 镜像。
4. 让 API、Worker、Scheduler 同时切换同一核心镜像。
5. 校验每个容器的 `.Config.Image` 和镜像 ID。

验证：四个服务均使用 `0.2.1-contract-cleaning-90a23f26-r3`。

防复发：发布证据必须同时包含 wheel SHA、镜像 ID、容器镜像名和运行时健康检查。

## 16. 最终清理不能依赖模糊名称

触发条件：真实样本的管理名可能不带 `test`、`synthetic` 或“验收”等标记。

风险：仅按名称正则清理会漏删测试文档；扩大正则又可能误删正式文档。

解决方式：

- 从本轮清洗报告读取精确 `document_ids`。
- 按 case 所属知识库分别删除 124 个通用文档和 3 个课程/路线文档。
- 再运行正式 ID 白名单保护的数据清理脚本。
- 清理后重新做受保护状态快照。

验证：正式课程 `9`、路线 `2`、Dify 课程文档 `11`、通用文档 `0`，额外课程/路线均为 `0`。

防复发：所有创建外部资源的验收脚本必须把精确远端 ID 写入受保护报告，并提供 `finally` 或发布后精确清理路径。

## 17. 工具输出与静态检查口径

- RTK 的 pytest/搜索封装在本环境曾出现过滤或参数兼容问题；最终证据在确认封装问题后使用原始 pytest/JUnit 输出复核，未把封装器失败算作产品失败。
- 本轮发布作用域 Ruff 为 0；全仓另有 11 个历史迁移/工具问题。迁移历史没有为追求全仓数字而机械重排。
- 清洗 runner 的进程退出码与报告内部通过数分别核验，避免“脚本退出 0”掩盖用例失败。
