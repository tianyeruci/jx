# V2 现阶段全链路审计报告（2026-07-28）

> 本文保存 2026-07-28 对背景、操作场景、V2 文档、当前代码、测试与 jx 测试服务器的核验结论。
>
> 证据分类：**本次已核验**、**历史记录**、**待验证**。不能将历史记录写成新的验收结论。

## 1. 结论

**不需要推倒重来。** 当前项目已经是可部署、可联调的 V2 测试版；但它尚未完全满足 2026-07-28 更新后的操作场景，也还不能据此宣称可正式上线。

准确定位如下：

| 维度 | 结论 |
| --- | --- |
| 测试服务器 | 正常运行，可继续联调 |
| 小程序后端主流程 | 已具备，能够开始接入 |
| 最新业务场景 | 部分完成，路线、画像、混合问题等仍有缺口 |
| 管理与运维 | 有日志、统计、清洗和临时测试页，但管理配置不完整 |
| 容量与故障恢复 | 尚未完成验收，不能用于活动峰值承诺 |
| 正式上线 | 暂不具备完整验收依据 |

本轮应采用“补齐关键链路 + 更新测试 + 再部署验收”的方式，不应从零重写。

## 3. 已完成工作

### 3.1 全链路基础能力

- FastAPI 服务、SSE 流式返回、统一错误结构、请求 ID、用户 ID HMAC 脱敏。
- Dify 四应用接入：商业顾问、朋友圈助手、写作助手、摘要与画像 Workflow。
- 两个知识库接入：通用知识库与课程知识库。
- PostgreSQL 持久化商业会话、消息、推荐结果、课程目录、路线、学习进度、清洗状态和事件日志。
- Redis 用于会话锁、停止标记、缓存、PV/UV 实时计数和 Celery Broker/Backend。
- Celery Worker、Beat 定时维护、清洗异步任务、失败补偿框架。

### 3.2 三个用户入口

- 商业顾问支持多轮问答、历史、反馈、课程推荐和学习路线。
- 朋友圈助手与写作助手使用无状态 Workflow，不保存商业会话、画像或课程点击事件。
- 入口开场白和推荐问题可由 Dify 参数接口聚合。

### 3.3 商业顾问会话生命周期

- 新建会话、续聊、停止生成、历史列表、消息列表、重命名、删除和反馈。
- SSE 可返回：`request_started`、`status`、`answer_delta`、`retriever_resources`、`course_cards`、`learning_route`、`expert_insight`、`message_end`、`error`。
- 保存 Token 用量、首 Token 耗时、总耗时、推荐结果和检索资源。
- 同一会话同时生成时返回 `409 CONVERSATION_BUSY`。

### 3.4 课程推荐、跳转与统计

- 本地课程和路线目录审核、启用状态校验。
- 模型候选课程 ID 二次校验；停用、未审核或虚构课程不会生成有效课程卡片。
- 课程正式地址由服务端生成签名跳转链接，模型不直接输出正式链接。
- 点击统计采用每日聚合：有效跳转每次增加 PV，同一用户同一天只增加一次 UV。

这满足“统计课程链接被点击次数”的需求。当前不保存每一次点击的明细事件，因此不能查询单次点击时间线或逐次审计记录。

### 3.5 运维、日志和部署

- 管理员双 Token 保护的会话、课程目录、PV/UV 和事件日志查询接口。
- 结构化 JSON 容器日志和 `SystemEventLog` 事件日志。
- 清洗批次、单文件状态、失败重试能力。
- 不可变核心/UI 镜像、发布校验、数据库/Redis/上传卷备份、恢复验证、迁移、健康检查和回滚手册。
- Streamlit 临时页通过 Dify 既有 Nginx 的 `/ai-management-test/` 路径访问，不新增公网端口。

## 4. 最新场景与当前实现的差距

### P0：摘要与用户画像不会按聊天阈值自动触发

当前会话流在计算 `enqueue_summary` 之前就判断是否入队；该变量此时固定为 `False`。因此达到摘要阈值后，正常聊天不会自动把摘要与画像任务加入 Worker。

影响：

- 长会话摘要不及时。
- 用户画像不能及时更新。
- 跨会话的个性化课程/路线推荐效果不足。
- 只有手工调用或夜间清理等旁路可能触发摘要。

证据：`ai_management/conversations.py` 中入队判断位于约第 268 行，而实际 `enqueue_summary` 结果在约第 383 行才获得。

### P0：学习路线流程与最新场景不一致

最新场景要求：

1. 先说明路线和推荐原因。
2. 让用户确认路线。
3. 询问或引导用户说明当前所处阶段。
4. 再推荐当前阶段和下一阶段课程。

当前实现的问题：

- 无进度时会默认第一阶段。
- 课程卡片只筛选当前阶段，不包含下一阶段。
- 旧 E2E 用例要求首次路线推荐立即返回课程，与最新“先确认、后推荐”的要求不一致。

### P0：混合问题没有真正结构化拆分

最新场景要求课程问题查询课程知识库，非课程问题查询通用知识库，再合并回答。

当前 Dify 流程会将同一个完整 `sys.query` 依次交给通用和课程知识库；它不是“先拆分子问题，再分别检索”的实现。该方式可能可用，但无法稳定保证复杂混合问题的检索边界。

### P0：数据库和 Redis 拓扑不符合最新要求

最新要求是使用 Dify 的 PostgreSQL 和 Redis，但与 Dify 的数据区分开。

当前部署实际创建了独立的：

- `ai-management-postgres`
- `ai-management-redis`
- 独立 PostgreSQL、Redis 和上传卷

所以这一项尚未按最新要求完成。若后续迁移，建议使用同一实例但逻辑隔离：PostgreSQL 使用独立数据库和角色；Redis 使用确认未占用的逻辑 DB、`ai:` 键前缀，必要时配置独立 ACL 用户。迁移前必须完成备份、恢复验证和回滚预案。

### P1：历史保留和后台配置未闭环

需求是默认保留 7 天、后台可调整、每天凌晨 2 点执行，且模型上下文主要使用当前日原始消息和历史摘要。

当前状态：

- 默认 7 天已实现，但仅通过环境变量配置。
- 当前默认清理时间是 03:30，不是 02:00。
- 没有可修改保留天数和清理时间的后台接口或页面。
- 摘要由轮数/字符阈值触发，不是严格跨日摘要策略。
- 展示给用户的 7 天历史与发送给模型的上下文尚未明确拆成两套策略。

### P1：聊天附件能力缺失

商业顾问请求目前仅有 `query` 和可选 `conversation_id`；Dify 商业顾问 DSL 的文件上传也是关闭状态。

如果“上传附件”指用户在商业顾问对话中上传文件，则目前缺少：上传接口、文件存储、安全校验、模型引用、管理员查看和清理策略。

如果附件仅指知识库管理上传，则可优先使用 Dify 原生能力，不必重复建设。

### P1：单文件超过 50MB 不支持

背景说明存在超过 50MB 的文件。当前限制为：单文件 50MB、单批最多 10 个、单批总计 500MB。单文件超过 50MB 会被服务拒绝。

因此大文件知识清洗仍未闭环。

### P1：清洗写操作权限需要加强

`/internal/v1/knowledge/*` 当前仅使用 `X-Internal-Token`，不要求 `X-Admin-Token`。创建清洗批次、上传知识文件和失败重试都属于管理写操作，正式使用时应纳入管理员鉴权范围。

### P1：临时 Streamlit 页面不能长期公开

当前临时页可由公网访问，且 Nginx 路径未配置登录认证。它可代表服务器发起管理接口调用，因此只适合作为临时测试工具。

测试结束后应停止 UI 并移除 Nginx 路径，或至少增加访问认证；不能作为正式管理后台长期保留。

### P1：容量、恢复和故障注入没有验收

当前服务配置为单 API 进程、Worker 并发 2，尚未进行以下验证：

- 20 并发、10 分钟流式测试。
- Worker 重启恢复。
- Redis、PostgreSQL、Dify 故障注入。
- 清洗完整 E2E 和补偿删除。
- 灰度和正式验收。

背景中的 3000–5000 人使用规模尚未明确是同时在线还是同时发起 AI 流式请求；这会直接影响容量设计和验收指标。因此目前不能承诺活动峰值承载能力。

### P2：项目结构已改善但仍需模块化

项目已从单一入口拆出路由、Worker 和观测模块，但以下文件仍偏大：

- `cleaning.py`：约 644 行。
- `conversations.py`：约 556 行。
- `test_ui.py`：约 444 行。
- `course_import.py`：约 410 行。

建议后续按“路由/API、应用服务、仓储、Dify 适配、策略/校验、异步任务、页面组件”继续拆分。该项不阻塞当前联调，但会影响后续维护效率。

## 5. 小程序后端接口评估

### 5.1 当前可直接接入的用户接口

所有内部用户接口由小程序后端保存 `X-Internal-Token`；用户类接口还需传稳定的 `X-User-Id`。小程序前端不得持有内部 Token、管理员 Token、Dify Key 或 Dataset ID。

| 能力 | 接口 | 结论 |
| --- | --- | --- |
| 三入口配置 | `GET /internal/v1/entry-config` | 可接入 |
| 商业顾问流式聊天 | `POST /internal/v1/business/chat` | 可接入 |
| 停止商业生成 | `POST /internal/v1/business/chat/{task_id}/stop` | 可接入 |
| 历史列表/消息 | `GET /internal/v1/business/conversations`、`GET /internal/v1/business/conversations/{id}/messages` | 可接入 |
| 重命名/删除 | `PATCH`、`DELETE /internal/v1/business/conversations/{id}` | 可接入 |
| 消息反馈 | `POST /internal/v1/business/messages/{message_id}/feedback` | 可接入 |
| 朋友圈/写作 | `POST /internal/v1/tools/moments/run`、`POST /internal/v1/tools/writing/run` | 可接入 |
| 停止工具生成 | `POST /internal/v1/tools/{task_id}/stop` | 可接入 |
| 课程跳转 | 服务返回 `/r/{token}`，由前端打开 | 可接入 |

管理员接口不应由普通小程序前端调用，包括会话审计、课程统计、目录、日志与清洗接口。

### 5.2 接口尚不适合冻结为正式契约的部分

虽然主流程可联调，但正式交付前应补齐：

- 每个接口明确的响应模型，而不是大量通用字典返回。
- SSE 每个事件的 JSON Schema、事件顺序、终态规则和客户端处理规则。
- 完整错误码和重试策略表。
- 幂等键：移动端或网络重试时，当前可能重复创建消息和重复调用模型。
- 历史列表分页和游标。
- 断线重连、重复请求、取消后重试的统一规则。
- 聊天附件接口（如该需求确认存在）。
- 最新学习路线“确认—阶段询问—当前与下一阶段课程”所需事件和返回结构。

建议小程序后端通过自己的适配层调用 AI 管理服务，不让小程序业务代码直接绑定当前所有字段。

## 7. 推荐处理顺序

1. 将 `背景介绍.txt` 与 `用户操作和管理员操作部分场景.md` 固化为最新需求基线，并同步更新 V2 文档和 E2E 用例。
2. 修复摘要/画像任务自动入队问题。
3. 调整路线交互为“路线与原因 → 用户确认 → 阶段询问 → 当前与下一阶段课程”。
4. 增加混合问题结构化拆分与双知识库分别检索。
5. 将历史清理默认改为凌晨 2 点，并建设管理员可配置的保留策略。
6. 明确聊天附件范围；若需要，补齐上传、存储、校验、查看与清理链路。
7. 制定并执行与 Dify PostgreSQL/Redis 共用基础设施但逻辑隔离的数据迁移计划。
8. 将清洗写操作加管理员鉴权，并解决单文件超过 50MB 的处理方案。
9. 补齐正式 API/SSE 契约、幂等、分页和错误码说明。
10. 将本地 `d8f5467` 与上述修复一起生成新镜像发布，完成完整测试、并发、故障注入、回滚演练后再做正式验收。

## 8. 采用的关键假设

- Dify 控制台可作为知识库管理、模型切换和 Prompt 修改的管理入口；不重复建设同类正式后台。
- “上传附件”若指聊天文件，则当前按未实现处理；若仅指知识库文件，则 Dify 原生功能优先。
- 3000–5000 人暂按活动期间用户规模理解，不等同于 3000–5000 路并发 AI 流式请求；正式容量指标需在上线验收前明确。
