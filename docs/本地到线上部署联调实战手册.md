# 本地到线上部署联调实战手册

> 适用项目：`jx-now` AI 管理服务  
> 最近更新：2026-07-23  
> 维护方式：每次发布后补充“发布记录”和新发现的坑，不在本文保存任何真实密钥。

## 1. 目标和当前拓扑

这份手册用于完成一条可重复、可检查、可回滚的发布链路：

```text
本地修改和测试
  → 构建 Python wheel
  → 上传服务器
  → 离线构建镜像
  → 修改服务器配置
  → 数据库迁移
  → 同步重建 API/Worker/Scheduler
  → 健康检查、契约测试、RAG 和全链路测试
  → 浏览器人工验收
  → 保存证据和发布记录
```

当前环境约定：

| 项目 | 位置或名称 |
|---|---|
| 本地仓库 | `D:\work\projectc\jx-now` |
| SSH 别名 | `jx-server` |
| 服务器部署目录 | `/opt/ai-management` |
| Dify Compose 目录 | `/opt/dify/docker` |
| 核心镜像 | `jx-now-ai-management:0.1.0` |
| 测试 UI 镜像 | `jx-now-ai-management-ui:0.1.0` |
| API 私网地址 | `172.30.157.197:8000` |
| UI 服务器监听 | `127.0.0.1:8501` |

`docker-compose.ai.yml` 当前会创建项目独立的 PostgreSQL、Redis 和持久卷，并把 API、Worker、Scheduler 同时连接到 Dify 的 `docker_default` 网络。不要删除这些持久卷，也不要直接修改 Dify 数据库。

## 2. 发布前检查

### 2.1 确认本地改动

在本地 PowerShell 执行：

```powershell
Set-Location D:\work\projectc\jx-now
rtk git status --short
rtk git diff
```

工作区可能包含尚未提交的用户改动。不要用 `git reset --hard`、`git clean -fd` 或覆盖无关文件。

### 2.2 跑离线测试

```powershell
rtk pytest -q tests
```

若 RTK 本身超时或不可用，退回：

```powershell
python -m pytest -q tests
```

本次基线是 29 项测试通过。测试数以后增加时，以仓库当前实际数量为准。

### 2.3 记录线上旧版本

先只读检查，保留回滚信息：

```powershell
ssh jx-server "cd /opt/ai-management && docker compose -f docker-compose.ai.yml ps"
ssh jx-server "docker image inspect jx-now-ai-management:0.1.0 --format '{{.Id}} {{index .RepoDigests 0}}' 2>/dev/null || true"
ssh jx-server "cd /opt/ai-management && docker compose -f docker-compose.ai.yml exec -T api alembic current"
```

将镜像 ID、迁移版本、检查时间写入本次发布记录。若镜像没有 RepoDigest，只记录镜像 ID。

## 3. 本地构建发布物

### 3.1 构建 wheel

项目当前可以直接用 `pip wheel` 构建，不依赖本机安装 `build` 命令：

```powershell
python -m pip wheel . --no-deps --no-cache-dir --wheel-dir dist
Get-FileHash .\dist\jx_now_ai_management-0.1.0-py3-none-any.whl -Algorithm SHA256
```

不要把整个本地虚拟环境或 Windows 依赖目录上传服务器。核心服务只上传项目 wheel；服务器用已有的 Linux `wheelhouse` 离线安装依赖。

### 3.2 版本和镜像标签

当前 Compose 固定使用 `jx-now-ai-management:0.1.0`。为了能识别和回滚实际发布物，每次服务器构建时还应保留一个不可变标签，例如：

```text
jx-now-ai-management:0.1.0-20260723-<git短SHA>
```

在正式建立自动发布前，不必为了改标签大幅修改 Compose；可以先构建不可变标签，再把同一镜像标记为 Compose 使用的固定标签。禁止只依赖反复覆盖的 `0.1.0` 标签判断当前代码版本。

## 4. 上传到服务器

### 4.1 上传到临时目录

在本地 PowerShell 执行：

```powershell
scp .\dist\jx_now_ai_management-0.1.0-py3-none-any.whl jx-server:/tmp/
scp .\scripts\dify_contract_check.py jx-server:/tmp/
scp .\scripts\evaluate_business_e2e.py jx-server:/tmp/
scp .\test_data\rag\business_e2e_cases.jsonl jx-server:/tmp/
```

然后明确移动到各自目录：

```powershell
ssh jx-server "install -m 0644 /tmp/jx_now_ai_management-0.1.0-py3-none-any.whl /opt/ai-management/wheelhouse/ && install -m 0644 /tmp/dify_contract_check.py /opt/ai-management/scripts/ && install -m 0644 /tmp/evaluate_business_e2e.py /opt/ai-management/scripts/ && install -m 0644 /tmp/business_e2e_cases.jsonl /opt/ai-management/test_data/rag/"
```

如果 SSH 用户没有写权限，先上传 `/tmp`，再通过服务器已有的授权方式移动；不要擅自放宽 `/opt/ai-management` 权限。

更新 Compose 等配置文件时先保存带时间戳的副本。在 PowerShell 中生成时间戳，
不要让 PowerShell 解析远端 Bash 的 `$(date ...)`：

```powershell
$deployStamp = Get-Date -Format 'yyyyMMdd-HHmmss'
scp .\docker-compose.ai.yml jx-server:/tmp/docker-compose.ai.yml.new
ssh jx-server "cd /opt/ai-management && cp docker-compose.ai.yml docker-compose.ai.yml.bak-$deployStamp && install -m 0644 /tmp/docker-compose.ai.yml.new docker-compose.ai.yml"
```

### 4.2 为什么要逐类上传

不要使用下面这种含糊命令：

```text
scp 文件1 文件2 jx-server:/opt/ai-management/ai_management/
```

它很容易把测试脚本放进 Python 包目录，或用错误文件覆盖同名目标。wheel、脚本、测试数据、迁移文件和 Compose 文件必须分别进入明确目录。

### 4.3 校验上传结果

```powershell
ssh jx-server "sha256sum /opt/ai-management/wheelhouse/jx_now_ai_management-0.1.0-py3-none-any.whl && ls -l /opt/ai-management/scripts/evaluate_business_e2e.py /opt/ai-management/test_data/rag/business_e2e_cases.jsonl"
```

服务器 SHA256 应与本地一致。

## 5. 安全修改线上配置

服务器真实配置只保存在 `/opt/ai-management/.env`，不提交 Git，不复制到测试报告。

需要检查的是“键是否存在”，不是打印值：

```powershell
ssh jx-server "cd /opt/ai-management && grep -E '^(INTERNAL_API_TOKEN|PUBLIC_BASE_URL|DATABASE_URL|REDIS_URL|DIFY_BASE_URL|DIFY_KNOWLEDGE_BASE_URL|DIFY_.*_API_KEY|DIFY_.*_DATASET_ID)=' .env | sed -E 's/=.*/=<set>/'"
```

重点配置：

- `AI_BIND_ADDRESS`：生产使用私网 IP 或回环地址，不使用 `0.0.0.0`。
- `INTERNAL_API_TOKEN`：只给可信后端和运维测试使用。
- `PUBLIC_BASE_URL`：签名跳转链接对调用方实际可达的地址。
- `DATABASE_URL`、`REDIS_URL`：指向本项目独立容器和 DB。
- `DIFY_BASE_URL`、`DIFY_KNOWLEDGE_BASE_URL`：容器内优先走 Dify 内网地址。
- 四个 Dify App Key：商业顾问、朋友圈、写作、总结画像相互独立。
- 两个 Dataset ID：通用知识库和课程知识库不能填反。

### 5.1 严禁泄密的命令

不要在会被保存、分享或粘贴到聊天中的终端执行：

```text
docker compose config
cat .env
env
docker inspect <container>
```

`docker compose config` 会展开 `env_file`，可能把全部密钥打印出来。可替代为：

```powershell
ssh jx-server "cd /opt/ai-management && docker compose -f docker-compose.ai.yml config --services"
ssh jx-server "cd /opt/ai-management && docker compose -f docker-compose.ai.yml ps"
ssh jx-server "docker inspect ai-management-api-1 --format '{{json .NetworkSettings.Ports}}'"
```

若必须诊断单个环境变量，只输出“已设置/未设置”或脱敏后的末四位。

## 6. 服务器离线构建

### 6.1 构建核心镜像

在服务器执行：

```bash
cd /opt/ai-management
release_tag="jx-now-ai-management:0.1.0-20260723-<git短SHA>"
docker build --pull=false -f Dockerfile.offline -t "$release_tag" .
docker tag "$release_tag" jx-now-ai-management:0.1.0
```

`Dockerfile.offline` 使用 `/opt/ai-management/wheelhouse`，避免服务器访问 PyPI。服务器网络慢或不可控时，优先更新本地 wheelhouse，不要临时改为在线安装。

同一个版本号可能触发 Docker 缓存而继续使用旧 wheel。发生怀疑时：

1. 对比 wheel SHA256。
2. 使用不可变 release tag。
3. 必要时对安装 wheel 的层使用 `--no-cache` 重建。
4. 启动后从容器内检查目标代码特征或包版本。

### 6.2 防止重复构建

远程命令超时不代表服务器构建已经停止。重试前先检查：

```powershell
ssh jx-server "ps -ef | grep '[d]ocker build\\|[d]ocker compose.*build'"
```

只允许一个目标构建运行。不要连续启动多个 `docker compose build api`，否则会争用 CPU、磁盘和 Docker 锁。

### 6.3 UI 的 Linux 依赖

Windows 上直接下载的 wheel 不能用于 Linux 镜像。需要补充 UI 离线依赖时，在本地明确下载 Linux CPython 3.11 wheel：

```powershell
python -m pip download ".[ui]" `
  --dest ui-wheelhouse-linux `
  --platform manylinux2014_x86_64 `
  --python-version 311 `
  --implementation cp `
  --abi cp311 `
  --only-binary=:all:
```

将目录上传到服务器的 `/opt/ai-management/ui-wheelhouse-linux` 后再构建：

```bash
cd /opt/ai-management
docker build --pull=false -f Dockerfile.ui-offline -t jx-now-ai-management-ui:0.1.0 .
```

纯 Python 的 `py3-none-any` wheel 跨平台，但包含本地扩展的 `win_amd64.whl` 一定不能装进 Linux 容器。

## 7. 迁移和启动

### 7.1 先备份

涉及数据库迁移前，至少完成一次 PostgreSQL 逻辑备份，并记录备份文件位置和恢复命令。Dify 工作流有改动时，发布前导出当前 DSL。

不要删除 `ai_postgres_data`、`ai_redis_data`、Dify 数据卷或对象存储来“重新开始”。

### 7.2 执行迁移

先启动依赖和 API，再迁移：

```bash
cd /opt/ai-management
docker compose -f docker-compose.ai.yml up -d postgres redis api
docker compose -f docker-compose.ai.yml exec -T api alembic upgrade head
docker compose -f docker-compose.ai.yml exec -T api alembic current
```

### 7.3 同步重建三个进程

API、Worker、Scheduler 必须使用同一镜像：

```bash
cd /opt/ai-management
docker compose -f docker-compose.ai.yml up -d --no-build --force-recreate api worker scheduler
docker compose -f docker-compose.ai.yml ps
docker compose -f docker-compose.ai.yml logs --tail=100 api worker scheduler
```

不要只更新 API；数据结构、任务代码和调度逻辑不一致会产生难排查的间歇故障。

## 8. 分层测试

测试按从便宜到昂贵的顺序执行，失败后先修当前层，不要直接用浏览器反复碰运气。

### 8.1 容器和健康检查

```powershell
ssh jx-server "cd /opt/ai-management && docker compose -f docker-compose.ai.yml ps"
curl.exe http://172.30.157.197:8000/health/live
curl.exe http://172.30.157.197:8000/health/ready
```

预期容器健康，`live` 和 `ready` 成功。若 `ready` 返回 503，按响应中的数据库、Redis、Dify 配置状态逐项排查。

### 8.2 Dify 契约测试

测试应用读取、流式事件、会话和知识库连接：

```bash
cd /opt/ai-management
docker compose -f docker-compose.ai.yml exec -T api python scripts/dify_contract_check.py
```

只有需要测试知识库写入、Metadata、索引和删除时才运行：

```bash
docker compose -f docker-compose.ai.yml exec -T api python scripts/dify_contract_check.py --write-knowledge
```

后一个命令会创建并删除临时知识库文档，不应在不清楚目标 Dataset 时执行。

### 8.3 业务生命周期和停止

```bash
cd /opt/ai-management
docker compose -f docker-compose.ai.yml exec -T api python scripts/live_business_lifecycle.py
docker compose -f docker-compose.ai.yml exec -T api python scripts/live_stop_check.py
```

检查创建/续聊、重命名、反馈、删除、停止生成、课程卡片、路线和签名跳转。

### 8.4 RAG 直检

```bash
cd /opt/ai-management
mkdir -p var/reports
docker compose -f docker-compose.ai.yml exec -T api \
  ai-rag-eval test_data/rag/golden_questions.jsonl \
  --top-k 5 \
  --output var/reports/rag.json
```

评测文件生成在 API 容器内，随后复制到服务器持久目录：

```bash
cd /opt/ai-management
mkdir -p var/reports
api_container="$(docker compose -f docker-compose.ai.yml ps -q api)"
docker cp "${api_container}:/app/var/reports/rag.json" var/reports/rag.json
```

当前已验证参考值是 Recall@5 97.47%、Hit@5 100%、关键问题 Hit@5 100%。知识库、分块、Embedding 或测试集变化后应重新建立基线，不能永久照搬旧数字。

### 8.5 商业顾问全链路

容器已经从 `.env` 获取 `INTERNAL_API_TOKEN`，无需把密钥写进命令：

```bash
cd /opt/ai-management
docker compose -f docker-compose.ai.yml exec -T api \
  python scripts/evaluate_business_e2e.py \
  test_data/rag/business_e2e_cases.jsonl \
  --base-url http://127.0.0.1:8000 \
  --output var/reports/business-e2e.json
api_container="$(docker compose -f docker-compose.ai.yml ps -q api)"
docker cp "${api_container}:/app/var/reports/business-e2e.json" \
  var/reports/business-e2e.json
```

当前 6 条参考用例为 6/6 通过，首 Token P50/P95 为 4912/5410ms，总耗时 P50/P95 为 8506.5/10303ms。后续重点观察：

- 用例通过率和失败原因；
- Recall@K、Hit@K、MRR；
- 首 Token P50/P95；
- 总耗时 P50/P95；
- 错误课程 ID、停用课程、虚构路线和无依据回答；
- Dify 请求 ID、会话 ID 与本地请求 ID 是否可追踪。

### 8.6 极简交互页面

UI 只绑定服务器回环地址：

```bash
cd /opt/ai-management
docker compose -f docker-compose.ai.yml -f docker-compose.ui.yml \
  --profile test up -d --no-build test-ui
docker ps --filter name=test-ui --format 'table {{.Names}}\t{{.Ports}}\t{{.Status}}'
```

本地建立 SSH 隧道：

```powershell
ssh -N -L 127.0.0.1:8501:127.0.0.1:8501 jx-server
```

浏览器打开 `http://127.0.0.1:8501`。验收：

- 新建会话和连续问答；
- 流式文本是否逐步出现；
- 课程卡片和学习路线；
- 历史会话切换、重命名、删除；
- 点赞/点踩；
- 停止生成；
- 页面刷新后数据仍在。

基础 Compose 和 UI 覆盖文件都应保持 `127.0.0.1:8501:8501`。不要把 UI
改成 `0.0.0.0:8501`。Compose 多文件的 `ports` 可能发生合并而非覆盖，启动后
必须以 `docker ps` 的实际绑定为准；若同时看到 `0.0.0.0:8501`，立即停止 UI
并修正 Compose 后重建。

## 9. 保存证据

建议每次发布在 `var/reports/releases/<日期-版本>/` 保存：

- 本地测试摘要；
- wheel 文件名和 SHA256；
- 新旧镜像 ID及不可变标签；
- Alembic 迁移版本；
- Compose 容器状态；
- 健康检查结果；
- Dify 契约测试摘要；
- `rag.json` 和 `business-e2e.json`；
- 5～10 条人工抽检结论；
- 已知问题和回滚点。

报告不得包含 `.env`、API Key、内部 Token、数据库密码或完整的 `docker inspect` 输出。

同时更新根目录的 `AI管理服务当前状态与后续测试交接.md`，只写当前状态、指标、服务器路径、下一步和非敏感故障结论。

## 10. 回滚

### 10.1 应用镜像

发布前给旧镜像保留不可变标签，例如：

```bash
docker tag jx-now-ai-management:0.1.0 jx-now-ai-management:rollback-<日期时间>
```

需要回滚时，把旧镜像重新标记为 Compose 固定标签，然后同步重建三个进程：

```bash
docker tag jx-now-ai-management:rollback-<日期时间> jx-now-ai-management:0.1.0
cd /opt/ai-management
docker compose -f docker-compose.ai.yml up -d --no-build --force-recreate api worker scheduler
```

回滚前必须确认数据库迁移向后兼容。若不兼容，只能使用已经评审和验证过的 Alembic downgrade 或向前修复，不能直接删表、删卷。

### 10.2 Dify

Dify 应用发布与服务镜像是两个独立版本：

- 发布工作流前导出旧 DSL；
- 记录应用发布时间和绑定的知识库；
- 回滚 DSL 后重新跑契约测试和 6 条全链路用例；
- 不复用已泄露或用途不明的旧 Key。

## 11. 已验证的排坑经验

| 现象 | 常见原因 | 快速处理 |
|---|---|---|
| 服务器构建长时间无输出 | PyPI 慢或远程命令超时 | 使用离线 wheelhouse；先查进程，不重复启动构建 |
| 重建后仍像旧代码 | 固定版本号触发 Docker 缓存 | 校验 wheel SHA256，使用不可变镜像标签，必要时 `--no-cache` |
| Linux UI 构建提示 wheel 不兼容 | 在 Windows 下载了 `win_amd64` wheel | 用 `--platform manylinux2014_x86_64` 重新下载 |
| UI 意外暴露公网端口 | Compose 多文件端口发生合并 | 用 `docker ps` 查实际绑定，只保留 `127.0.0.1:8501` |
| 商业顾问有答案但无课程卡片 | Dify 节点事件或 JSON 解析不匹配 | Dify 1.13.3 检查 `node_finished` 和 `outputs.text` |
| 正常答案覆盖了推荐决策 | 把普通最终回答节点当成决策节点 | 只接受具备决策字段的结构化输出 |
| SSE 测试脚本解析失败 | `course_cards` 是列表，路线是对象 | 按事件类型兼容列表和对象 |
| 签名跳转在容器内超时 | 私网地址回环或网络路径问题 | 在容器内用 localhost 验证状态与 `Location`，外部再测真实入口 |
| 日志里出现大量密钥 | 执行了 `docker compose config` 或打印环境 | 立即停止传播并轮换暴露密钥；以后只查键名和目标字段 |
| PowerShell 报 `Get-Date`，远端命令变形 | 双引号中的 Bash `$()` 被 PowerShell 抢先解释 | 用 PowerShell 先生成时间戳，或正确使用单引号和转义 |
