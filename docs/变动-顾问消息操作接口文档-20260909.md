# 三类 AI 顾问消息操作接口变动说明

> 适用对象：小程序后端开发人员、AI 管理服务维护人员。
>
> 适用范围：本次商业顾问、朋友圈顾问、日常写作新增或发生契约变化的接口。未在本文列出的接口保持原契约，以正式接口标准为准。

## 1. 本次接口清单

### 新增接口（3 个）

| 方法与路径 | 新增能力 | 调用方主要处理 |
| --- | --- | --- |
| `POST /internal/v1/business/messages/{message_id}/regenerate` | 商业顾问重新生成最新回答；覆盖原本地助手消息，不增加消息数量 | 传本地助手 `message_id`；重新累计 SSE 正文；成功后继续使用原 `message_id` |
| `POST /internal/v1/tools/{kind}/messages/{message_id}/feedback` | 朋友圈顾问、日常写作点赞、点踩和取消反馈 | `kind` 传 `moments` 或 `writing`；`message_id` 原样使用工具 SSE 返回的不透明 ID |
| `POST /internal/v1/tools/{kind}/messages/{message_id}/regenerate` | 朋友圈顾问、日常写作在当前 Dify 会话重新生成最新回答 | 传工具 SSE 返回的旧 `message_id`；成功后用响应中的新 `message_id` 替换旧 ID |

### 变更接口（8 个）

这些都是修改前已经存在的接口。本次没有改变其路径；变化集中在响应字段、可用场景、并发校验和停止终态。

| 方法与路径 | 主要变更内容 | 调用方主要处理 |
| --- | --- | --- |
| `GET /internal/v1/entry-config` | 商业顾问新增 `regenerate=true`、`stop=true`；朋友圈/写作的 `feedback` 从 `false` 改为 `true`，并新增 `regenerate=true`、`stop=true` | 可按这些能力字段显示反馈、重新生成和停止按钮 |
| `GET /internal/v1/business/conversations/{conversation_id}/messages` | 每条 `items[]` 新增 `can_regenerate: boolean`；原有多消息数组、排序和分页没有变化 | 可用该字段预先控制重新生成按钮；它不是必传参数，真正调用时仍处理 `404/409` |
| `POST /internal/v1/business/chat` | 请求体和成功 SSE 不变；失败 `error` 增加本地 `conversation_id`、`message_id` 和 `status=failed` | 失败时可定位对应本地消息，并按 `error.status=failed` 结束本轮生成 |
| `POST /internal/v1/tools/moments/run` | 请求体不变；SSE 新增早期 `task_started.task_id`、结束时的 `conversation_id/message_id/status`，失败增加 `status=failed` | 保存 `task_id` 用于停止，保存非空 `message_id` 用于反馈/重新生成；失败时清除本轮正文 |
| `POST /internal/v1/tools/writing/run` | 与朋友圈普通生成相同：请求体不变，SSE 增加任务 ID、消息 ID 和明确终态 | 保存 `task_id/message_id`；按 `completed/stopped/failed` 处理正文 |
| `POST /internal/v1/tools/{task_id}/stop` | 删除找不到映射时跨 App、跨 transport 轮询的兜底；只停止当前用户仍活动的精确 Chat 任务；原 SSE 可靠结束为 `stopped` | 只能使用同一条 SSE 返回的活动 `task_id`；未知、跨用户、重复停止或已结束统一处理 `404 TASK_NOT_FOUND` |
| `POST /internal/v1/business/messages/{message_id}/feedback` | 请求体不变；增加会话锁和消息状态校验，避免反馈落到重新生成前的旧 Dify 消息 | 重新生成进行中或消息状态不可反馈时处理 `409 CONVERSATION_BUSY` |
| `POST /internal/v1/business/chat/{task_id}/stop` | 请求不变；从只处理普通生成扩展为同时处理普通生成和重新生成；只有 Dify 确认后才形成停止终态 | 使用当前商业 SSE 的 `task_id`；重复停止或任务已结束处理 `404 TASK_NOT_FOUND` |

本次没有删除接口，也没有修改 `/internal/v1` 版本、鉴权头或上述既有生成接口的请求体。

### 1.1 对比口径

下文中的“修改前”指本次顾问消息操作功能开始前的代码基线 `c3385b9`；“修改后”指本文描述的当前实现。对比的是小程序后端可见的 HTTP/SSE 契约及会影响调用结果的服务端行为，不把纯内部重构列为接口变化。

### 1.2 新增接口：从不存在变为可调用

| 接口 | 修改前 | 修改后 |
| --- | --- | --- |
| `POST /internal/v1/business/messages/{message_id}/regenerate` | 无此路由，商业顾问回答不能通过 AI 管理服务重新生成 | 新增 SSE 接口；使用本地助手 `message_id`，只允许最新且未摘要的回答；在同一条本地消息上替换答案，不增加消息数量 |
| `POST /internal/v1/tools/{kind}/messages/{message_id}/feedback` | 无此路由，朋友圈顾问和日常写作不能通过 AI 管理服务提交反馈 | 新增 JSON 接口；支持 `like`、`dislike`、`null`，校验消息属于当前用户、当前 `kind` 和当前有效 Dify 会话后提交给 Dify |
| `POST /internal/v1/tools/{kind}/messages/{message_id}/regenerate` | 无此路由，朋友圈顾问和日常写作不能重新生成 | 新增 SSE 接口；回读当前 Dify 会话最新消息的原 `query/inputs`，按当前配置重新校验和注入控制字段，在同一 Dify 会话中生成新消息 |

### 1.3 入口能力字段：修改前与修改后

`GET /internal/v1/entry-config` 的路由、请求头和响应外层结构没有改变，变化的是三个入口的能力字段：

| 入口 | 修改前 | 修改后 |
| --- | --- | --- |
| `business_advisor` | `history=true`、`feedback=true`；没有 `regenerate`、`stop` 字段 | `history=true`、`feedback=true`；新增 `regenerate=true`、`stop=true` |
| `moments_advisor` | `history=false`、`feedback=false`；没有 `regenerate`、`stop` 字段 | `history=false`；`feedback` 从 `false` 变为 `true`；新增 `regenerate=true`、`stop=true` |
| `writing_advisor` | `history=false`、`feedback=false`；没有 `regenerate`、`stop` 字段 | `history=false`；`feedback` 从 `false` 变为 `true`；新增 `regenerate=true`、`stop=true` |

`history` 和 `course_recommendation=false` 没有变化。朋友圈/写作的 `history=false` 仍表示本服务不提供正文历史列表，不表示 Dify 当前会话没有短期 Memory。

### 1.4 商业消息列表：只新增一项级字段

接口：

```http
GET /internal/v1/business/conversations/{conversation_id}/messages
```

修改前，响应本来就是多条消息的分页结构：

```json
{
  "items": [
    {
      "message_id": "business-m2",
      "role": "assistant",
      "content": "当前回答",
      "status": "completed",
      "recommendation": {},
      "retriever_resources": [],
      "created_at": "2026-09-09T09:00:00Z"
    }
  ],
  "next_cursor": null
}
```

修改后，只在每一条 `items[]` 中增加：

```diff
  "created_at": "2026-09-09T09:00:00Z",
+ "can_regenerate": true
```

即：

| 项目 | 修改前 | 修改后 |
| --- | --- | --- |
| 多消息返回 | 已使用 `items` 数组 | 不变 |
| 排序 | 已按 `created_at`、`message_id` 从早到晚排列 | 不变 |
| 分页 | 已支持 `cursor + limit`，并返回 `next_cursor` | 不变 |
| 重新生成提示 | 无 `can_regenerate`，客户端无法从列表预先判断按钮是否可用 | 每条消息都有 `can_regenerate: boolean`；只有最新、未摘要且状态允许的助手回答可能为 `true` |

`can_regenerate` 不是调用重新生成接口的必传参数，也不是服务端授权凭证。客户端可以不用它；若用于按钮展示，仍必须处理真正调用时可能发生的 `404/409`。

### 1.5 朋友圈/写作普通生成 SSE：请求不变，响应增加可操作 ID 和明确终态

涉及接口：

```http
POST /internal/v1/tools/moments/run
POST /internal/v1/tools/writing/run
```

两个接口的路径、请求头和请求体没有变化，变化的是 Chat SSE：

| 阶段 | 修改前 | 修改后 |
| --- | --- | --- |
| 任务开始 | 服务端内部取得并保存 `task_id`，但不向客户端发送 Chat `task_started` | 首次取得任务 ID 时发送 `event: status`，其中 `code=task_started`、`task_id=<ID>`；客户端可在生成中调用停止接口 |
| 正文增量 | `event: answer_delta` | 不变 |
| 成功结束 | `message_end` 主要只有 `request_id`、`task_id` | `message_end` 增加本地 `conversation_id`、不透明 Dify `message_id` 和 `status=completed`，并继续返回 `request_id`、`task_id` |
| 用户停止 | 没有稳定、明确的工具 Chat 停止终态 | 原 SSE 返回 `message_end.status=stopped`；已收到的正文片段保留 |
| 生成失败 | `error` 主要只有 `code`、`message`、`request_id`、`retryable` | `error` 增加 `conversation_id`、可用时的 `message_id/task_id` 和 `status=failed`；客户端必须丢弃本轮全部正文片段 |
| 后续消息操作 | SSE 不公开 `message_id`，无法可靠反馈或重新生成 | 成功或停止后公开不透明 `message_id`，供反馈和重新生成接口原样回传 |

修改前的成功终态：

```text
event: message_end
data: {"request_id":"req-1","task_id":"task-1"}
```

修改后的成功终态：

```text
event: message_end
data: {"request_id":"req-1","conversation_id":"local-tool-c1","message_id":"opaque-m1","task_id":"task-1","status":"completed"}
```

### 1.6 既有停止接口：路径不变，停止目标和终态变得严格

#### 工具停止

接口仍为：

```http
POST /internal/v1/tools/{task_id}/stop
```

| 修改前 | 修改后 |
| --- | --- |
| 有 Redis 映射时按映射停止；映射不存在时会依次尝试朋友圈/写作两个 App，并在每个 App 内尝试 Workflow stop 和 Chat stop | 只接受 Redis 中仍存在的精确任务映射；映射必须属于当前用户、入口必须是朋友圈/写作、`transport` 必须是 Chat |
| 跨用户可能返回 `VALIDATION_ERROR`；最终找不到可能返回 `DIFY_UNAVAILABLE` | 未知、跨用户、重复停止或已结束统一返回 `404 TASK_NOT_FOUND`，避免泄露任务归属 |
| 停止请求与原 SSE 的结束存在竞态，未稳定区分停止与普通完成 | 增加停止中的状态和终态互斥；Dify 确认停止后，原 SSE 可靠返回 `message_end.status=stopped` |

因此，修改后不能拿任意 `task_id` 让服务端跨 App 猜测；必须使用同一条 SSE 的 `task_started.task_id`，并在该任务仍活动时立即停止。

#### 商业顾问停止

接口仍为：

```http
POST /internal/v1/business/chat/{task_id}/stop
```

| 修改前 | 修改后 |
| --- | --- |
| 只服务于商业顾问普通生成 | 同时服务于普通生成和本次新增的商业顾问重新生成 |
| 发起 Dify stop 前就写入 stopped 标记，重复停止和流终态存在竞态 | 先记录 stopping；只有 Dify 确认成功后才记录 stopped，并用终态互斥避免重复结束 |
| Dify stop 失败时存在被过早视为已停止的风险 | Dify stop 失败不会被错误标记为 stopped；重复停止或已结束返回 `404 TASK_NOT_FOUND` |

该接口的请求头、无请求体约定以及成功响应形态没有变化。

### 1.7 既有商业反馈：请求不变，增加并发和状态校验

接口仍为：

```http
POST /internal/v1/business/messages/{message_id}/feedback
```

| 修改前 | 修改后 |
| --- | --- |
| 查到本地消息和 `dify_message_id` 后直接向 Dify 提交反馈 | 在与商业生成/重新生成相同的会话锁内重新读取目标消息 |
| 没有针对“反馈与重新生成同时发生”的专门保护 | 只允许状态为 `completed` 或 `stopped` 的助手消息反馈；重新生成占用会话或消息状态不可反馈时返回 `409 CONVERSATION_BUSY` |
| 可能在重新生成切换 Dify 消息 ID 的竞态窗口中使用旧 ID | 锁内读取并提交，避免把反馈发给已经被替换的旧 Dify 消息 |

请求路径、请求头、`rating/content` 请求体和成功响应均未改变。

### 1.8 商业普通生成 SSE：只增强失败事件

接口仍为：

```http
POST /internal/v1/business/chat
```

该接口修改前已经会发送 `task_started`，成功 `message_end` 也已经包含本地 `conversation_id/message_id`、Dify 消息 ID、`task_id` 和 `status`；这些不能算作本次新增。

本次变化仅是共享商业生成流的失败事件补充定位字段。修改前：

```text
event: error
data: {"code":"DIFY_UNAVAILABLE","message":"Dify服务暂不可用","request_id":"req-1","retryable":true}
```

修改后：

```text
event: error
data: {"code":"DIFY_UNAVAILABLE","message":"Dify服务暂不可用","request_id":"req-1","retryable":true,"conversation_id":"business-c1","message_id":"business-m2","status":"failed"}
```

这样普通生成和商业重新生成都能用本地会话/消息 ID 定位失败对象，并以 `error.status=failed` 作为失败终态。请求体和成功 SSE 契约没有变化。

### 1.9 明确未变化的接口基础契约

- API 版本仍为 `/internal/v1`；
- 内部鉴权头仍为 `X-Internal-Token`，用户接口仍使用 `X-User-Id`；
- 商业普通生成 `POST /internal/v1/business/chat` 的请求体没有变化；
- 朋友圈/写作普通生成 `/run` 的请求体没有变化；
- 商业消息列表的 `items + next_cursor` 外层结构、排序和分页没有变化；
- 商业反馈的路径和请求体没有变化；
- 商业停止、工具停止的路径和请求体没有变化；
- 工具创建会话、查询当前会话和 reset 的接口路径没有变化；
- 没有新增数据库迁移；朋友圈/写作正文仍不在本地持久化；
- 商业顾问 Dify Memory 仍关闭；朋友圈/写作继续使用同一 Dify 会话的短期 Memory。

## 2. 通用请求头

本文所有接口都需要内部服务令牌：

```http
X-Internal-Token: <内部服务令牌>
```

除 `GET /internal/v1/entry-config` 外，本文其余用户消息和任务接口还需要：

```http
X-User-Id: <小程序后端稳定用户 ID>
```

JSON 请求另外携带：

```http
Content-Type: application/json
```

SSE 请求另外携带：

```http
Accept: text/event-stream
```

调用方不得直接调用 Dify，也不得把 Dify `conversation_id` 暴露给小程序前端。

## 3. 本次涉及的 ID

| 字段 | 商业顾问 | 朋友圈顾问、日常写作 |
| --- | --- | --- |
| `conversation_id` | AI 管理服务本地商业会话 ID | AI 管理服务本地工具会话 ID |
| `message_id` | 本地 `BusinessMessage.id` | 不透明的 Dify 消息 ID，只保存和原样回传 |
| `task_id` | 当前 Dify 生成任务 ID，用于停止 | 当前 Dify 生成任务 ID，用于停止 |

工具 `message_id` 不得解析、拼接或自行构造。工具 reset、跨日过期或会话失效后，应同时清除页面保存的旧 `message_id`。

## 5. 商业顾问重新生成

### 请求

```http
POST /internal/v1/business/messages/{message_id}/regenerate
X-Internal-Token: <内部服务令牌>
X-User-Id: <小程序后端稳定用户 ID>
Accept: text/event-stream
```

路径参数：

| 参数 | 类型 | 必填 | 说明 | 示例 |
| --- | --- | --- | --- | --- |
| `message_id` | string | 是 | 商业顾问消息列表或原 SSE 返回的本地助手消息 ID，不是 `dify_message_id` | `business-m2` |

查询参数：无。

请求体：无。不要发送原问题、旧答案、`conversation_id` 或 Dify ID；服务端会根据本地 `message_id` 找回配对的原用户问题。

完整请求案例：

```http
POST /internal/v1/business/messages/business-m2/regenerate HTTP/1.1
Host: <AI管理服务地址>
X-Internal-Token: <内部服务令牌>
X-User-Id: <小程序后端稳定用户 ID>
Accept: text/event-stream
```

### 可重新生成条件

目标消息必须同时满足：

- 属于当前 `X-User-Id` 的当前有效商业会话；
- 是助手消息；
- 是当前会话最新一条回答；
- 对应的用户问题和助手回答尚未进入摘要游标；
- 当前会话没有其它生成或重新生成操作占用。

接口受理后，旧回答立即作废并从本地消息内容中清除，旧反馈同时清空。重新生成不会新增用户消息或助手消息。

### SSE 示例

开始生成：

```text
event: request_started
data: {"request_id":"req-1","conversation_id":"business-c1","message_id":"business-m2"}

event: status
data: {"code":"task_started","message":"已开始生成","task_id":"task-1"}
```

增量正文：

```text
event: answer_delta
data: {"delta":"新的回答片段"}
```

成功或停止：

```text
event: message_end
data: {"request_id":"req-1","conversation_id":"business-c1","message_id":"business-m2","dify_message_id":"dify-m-new","task_id":"task-1","status":"completed","first_token_ms":320,"total_ms":1820,"token_usage":{}}
```

其中 `status` 为：

- `completed`：保存完整新回答；
- `stopped`：保留本轮已经收到的新回答片段。

本地 `message_id` 始终保持为原助手消息 ID；`dify_message_id` 会替换为本次新生成的 Dify 消息 ID。

流中失败：

```text
event: error
data: {"code":"DIFY_UNAVAILABLE","message":"Dify服务暂不可用","request_id":"req-1","retryable":true,"conversation_id":"business-c1","message_id":"business-m2","status":"failed"}
```

`failed` 时旧回答和本轮已流出的新片段都不保留。客户端必须清空本轮累计的 `answer_delta`，不能恢复旧回答。

### 停止重新生成

收到 `status.code=task_started` 后，使用现有接口停止：

```http
POST /internal/v1/business/chat/{task_id}/stop
```

请求头：

```http
X-Internal-Token: <内部服务令牌>
X-User-Id: <小程序后端稳定用户 ID>
```

路径参数：

## 11. SSE 终态处理规则

| 终态 | 事件 | 客户端正文处理 | 客户端 ID 处理 |
| --- | --- | --- | --- |
| 成功 | `message_end.status=completed` | 保留完整累计正文 | 保存非空 `message_id` |
| 用户停止 | `message_end.status=stopped` | 保留已收到的正文片段 | 仅在非空时保存 `message_id` |
| 失败 | `error.status=failed` | 丢弃本轮全部 `answer_delta` | 不把本轮 ID 当作可操作成功消息 |

客户端必须遵守：

- 一个 SSE 流只处理一个终态；
- `message_end.status` 只可能是 `completed` 或 `stopped`；
- 失败不能伪装成 `message_end`，只能通过 `event: error` 表示；
- 必须按 SSE 事件边界解析，不能把单次网络分片当作完整 JSON；
- 收到 `task_started` 后才启用停止按钮；
- 收到非空 `message_id` 后才启用反馈和重新生成按钮。

## 12. 预检、流中错误和错误码

重新生成接口的预检发生在 `StreamingResponse` 建立前：

- 预检失败：返回普通 HTTP JSON 4xx/5xx，不建立 SSE；
- 预检成功：HTTP 200 并建立 SSE；后续 Dify 错误通过 `event: error` 返回。

统一错误结构示例：

```json
{
  "code": "MESSAGE_NOT_REGENERATABLE",
  "message": "该消息不可重新生成",
  "request_id": "请求追踪ID",
  "retryable": false
}
```

主要错误码：

| HTTP | `code` | 含义与客户端处理 |
| ---: | --- | --- |
| 401 | 鉴权错误 | 缺少或错误的 `X-Internal-Token`，检查服务间鉴权 |
| 404 | `MESSAGE_NOT_FOUND` | 用户、kind、有效会话或消息不匹配；reset/跨日后清除旧消息 ID |
| 404 | `TASK_NOT_FOUND` | 任务不存在、不属于当前用户、已结束或已停止 |
| 409 | `MESSAGE_NOT_REGENERATABLE` | 目标不是最新可重新生成消息，或商业消息已进入摘要 |
| 409 | `CONVERSATION_BUSY` | 商业会话正在生成或重新生成，稍后重试 |
| 409 | `CONFLICT` | 工具会话正在生成、重新生成或 reset，稍后重试 |
| 422 | 请求字段校验错误 | `rating`、`content` 或请求结构不合法 |
| 502 | `DIFY_UNAVAILABLE` | Dify 超时或不可达，可按 `retryable` 决定是否重试 |
| 502 | `DIFY_RESPONSE_INVALID` | Dify 消息、输入、时间或会话 ID 等响应不符合契约 |

为避免泄露消息是否属于其他用户或工具，跨用户、跨 `kind` 和未知工具消息统一表现为 `404 MESSAGE_NOT_FOUND`。

## 13. 商业顾问与工具重新生成的差异

| 维度 | 商业顾问 | 朋友圈顾问、日常写作 |
| --- | --- | --- |
| `message_id` | 本地 `BusinessMessage.id` | 不透明 Dify 消息 ID |
| Dify Memory | 关闭 | 开启，窗口为 6 |
| 上下文来源 | AI 管理服务显式组装 | 同一 Dify 会话的短期 Memory |
| 重新生成结果 | 覆盖同一本地助手消息 | 在同一 Dify 会话新增一轮 |
| 新 `message_id` | 本地 ID 不变 | 返回新的不透明 ID |
| 旧答案影响 | 不再进入商业上下文、摘要或画像 | 仍可能保留在 Dify Memory 中 |
| 本地正文 | 保存商业顾问消息正文 | 不保存工具消息正文 |
| 本地反馈 | 保存商业顾问反馈 | 不保存工具反馈 |

因此，小程序后端不能用同一套 ID 替换逻辑处理三类入口：商业顾问继续关联原本地消息 ID；朋友圈/写作必须在重新生成成功后替换为新的工具消息 ID。

## 14. 小程序后端最小改造清单

1. 根据 `entry-config` 的 `feedback`、`regenerate`、`stop` 字段显示操作按钮。
2. SSE 收到 `task_started` 时保存 `task_id` 并启用停止按钮。
3. SSE 成功或停止后保存非空 `message_id`；工具消息 ID 只原样回传。
4. 点击重新生成后立即清除页面旧答案并重新累计 `answer_delta`。
5. 商业顾问成功后继续使用原本地 `message_id`；工具成功后替换为新 `message_id`。
6. `failed` 清除本轮全部片段，`stopped` 保留本轮片段。
7. reset、跨日过期或当前工具会话失效后，清除旧工具 `message_id` 和 `task_id`。

## 15. AI 管理服务边界

- 本次接口没有数据库迁移。
- 商业顾问 Dify Memory 关闭，正文和反馈继续由 AI 管理服务本地持久化。
- 朋友圈顾问、日常写作 Dify Memory 开启，窗口为 6；工具正文和反馈不在本地持久化。
- 工具重新生成不会物理删除 Dify Memory 中的旧问答，不应向调用方承诺旧答案已从 Dify 删除。
- 工具 reset 和跨日过期继续使用既有的精确 Dify 会话删除队列，不直接修改 Dify 业务数据库。
- 工具操作审计只记录请求 ID、哈希用户、`kind`、消息/任务标识和状态，不记录 `query`、`inputs`、生成正文或真实用户 ID。
