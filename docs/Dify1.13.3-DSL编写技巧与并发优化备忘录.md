# Dify 1.13.3 DSL 编写技巧与并发优化备忘录

> 用途：沉淀后续编写和调整 Dify DSL 时可直接复用的规则、模式、性能优化点与版本边界。本文优先记录对 `jx-now` 当前场景有价值的内容，不记录密钥、真实业务数据或临时测试内容。
>
> 证据分级：
>
> - **官方确认**：基于 Dify 官方文档 2026-07-28 可见内容。
> - **案例借鉴**：基于仓库内 3 份外部案例，说明“可借鉴模式”，不等于必须照搬。
> - **项目实测**：基于本仓库和 jx 测试环境实际联调结果。

## 1. 适用范围与版本基线

- 目标版本：Dify `1.13.3`。
- 当前项目主要模式：
  - `business_advisor`：`advanced-chat`，有状态、多知识库、推荐决策、SSE。
  - `moments_advisor`、`writing_advisor`：偏无状态、单轮生成型 Workflow。
  - `summary_profile`：结构化结果输出型 Workflow。
- 默认假设：
  - 可以使用 `Code`、`Knowledge Retrieval`、`If-Else`、`Question Classifier`、`Iteration`、`Answer`、`LLM`。
  - 控制台可创建/导入/发布 DSL，可查看节点运行日志。
  - 目标部署仍是 Dify 官方 Docker 自托管模式。

## 2. Dify 1.13.3 已确认能力边界

### 2.1 官方确认可用

- `Code` 节点可执行 Python/JavaScript，自定义输入输出变量，适合做格式整理、字段提取、规则归一化、检索证据压缩。
- `Knowledge Retrieval` 节点支持：
  - 单库或多库检索；
  - 节点级 `top_k`、`score_threshold`、rerank；
  - metadata filtering；
  - 文本查询；
  - 多模态知识库场景下的图片查询。
- `If-Else` 负责条件分流，适合做命中/未命中、风险/非风险、图片/文本、人工/业务问题等路径切换。
- `LLM` 节点支持 Structured Outputs；若模型原生支持 JSON，优先用结构化输出而不是手搓 fenced JSON。
- `Parameter Extractor` 可把自然语言抽成结构化字段，适合代替“LLM 输出 JSON + Code 正则解析”的脆弱链路。
- `Iteration` 支持顺序和并发模式；官方文档说明并发模式最多同时处理 10 个元素。
- `Answer` 节点支持多次输出和流式输出；变量顺序会影响流式展示时机。
- `Variable Aggregator` 官方定位是“把互斥分支汇合成统一输出变量”，适用于 Question Classifier / If-Else 这类“一次只执行一条分支”的场景。
- Chatflow API 支持 `streaming` 和 `blocking`；`advanced-chat` 可带文件，文件需先 upload 再引用。

### 2.2 版本风险边界

- **项目实测**：互斥分支下，未执行节点不会提供空变量；下游节点直接引用未执行分支变量会失败。
- **官方文档 + 项目实测结论**：如果要汇合互斥分支，要么：
  - 每个分支自己走完；
  - 要么用 `Variable Aggregator` 先做变量收敛，再进入统一下游。
- **附加版本风险**：查到 Dify 官方 GitHub 有一个 `1.13.3` 的 `Variable Aggregator` 相关问题单，描述的是 group 开关 UI 故障，而不是聚合节点整体不可用。因此：
  - 可以把 `Variable Aggregator` 作为候选方案；
  - 但对当前核心业务链，优先用“显式分支闭环”；
  - 如需使用 Aggregator，先避免依赖复杂 group 配置，先做最小验证。

## 3. 下次编写 DSL 的默认规则

### 3.1 先做输入规范化，再做业务判断

**默认采用。**

适用场景：

- 需要统一 query、来源、风格、用户状态、附加参数；
- 需要把复杂 Start 输入整理成后续稳定字段。

推荐做法：

- 先接一个 `Code` 或 `Parameter Extractor` 节点；
- 输出固定命名字段，如：
  - `normalized_query`
  - `question_type`
  - `style_label`
  - `risk_level`
  - `route_hint`

好处：

- 后续节点 prompt 更短；
- 条件判断更清晰；
- 便于排查问题；
- 减少下游重复写同类规则。

### 3.2 互斥分支不要直接共用“硬引用所有变量”的下游节点

**强制采用。**

反例：当前 `business_advisor.yml` 的已知故障。

错误模式：

```text
Question Classifier
  ├─ general -> general_knowledge
  ├─ course  -> course_knowledge
  └─ mixed   -> general_knowledge_mixed -> course_knowledge

然后统一进入 recommendation_decision / final_answer，
但这两个节点同时引用 general_knowledge、general_knowledge_mixed、course_knowledge
```

问题：

- 一次运行只会执行其中一条分支；
- 未执行节点不会返回空变量；
- 下游直接引用时会报“variable not found”。

默认正确写法二选一：

1. **分支局部闭环**  
   每条分支有自己的检索、决策、回答节点。

2. **先收敛再统一处理**  
   只有在验证过 Aggregator 可稳定使用时，才把各分支同类型变量先收敛，再接统一节点。

当前项目默认优先选 `1`。

### 3.3 优先结构化输出，不优先 fenced JSON 正则解析

**推荐采用。**

优先级：

1. `LLM Structured Outputs`
2. `Parameter Extractor`
3. `Code` 解析明确格式
4. `fenced JSON + regex` 兜底

原因：

- fenced JSON 很容易受模型多输出一句解释、少写一个反引号、字段漂移影响；
- 结构化输出更适合做条件判断、工具调用、候选 ID 返回、状态字段传递。

例外：

- 如果目标模型或插件在目标环境中 Structured Outputs 不稳定，可退回 `Code` + 容错解析；
- 但要明确这是兼容兜底，不是首选。

### 3.4 先压缩检索结果，再交给最终生成节点

**推荐采用。**

适用场景：

- RAG 结果 chunk 多；
- 生成节点只需要少量核心证据；
- 需要降低 token 和无关噪声。

推荐做法：

- 检索后接一个 `Code` 节点；
- 只保留：
  - 标题
  - 关键信号
  - 规则/结论
  - 候选 ID
  - 禁忌/限制

不要原样把整个 `result` 数组直接丢给最终回答节点，除非数据量极小且字段稳定。

### 3.5 命中与未命中必须分流

**推荐采用。**

做法：

- `Knowledge Retrieval` 后立刻接 `If-Else`；
- 判断 `result` 是否为空；
- 命中走“知识增强回答”；
- 未命中走“保守兜底回答”或“澄清问题”。

不要把“命中/未命中”混在同一个 prompt 里让模型自己猜。

### 3.6 风险复检只在必要时触发

**推荐采用。**

适用场景：

- 可能涉及安全、越界、误导、成人、承诺、激进表达；
- 但不是每轮都高风险。

做法：

- 先生成结果；
- 通过规则字段或意图识别结果决定是否进入第二个 LLM 审核节点；
- 低风险直接输出；
- 高风险再复检。

收益：

- 降低延迟；
- 降低 token；
- 不把所有请求都强制走双 LLM。

### 3.7 长耗时链路可以插入中间 Answer，但默认只用于长任务

**可选采用。**

适用场景：

- SQL、批处理、长循环、文件处理、复杂外部调用。

不适用场景：

- 商业顾问这种希望连续自然对话的主链路。

原因：

- 中间 Answer 会提升可感知反馈；
- 但会打碎聊天体验，不适合日常问答主路径。

## 4. 针对当前项目的 DSL 模式建议

### 4.1 商业顾问 `business_advisor`

默认模式：

```text
Start
-> 输入规范化
-> 问题拆分/结构化
-> 分类器
  ├─ 通用问题   -> 通用检索 -> 通用决策 -> 通用回答
  ├─ 课程问题   -> 课程检索 -> 课程决策 -> 课程回答
  └─ 混合问题   -> 混合通用检索 -> 混合课程检索 -> 混合决策 -> 混合回答
```

规则：

- 每条分支只引用本分支必定存在的变量；
- 推荐决策输出同一 JSON 契约，方便服务端统一解析；
- 课程/路线 ID 只输出候选，不在 Dify 里直接拼正式卡片；
- 最终课程卡片、正式链接、签名跳转仍由服务端生成；
- 需要引用来源时，优先让检索节点提供 `retriever_resources`。

### 4.2 朋友圈顾问 / 日常写作

默认模式：

```text
Start -> 输入规范化 -> 单轮意图整理 -> 生成 -> 可选安全复检 -> Answer
```

规则：

- 不引入不必要的分类器；
- 不引入多知识库，除非确实要做风格知识增强；
- 尽量保持低延迟。

### 4.3 摘要画像 / 结构化 Workflow

默认模式：

```text
Start -> 结构化提取 -> Code归一化/补全 -> 输出 JSON
```

规则：

- 优先 Structured Outputs 或 Parameter Extractor；
- 输出字段固定、可验证；
- 不要让“自然语言描述”混入最终机器可读结果；
- `target_message_id`、游标、状态位这类关键字段，优先由流程变量强制回填，不依赖模型原样复述；
- 当前项目的 `summary_profile.yml` 已采用 `LLM -> Code -> End`，用于兼容 fenced JSON、前后解释文本和缺省数组字段。

### 4.4 本仓库 4 个 DSL 的当前处理结论

- `business_advisor.yml`
  - **项目实测已发现硬错误**：互斥分支汇合后直接引用未执行分支变量。
  - **当前处理**：改为分支局部闭环，并为混合问题拆出独立课程检索节点。
- `summary_profile.yml`
  - **未发现同类分支错误，但有稳定性缺口**：原先直接透传 `llm.text` 给 Worker。
  - **当前处理**：增加 `summary_normalize` Code 节点，统一输出稳定 JSON。
- `moments_advisor.yml`
  - **本次审计结论**：单一路径 `start -> llm -> end`，无分类器、无检索、无共享分支变量问题。
  - **当前处理**：不做结构性修改，避免无证据改动。
- `writing_advisor.yml`
  - **本次审计结论**：单一路径 `start -> llm -> end`，无分类器、无检索、无共享分支变量问题。
  - **当前处理**：不做结构性修改，避免无证据改动。

### 4.5 商业顾问现用导出件的增量优化结论（2026-07-31）

当前实际使用的导出件 `dify/商业顾问（当前使用版本）.yml` 已经优于仓库旧基线：

- 固定问候/人工等路径为 0 LLM；
- 正常路径为 1 次检索规划 + 1 次分支回答；
- JSON 解析失败才显式增加 1 次格式修复；
- 检索结果已经过 Code 节点压缩。

因此不应为了“减少节点数量”删除证据压缩和格式门禁，也不应整份替换为改名环境变量、直接向 Prompt 注入原始检索数组或开启隐藏 LLM 重试的候选。

本轮增量规则：

- 保持全部 Start 输入、`WECHAT_*` 环境变量、知识库 ID、rerank 模型和后端 `decision_json` 契约；
- 固定路径 0 LLM、正常路径最多 2 LLM，格式错误路径最多 3 LLM；
- 为所有 LLM 设置显式 `max_tokens`，隐藏节点重试保持关闭；
- 证据压缩必须先裁剪单条结果，再执行总预算；否则第一条超长 chunk 会导致整段证据为空；
- 会话状态仍由 AI 管理服务注入；依据 ADR-004，不启用 Dify Conversation Variables；
- 3000～5000 活跃用户不是同时并发数。DSL 只能降低单请求成本，容量仍需用隔离应用做真实压力验证。

对应产物和验证边界见[商业顾问 DSL 优化与隔离验收记录-2026-07-31](商业顾问DSL优化与隔离验收记录-2026-07-31.md)。

### 4.6 商业顾问回答排版与结构化规则

当前项目不应把“风格”和“排版”混为一谈：

- `business_output_style` 继续由 AI 管理服务注入，用于控制语气、措辞和专业度；
- DSL Prompt 只规定跨端可读的最低排版和信息顺序；
- 事实、证据、课程/路线 ID、合规和安全规则始终高于排版要求；
- 不增加“专门润色”LLM，也不提高 `max_tokens`，避免为美观牺牲并发和响应速度。

当前适用的自适应结构：

| 场景 | 默认结构 | 约束 |
|---|---|---|
| 简单答复、澄清、转人工 | 1～3 个短段落 | 不强行加标签；澄清最多问一个关键问题 |
| 复杂通用商业问题 | `【结论】` → `【关键判断】` → `【建议行动】` | 仅在必要时增加 `【注意事项】` |
| 复杂课程/路线问题 | `【建议】` → `【匹配依据】` | 仅在证据充分时增加 `【开始方式】` |
| 复杂混合问题 | `【结论】` → `【业务建议】` → `【学习建议】` | 先业务判断，再给有证据的学习建议 |

跨端排版使用中文括号标签、空行、`- ` 列表和 `1. ` 编号。不要依赖 HTML、
Markdown 表格、代码围栏、`#` 标题或 emoji；这些形式在 Dify、纯文本 SSE
消费者和小程序之间不一定一致，也会增加输出 token。

复杂回答通常控制在 400～800 个中文字符，每段最多 3 句，并列判断 2～4 项，
有明确顺序的行动 3～5 步。长度是上限导向，不是凑字数目标；证据不足时宁可更短。

当 LLM 必须输出严格 JSON 时，`final_answer` 中的换行必须使用 `\n` 转义；
Code 节点解析后才形成真实换行。主回答与格式修复 Prompt 必须共享相同契约，
否则修复分支可能恢复 JSON 格式，却丢失回答结构。

外部案例的采用边界：

- 本仓库跨境电商案例只有“清晰、简洁、结构化”的原则，没有足够具体的商业顾问版式；
- 情感回复案例刻意输出单句，适合复制文案，不适合复杂商业分析；
- 学生成绩案例的阶段标签思路可以借鉴，但 SQL、图表 JSON 和重型阶段链路不适用；
- GitHub 社区工作流可用于观察编排方式，但财报类 HTML/CSS/JS 报告不适合本项目的
  SSE 文本回答，不能直接照搬。

因此本项目只借鉴“自适应分段、标签和行动步骤”，不引入网页报告、表格、图表、
额外展示节点或第二次润色模型。

## 5. 并发与性能优化

### 5.1 先减节点数，再谈并发

最有效的优化通常不是“把所有节点并行化”，而是减少无意义的 LLM 调用。

优先顺序：

1. 能用 `Code` 做确定性处理，就不要加一个 LLM。
2. 能用一个结构化提取节点完成，就不要拆成多个 prompt 再二次解析。
3. 能通过前置分流避免无关检索，就不要所有请求都先查库。

### 5.2 检索侧优化

默认策略：

- `top_k` 先从小值开始；
- 没有充分证据不要默认开 rerank；
- 命中率不足时再调大 `top_k` 或补 rerank；
- 大库优先用 metadata filtering 缩小候选范围。

对当前项目：

- 通用库和课程库已分库，这是正确方向；
- 不要再把所有知识混到一个库里靠 prompt 区分。
- 商业顾问现用链路已使用 `qwen3-rerank`，且本轮以准确率为硬门槛；在没有同一知识库、同一黄金集的召回 A/B 前，不因一般性性能建议移除 rerank。

### 5.3 生成侧优化

推荐做法：

- 最终生成节点只喂“当前问题 + 关键上下文 + 压缩证据 + 输出规则”；
- 不把完整历史、完整检索 chunk、完整原始 JSON 全塞进去；
- 风险复检只在必要时触发；
- 低价值的“礼貌润色节点”尽量删掉。

### 5.4 Iteration 的使用边界

**官方确认**：`Iteration` 并发模式最多同时处理 10 个元素。

适合：

- 独立 SQL 执行；
- 批量文档处理；
- 多个互不依赖的 API 调用；
- 批量转换。

不适合：

- 强状态、顺序敏感的对话主链路；
- 需要严格顺序流式展示的生成路径；
- 多轮对话里的“逐步推理”主逻辑。

默认规则：

- 用户可见主链路优先顺序模式；
- 纯批处理支路再考虑并发模式。

### 5.5 Answer 变量顺序影响流式体验

**官方确认**：Answer 会按照变量在答案里的出现顺序决定何时开始输出。

因此：

- 需要尽快给用户可见内容时，把能早到的文本变量放前面；
- 不要把一个必须等待的慢变量写在最前面，否则整段都会等。

### 5.6 多模态场景不要默认走多模态检索

如果知识库本质是文本规则库：

- 先用视觉模型抽取图片事实；
- 再把抽取出的结构化文本用于普通文本检索；
- 通常比直接建设多模态知识库更稳、更便宜，也更方便调试。

只有在知识本身包含大量图片语义，且已建立多模态知识库时，才优先考虑图片检索。

## 6. 当前版本防踩坑清单

### 6.1 DSL 编排层

- 不要在互斥分支后的共享节点直接引用所有分支变量。
- 不要把 `llm.text` 原样作为机器消费的最终 JSON，除非已经验证模型输出绝对稳定。
- 不要把“未命中”和“命中”都塞进一个回答 prompt。
- 不要同时让多个分支竞争写同一个语义字段，除非先做收敛。
- 不要依赖模型“自己懂得只看相关字段”来规避结构错误。

### 6.2 Prompt 层

- Prompt 里不要写图上不存在、流程里不存在的工具或插件要求。
- Prompt 里不要同时要求“严格只用知识库”又要求“上下文不足时自由补齐”，除非明确了优先级和边界。
- Prompt 里不要混入内部实现术语给最终用户看。

### 6.3 运维层

- 重新导入为新应用或重建应用后，要核对 App Key 映射。
- Code 节点 401 先查 `CODE_EXECUTION_API_KEY` 与 `SANDBOX_API_KEY`。
- 发布后必须逐路径实测，不要只看 `/parameters` 成功。

## 7. 本仓库 3 个案例的可借鉴结论

### 7.1 学生成绩查询案例

可借鉴：

- 长链路里插入阶段性反馈；
- `Iteration` 处理数组任务；
- 结构化结果再进入图表/展示层。

不建议照搬：

- fenced JSON + 正则解析作为首选；
- prompt、few-shot、字段定义彼此不一致的写法；
- 把 SQL、展示 JSON、图表 JSON 全堆在同一 prompt 里。

### 7.2 跨境电商案例

可借鉴：

- 前置轻量规则分流；
- RAG 命中/未命中双路径；
- 简单业务优先低成本处理。

不建议照搬：

- prompt 中声明了插件/能力，但流程里没有真正实现；
- 一边做 RAG 分流，一边又让 RAG 节点自由补全太多外部知识。

### 7.3 情感回复案例

最值得借鉴：

- 输入规范化；
- 图片/文本双路径；
- 检索证据压缩；
- 风险复检按需触发；
- 分支内闭环，不做危险汇合；
- 生成节点只吃短而准的字段。

需要控制的代价：

- 节点数量多；
- 维护成本高；
- 不适合一开始就过度复制到所有应用。

## 8. 下次编写 DSL 的默认检查表

编写前：

1. 先确定是 `advanced-chat` 还是 `workflow`。
2. 先列出 Start 输入字段和最终输出契约。
3. 先确定是否真需要多知识库、分类器、图片分支、风险复检。

编写中：

1. 先做输入规范化。
2. 互斥分支只走分支内变量。
3. 机器消费的 JSON 输出默认加一层 Code 归一化。
4. 检索后立即判断命中/未命中。
5. 检索结果先压缩再生成。
6. 结构化结果优先 Structured Outputs / Parameter Extractor。
7. 慢节点和二次 LLM 只在必要时保留。

发布前：

1. 逐条检查每个下游节点引用的变量是否在本路径必定存在。
2. 逐分支实测。
3. 结构化输出链路额外验证“纯 JSON / fenced JSON / 前后带文本”三类兼容性。
4. 检查 Code 节点和 Sandbox。
5. 核对 App Key 映射。
6. 保存旧 DSL 导出件用于回退。
