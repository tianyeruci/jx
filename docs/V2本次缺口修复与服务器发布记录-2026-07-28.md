## 1. 修复内容

- 摘要任务改为消息结果提交后再入队，并以 Redis 会话锁避免同一会话的重复摘要任务。
- 模型上下文改为“当前会话摘要 + 北京时间当天有限原始消息 + 已确认画像/路线”；用户可见原始历史保留天数由受保护的管理接口配置，夜间维护固定北京时间 02:00 执行。
- 学习路线改为 `pending_route`、`pending_stage`、`active`、`completed` 状态机：确认路线不自动进入第一阶段，确认阶段后才给当前及下一阶段课程卡片，完成阶段才推进。
- 商业顾问、朋友圈和写作 SSE 统一携带 `schema_version`、`request_id`、`sequence`；终态只会是 `message_end` 或 `error`。
- 增加四项只保留当前值的输出风格设置、会话审计显示名/反馈/检索资源、用户 AI 数据清除、课程名称与区间/课程汇总 PV/UV。
- 增加两个固定 Dify 知识库的管理员接口；清洗与原样上传都执行文件校验，清洗 PDF 禁用 OCR；同名同哈希不重复索引，同名异内容在新版本索引后才移除旧版本。
- Compose 已改为连接 Dify PostgreSQL 中独立的 `ai_management` 数据库与角色、Dify Redis DB 5 和独立 Celery 队列；旧 AI 独立卷不删除。
- Streamlit 已调整为临时只读管理页；仍可用于三类用户入口测试，但不再提供知识库、Prompt、保留策略等管理写操作。

### 4.1 本次遇到的问题与解决方式

1. **离线核心构建在常规 Dockerfile 的在线依赖安装阶段停滞。** 改用已验证的 `Dockerfile.offline` 与 wheelhouse 构建，核心与 UI 仍分别构建、分别打标签。以后离线发布不应切回在线 `pip install`。
2. **Dify PostgreSQL 的网络别名不是 `db`。** 在 `docker_default` 网络中使用实际可解析的 `db_postgres`；数据库名称限定为 `ai_management`。
3. **历史 AI 默认网络与 Dify 网络都可能有 `redis` 别名，导致解析到旧独立 Redis。** 最终让 V2 API/Worker/Scheduler 只加入 `docker_default`，Redis URL 使用 Dify Worker 的受控连接格式并切换至 DB 5。旧 AI 网络、容器和卷不删除，也不再加入 V2 服务。
4. **临时测试页不能安全地直接暴露管理写权限。** 保持 Streamlit 通过现有 Nginx 路由公开用于用户链路测试，管理写操作仅由双 Token API 承担。
5. **容器刚重建时立即访问 8000 会出现一次 `Connection refused`。** 这不是健康失败；发布手册已改为最多等待 60 秒的 ready 重试，只有超时才进入日志排查或回滚判断。
6. **将 DSL 重新导入为新 Dify 应用后，AI 服务不会自动更新应用访问 Key。** 已先备份 `.env` 至 `/opt/ai-management/backups/20260728-214753-app-key-sync`，再在服务器内同步三个用户入口的当前 Key 并重建 API、Worker、Scheduler；三个 `/parameters` 均返回 200。普通发布不一定轮换 Key，但每次发布后仍须核对映射。Key 不进入文档、聊天或日志。
7. **Dify Code 节点执行 Sandbox 时返回 401。** 根因为 API 的 `CODE_EXECUTION_API_KEY` 与 Sandbox 的 `SANDBOX_API_KEY` 不一致。已备份 Dify 配置至 `/opt/ai-management/backups/20260728-215046-dify-sandbox-key-sync`，使两者一致并只重建 Sandbox；只做哈希一致性验证，不输出 Key。
8. **商业顾问 Workflow 的分类分支在汇合处引用了未执行分支变量。** Sandbox 修复后定位到 `Variable #general_knowledge_mixed.result# not found`；随后已改为分支局部的检索、决策和回答链路，重新导入并发布后，通用、课程、混合三类问题均已收到 `message_end`。详见 [V2 Dify 联调问题与修复记录](V2-Dify联调问题与修复记录-2026-07-28.md)。
9. **摘要画像 Workflow 直接透传 LLM 原文会放大 JSON 漂移风险。** 随后已增加 `summary_normalize` Code 节点并重新导入发布；服务器侧直接调用 Workflow，已验证 `outputs.result` 为可解析 JSON，且 `target_message_id` 正确回填。
