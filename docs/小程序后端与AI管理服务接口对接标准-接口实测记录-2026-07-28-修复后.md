### 3.3 待复核条目 / 文件的最终语义

这是本轮重点确认并已写回接口文档的部分：

- `review_required` 是终态，不是可直接重试态。
- 单条目重试只允许 `failed` 条目。
- 文件重试只允许：
  - 文件级失败；
  - 文件下存在失败条目。
- 如果文件下全部条目都处于 `review_required`，文件重试返回 `409`，必须先人工复核。

本轮实测结果：

- 待复核条目直接重试：
  - HTTP `409`
  - `message="只有失败条目可以重试；待复核条目请先执行人工复核"`
- 纯待复核文件直接重试：
  - HTTP `409`
  - `message="待复核条目不能直接重试，请先执行人工复核"`
- 纯待复核文件在条目生成完成后：
  - 文件 `status=review_required`
  - 文件 `outcome=review_required`
  - 文件 `stage=review`
  - 条目 `retryable=false`

### 3.4 人工复核链路

本轮分别验证了两种真实复核路径：

1. `replace_and_approve`
   - 接口返回 `status=pending`
   - 条目重新入库成功
   - 远端父块 / 子块计数回读为 `1/1`
   - 临时 Dify 文档已删除，未污染知识库

2. `exclude`
   - 条目标记为 `excluded`
   - 文件终态同步刷新为 `excluded`
   - 批次聚合状态同步刷新
   - 当批次内文件都为 `succeeded` / `excluded` 时，`all_processed_without_error=true`

## 4. 本轮实际修复的清洗链路问题

本轮不是只做文档更新，实际修掉并复测过以下问题：

1. 待复核条目可被直接重试并发布，绕过人工复核。
2. 纯待复核文件在条目生成完成后仍停在 `processing`，没有进入终态。
3. `exclude` 后文件和批次聚合状态没有立即刷新。
4. 服务器 `Dockerfile.offline` 实际运行代码来自 `wheelhouse`；只同步源码再重建镜像，不会把本地修复带到运行容器。

当前处理结论：

- 以上 4 项都已修复并在 r7 版本完成真实复测。

## 5. 对接方需要直接遵守的口径

### 5.1 给小程序后端

- 文档清洗相关接口当前主要给 AI 管理页使用。
- 小程序后端这轮不需要接入新的清洗写接口。
- 若后续需要代调清洗接口，必须按基线文档里的最终语义处理 `review_required`，不能把它当成“失败后可直接重试”。

### 5.2 给 AI 管理页

- “重试文件”按钮只用于失败文件或存在失败条目的文件。
- “重试条目”按钮只用于失败条目。
- 待复核条目必须先点“复核”，不能直接点“重试”。
- `approve` / `replace_and_approve` 会自动重新提交条目，不需要再额外点一次“重试”。
- `exclude` 不是失败；它会同步刷新文件和批次统计。
