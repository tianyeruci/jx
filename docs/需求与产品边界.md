# 需求与产品边界

> 状态：历史首版资料。当前需求以 `V2决策记录.md`、`V2需求规格说明.md` 和当前专项规范为准；本文保留审计，不同步改写旧流程。

## 用户和调用关系

正式用户通过小程序使用三个入口。小程序后端已经完成登录、会员和是否允许调用 AI 的判断，AI 管理服务不重复判断会员，只信任经过内网与内部 Token 校验的后端调用。

管理员首版不需要新的复杂后台：

- 模型、Prompt、知识库和推荐问题在 Dify 控制台维护。
- 课程和路线由老板按 Markdown 模板提供，开发/运维通过 CLI 校验和发布。
- 只读管理接口用于查看会话、消息、推荐、Token、耗时、点击和清洗失败。
- Streamlit 仅是开发测试工具。

## 三个入口

### 商业顾问

用户可以：

- 新建、查看、重命名、删除和继续多个历史会话。
- 获取有知识库依据的商业问答。
- 直接查询某门审核课程。
- 在目标不明确时回答最多两个关键澄清问题。
- 选择审核路线，查看当前阶段课程，并明确确认完成或跳过阶段。
- 对回答点赞、点踩和填写原因。

产品约束：

- 课程推荐和商业问答是同一个入口。
- 课程和路线只能来自老板审核资料。
- 课程链接、启用状态和路线顺序不能由模型决定。
- 查询具体课程时不强制补齐画像。
- 点击不代表完成，模型推断不代表用户确认。

### 朋友圈顾问

单次创作、改写或润色朋友圈内容。不维护本地历史、画像、课程、路线或反馈。

### 日常写作

单次写作、改写、总结或校对。不维护本地历史、画像、课程、路线或反馈。

## 商业画像

长期保留最小商业画像：

- 业务或学习目标。
- 关注方向。
- 经验或当前阶段。
- 当前学习情况。
- 明确的时间、预算约束。
- 已确认路线。

画像分确认事实和候选，冲突候选不能自动覆盖确认事实。删除历史会话不删除画像。

## 历史和摘要

- 活跃会话中超过7天的原始消息删除，摘要保留。
- 整个逻辑会话连续7天不活动时，会话、消息和摘要全部删除。
- 用户画像和其他用户级路线进度不随会话删除。
- 摘要在异步 Worker 中生成，不增加主 Chatflow 延迟。
- 每轮模型上下文是摘要加摘要之后的最近消息，不重复发送已摘要原文。

## 课程资料字段

必填：

- 稳定 `course_id`
- 课程名称
- 所属方向
- 主要内容或解决的问题
- 官方跳转链接

系统字段：

- `enabled`
- `review_status`
- `source_file`
- `updated_at`

适合人群、课程重点、学习结果、特殊前置条件和阶段标签均可选。路线的阶段顺序已经表达一般学习先后关系，只有路线以外的硬要求才填写特殊前置条件。

## 文件清洗

用户一次选择一个策略和目标知识库，批量上传文件。每个文件独立进入：

```text
pending → processing → succeeded/failed
```

批次 `completed` 只表示所有文件处理结束，同时返回是否全部成功。用户可以看到原始文件名、失败阶段和可读原因，并重试仍有源文件的失败项。

策略是随代码发布的 Python 实现，首版不支持在页面中编写或上传策略。

## 非功能目标

- 首版目标是20个并发流式生成请求，不承诺5000并发。
- 同一会话同时只能有一个生成任务。
- API 应快速先返回状态事件，模型生成耗时单独统计。
- 日志默认不记录真实用户 ID、完整正文、敏感文件名或密钥。
- Dify、Redis 或 Worker 局部失败不能篡改课程事实，也不能让清洗文件永久处理中。

## 第一版不做

- 第四个课程入口。
- 朋友圈/写作历史、画像和反馈。
- 独立 AI 网关、微服务拆分和完整管理后台。
- 动态清洗插件、万能清洗器。
- AI 创建正式课程/路线或自动判定学完。
- 逐课、逐节和视频时间点进度。
- 精确到分钟删除 Dify 单消息。
- Outbox、复杂缓存版本和点击消息平台。
