# Git 提交与推送避坑记录（2026-07-29）

## 目的

记录本次版本提交中遇到的问题及处理方式，供后续提交前直接检查，避免误传私密资料、混入临时产物、忽略测试回归或错误理解工具输出。

## 1. 工作区改动很多，不能直接 `git add .`

### 现象

工作区同时包含：

- 应用源码、数据库迁移、测试和正式文档；
- `tmp/` 下的截图、测试脚本、SQLite 数据库和接口测试结果；
- `dist_fix_20260728/` 下的 wheel 分发包；
- `文件清洗样本/` 下的业务资料，其中部分文件名明确标注“勿传”；
- `推荐/`、`部署问题/` 以及与本次 V2 版本无关的 Dify 示例文件。

### 风险

直接执行 `git add .` 会把私密资料、一次性产物和无关材料一起推送到远端。即使后续删除，内容仍可能保留在 Git 历史中。

### 解决方式

先查看已跟踪与未跟踪文件，再按范围暂存：

```powershell
rtk git status
rtk proxy git -c core.quotePath=false ls-files --others --exclude-standard
rtk git add -u
rtk git add -- <明确需要新增的源码、迁移和文档路径>
rtk proxy git -c core.quotePath=false diff --cached --name-only
```

本次只纳入功能源码、迁移、测试、正式项目文档和已跟踪配置；排除临时目录、样本、wheel 包和无关示例。

### 固化建议

- 不要在包含业务样本的仓库中无检查地使用 `git add .`。
- 将确定不会入库的本地产物补充到 `.gitignore` 前，应先确认团队是否需要保留其中部分文件。
- 推送前必须查看“已暂存文件清单”，不能只看改动数量。

## 2. `.env.example` 也需要做凭据检查

### 现象

`.env.example` 有数据库、Redis、Dify API Key 和管理员 Token 等配置项改动。

### 风险

示例配置文件本应只含占位符，但复制真实环境配置时容易误带密码或 Token。

### 解决方式

单独审阅 `.env.example`，确认值仍为 `replace-with-...` 或空值；暂存后对差异执行敏感词扫描，并人工复核命中项：

```powershell
rtk git diff -- .env.example
rtk proxy git diff --cached | Select-String -Pattern '(api[_-]?key|secret|token|password)\s*[:=]' -CaseSensitive:$false
```

注意：敏感词扫描只能帮助定位，不能代替人工判断。本次命中的是文档占位说明，不是真实凭据。

## 3. `rtk pytest` 输出异常，不能把“未收集测试”当成测试通过

### 现象

使用 `rtk pytest ...` 时命令超时，并输出 `Pytest: No tests collected`，但这与项目实际测试情况不符。

### 解决方式

按 RTK 规则在代理失败后回退到原始测试入口，同时仍通过 `rtk proxy` 控制输出：

```powershell
rtk proxy python -m pytest -q
```

### 判断原则

- 超时、未收集测试、进程异常退出都不等于测试通过。
- 有效通过必须看到正常退出码和明确的通过数量。
- 本次最终结果为 `49 passed`。

## 4. 测试失败可能是契约已变、测试未同步，不能直接删断言

### 现象

全量测试中，`test_context_summary_trigger_and_no_overlap` 失败。旧断言要求摘要游标之前的当天消息不进入上下文；当前代码的新规则则是：当天原始消息全部进入上下文，更早内容由滚动摘要承载。

### 排查过程

1. 单独复跑失败用例，确认不是共享测试数据库污染；
2. 对比 `ai_management/context.py` 与测试差异；
3. 确认实现中的注释和新业务规则一致；
4. 仅更新测试名称和断言，使其验证当前契约；
5. 再次运行全量测试。

### 经验

- 先判断是实现回归、测试数据污染，还是测试契约过期。
- 只有确认业务契约后才能调整测试。
- 修复单个用例后必须跑全量测试，避免局部通过掩盖其他问题。

## 5. `git diff --check` 的 Markdown 行尾空格可能是有意换行

### 现象

`git diff --cached --check` 报告若干 `trailing whitespace`。对应位置是 Markdown 行尾的两个空格，用于强制换行。

### 处理方式

逐条查看位置后确认它们是 Markdown 语义，而不是代码格式污染，因此保留。

尝试用 `perl` 批量清理时，本机提示没有安装 `perl`。这也说明不应依赖未确认存在的格式化工具。

### 经验

- `git diff --check` 的告警需要结合文件类型判断，不能机械删除。
- Markdown 行尾双空格可能有显示语义。
- 批量修改前先确认工具可用，并防止改变文件编码或换行符。

## 6. 提交成功不代表推送成功

### 正确收尾

提交后单独推送，并检查输出中的远端提交范围：

```powershell
rtk git commit -m "<message>"
rtk git push origin main
rtk git status
rtk git log -1 --oneline
```

本次远端更新范围为 `d8f5467..27a8bc0`，推送到 `origin/main`。推送后工作区仍有未跟踪文件，这是主动排除的本地材料，不代表本次提交遗漏。

## 下次提交前检查清单

1. 查看当前分支、远端、已跟踪和未跟踪改动。
2. 明确本次提交边界，禁止无检查执行 `git add .`。
3. 排除 `tmp/`、构建产物、测试数据库、截图和私密业务样本。
4. 单独检查 `.env.example`、YAML、部署文档中的凭据。
5. 运行与改动相关的测试，再运行全量测试。
6. 对失败用例先隔离复跑并确认契约，不盲目改断言。
7. 暂存后检查文件清单、差异统计、空白告警和敏感词命中。
8. 提交后推送，并核对远端范围、最新提交和剩余本地改动。

### 7. 测试完成后仍要重新核对工作区

测试完成不等于工作区只有刚刚验证过的内容。再次提交前发现了新的管理员接口、课程集成、测试记录和文档改动，同时还出现了 `.playwright-cli/`、`output/` 等浏览器和测试产物。

解决方式是重新执行 `git status` 和 `git diff --stat`，按功能边界重新暂存；不要沿用上一次提交的文件清单，也不要因为“测试已经完成”就直接 `git add .`。
