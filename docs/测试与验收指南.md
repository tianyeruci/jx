## 4. RAG 检索评测

导入通用资料和课程资料后：

```powershell
ai-rag-eval test_data/rag/golden_questions.jsonl --top-k 5 --output var/reports/rag.json
```

工具对有标准相关文档的用例计算 Recall@5、MRR 和 HitRate@5；无答案、停用过滤、进度不推进和路线不篡改用例列为完整 Chatflow 行为检查，不能用检索命中率替代。

验收门槛：

- 关键问题 Hit@5 ≥ 90%。
- 全量 Recall@5 ≥ 80%。
- 引用完整率 ≥ 90%。
- 无依据回答率 ≤ 5%。
- 错误课程 ID、错误正式链接、虚构路线均为0。

至少人工检查10条完整回答。

### 4.1 小项目推荐的三层评测

不要只看一个“准确率”。商业顾问链路拆成三层即可：

1. 知识库直检：`ai-rag-eval` 计算 Recall@5、Hit@5、MRR，定位分块、Embedding、Top-K 和资料问题。
2. 全链路规则评测：调用 AI 管理服务真实 SSE，校验课程 ID、路线 ID、停用过滤、拒答、首 Token 和总耗时。
3. 少量人工抽检：每次发布人工看 5～10 条回答的事实依据、完整性和表达，不引入 LLM Judge 作为首版门禁。

全链路命令：

```powershell
python scripts/evaluate_business_e2e.py `
  test_data/rag/business_e2e_cases.jsonl `
  --base-url http://127.0.0.1:8000 `
  --token "<INTERNAL_API_TOKEN>" `
  --output var/reports/business-e2e.json
```

脚本为每条用例使用独立测试用户，结束后删除测试会话。报告包含逐例断言、通过率、首 Token P50/P95 和总耗时 P50/P95。

首版不建议直接引入 Ragas、DeepEval 或 Promptfoo。它们适合需要 LLM Judge、多个模型/Prompt 对比或 CI 平台化之后再接入；当前以确定性结构化断言为主，更便宜、稳定、容易解释。

## 6. 并发与故障

最低执行：

- 20个不同会话并发流式请求，持续10分钟。
- 同一会话并发返回409。
- 客户端断开后 Dify 停止和本地状态正确。
- Dify 超时/限流/不可用。
- Redis、PostgreSQL 短暂不可用。
- Worker 重启、清洗任务自动重试一次。
- 200MB 流式上传。

`p95 < 200ms` 只统计服务开始响应 SSE 状态事件的自身开销，不包含模型生成时间。

20并发10分钟脚本：

```powershell

  --token "<INTERNAL_API_TOKEN>" `
  --concurrency 20 `
  --duration-seconds 600
```

## 9. 扫描 PDF OCR 验收

OCR 验收只验证 jx 测试服务器的运行时配置和部署行为，不把软件安装误写成业务代码改动。至少保留脱敏报告证明：

- `.env` 的 `PDF_OCR_ENABLED`、OCR 镜像和模型路径正确；Paddle/PaddleOCR/PaddleX 导入、系统共享库和 manifest SHA-256 校验通过；
- 有文字层 PDF 不执行不必要的 OCR，无文字层 PDF 进入 `ai_ocr` 队列；
- 空闲时 `ai-ocr-worker` 不运行；队列出现任务时自动启动，任务执行期间不停止；队列和 Celery active/reserved/scheduled 连续 10 分钟为空后停止；
- 质量、置信度、隐私、Metadata、索引和 Dify 回读全部通过时才自动发布；页数超限、低置信度、模型校验失败、共享库失败或下游契约失败均进入 `review_required`/`failed`，不产生误发布；
- 启动失败时任务仍可在队列中观察到，systemd journal 有错误和退避记录；不通过清 Redis、删上传卷或手工改数据库恢复。

验收入口：`tests/test_pdf_ocr_quality.py`、`tests/test_cleaning_release_contract.py`、`tests/test_quick_deploy_contract.py`，以及部署手册中的 systemd/队列实测命令。当前 jx 目标为 OCR 最多 50 页、任务超时 3600 秒；机器可通过 `JX_ACCEPTANCE_CLEANING_BUDGET_MAX_YUAN` 配置本轮付费清洗累计上限，未配置时默认为 5.00 元。可用 `python scripts/jx_acceptance_budget.py --spent-yuan 0 --next-yuan 0.80` 做 fail-closed 预检。模型正文、密钥、Token、真实用户 ID 和原始敏感文件名只能留在受保护的 `var/reports/`，不能进入提交或文档。

PDF 格式/OCR 质量告警不应为了“全绿”强行改成失败；测试阶段先在 `var/reports/<run-id>/issues.jsonl` 脱敏记录，全部场景完成后统一修复并从头重跑。阻断项必须在问题中心保持 `open`，直到管理员用精确 `issue_id` 解决。

## 11. 2026-08-02 清洗链路与实时模式补充

- `BAILIAN_BATCH_ENABLED` 默认关闭（`false`）；只有明确配置为 `true` 且候选数或估算输入 Token 达到阈值时，四个内容模型策略和课程目录策略的新任务才允许进入百炼 Batch。默认测试环境保持 `false`，任务详情应显示 `实时调用（realtime）`，已有 Batch 任务不得被改写或自动降级。需要验证 Batch 时必须显式记录临时阈值、费用确认和 24 小时异步轮询结果；实时调用仍需验证 RPM/TPM 限制、实时 Worker 并发和独立价格快照。
- `course_route_catalog` 默认由 `COURSE_CATALOG_AUTO_PUBLISH=true` 控制自动路径：先用确定性解析固定课程名称、链接、稳定 ID、路线归属和顺序，再调用模型补语义字段。普通名称冲突、来源依据不足、价格/模型契约/隐私/Dify 回读任一失败，都必须整源阻断，不能只发布部分课程；关闭开关时才验收结构审核表和语义审核表人工回退路径。
- 同名或同内容重传必须先执行精确源文件删除，核对远端分片为 0、`source_deleted_at` 和 `dedupe_released_at` 已写入、批次聚合已终态；不能用文件名模糊删除、单独删 Dify 文档或直接改库替代。
- PDF/DOCX 转换后的前置 Markdown 仅在测试环境通过 `SAVE_CONVERSION_MARKDOWN=true` 保存到服务器专用目录；验证 API 与清洗 Worker 共享挂载、文件权限和过期清理，生产环境必须关闭且不提供 HTTP 下载。
