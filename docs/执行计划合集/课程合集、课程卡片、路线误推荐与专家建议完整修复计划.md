# 课程合集、课程卡片、路线误推荐与专家建议完整修复计划

## 总结

本次统一处理四类问题：

- 测试页没有直接渲染服务端已经定义的课程卡片。
- Dify 回答正文泄露课程/路线 ID，且正文可能与服务端最终卡片不一致。
- 课程合集边界和时长未结构化，导致 `AI智能体写作` 被误归入 `AI写作课`。
- 课程卡片发送后缺少一条面向用户的综合下一步建议。

固定接口保持不变：不新增路径、请求字段、响应字段、SSE 事件或枚举；专家建议复用现有 `course_recommendation_note`。

## 核心实现

### 1. 课程合集清洗与内部数据

- 新增内部 `CourseCollection` 和 `CourseCollectionMember`：
  - 稳定合集 ID、干净名称、原始标题、声明讲数、标准化总时长、可选标题入口课程、成员及顺序。
  - 不向 HTTP/SSE 增加合集字段；现有 `series_name` 保存干净合集名。
- 括号标题无论是否有链接都识别为合集：
  - 连续 `1/…N/` 子项按声明讲数归组。
  - `N=1` 时允许紧邻、同路线同阶段的无编号课程作为唯一子项。
  - 标题有链接且存在子项时，链接保留为合集入口，不混入成员顺序。
  - 没有子项时，标题课程自身作为唯一成员。
  - 达到声明讲数即关闭合集，后续普通课程不再继承。
- 缺讲只记录警告并保留已知成员；重复、越界、顺序冲突或多合集归属进入结构审核，禁止模型猜测。
- 真实样本基线保持 `137` 条源行、`105` 门课程、`5` 条路线，并形成 `33` 个内部合集：
  - `AI写作课`：2 门、4 小时；
  - `AI智能体写作`：标题自身为唯一课程、2 小时。
- 合集名称、时长和顺序进入课程检索正文，但不写入链接；Dify 文档数量仍为课程加路线，不额外创建合集文档。

### 2. 合集与路线推荐规则

- 在路线评分前增加唯一合集匹配：
  - 规范化空格、括号和末尾“课/课程”等通用后缀，使“AI写作”可匹配“AI写作课”。
  - 多个合集同时命中则澄清，不任意选择。
- 合集查询继续使用现有 `direct_course`，按成员顺序最多返回 5 张卡片。
- 只有明确命中正式路线或用户明确要求切换路线时才进入路线流程，不把合集自动扩大成所属大路线。
- 内部保存上一轮合集范围：
  - “从零开始”等续问继续针对该合集。
  - 有明确入门成员时只返回这些成员。
  - 没有入门成员时返回澄清，不给高级课程或无关路线卡，并询问是否切换到更广路线。
- 现有路线确认规则不变：等待路线或阶段确认时 `course_cards` 必须为空；确认阶段后才返回当前及下一阶段课程。
- `learning_route` 每次返回完整路线全部阶段；每个阶段保留机器字段 `course_ids`，并补充与其一一对应的同序 `course_names` 以及按课程原始顺序首次出现去重的 `course_collection_names`。

### 3. 正文、卡片和专家建议

- Dify 采用“候选决策 → 主回答模型”两阶段：
  - 主回答模型输出内部 `final_answer`、综合 `expert_insight` 以及该建议实际依据的 `expert_course_ids`。
  - 不新增独立模型调用；专家建议复用主回答模型，只有少量输出 token 增量。
- 服务端先校验课程，再决定是否发送专家建议：
  - 只有实际发出 `course_cards` 才允许发送，包括明确查课、合集推荐和已激活路线。
  - 专家建议始终是一条综合消息，不按卡片逐条生成。
  - `expert_course_ids` 必须与最终发送的卡片 ID、顺序和最多 5 门限制一致。
  - 候选被过滤时保留最终有效卡片；只要最终卡片通过门禁，模型建议缺失或不合规就使用服务端安全默认建议，不让用户看到推荐理由或内部信息。
- 专家建议使用：
  - 最终课程事实、当前问题、已确认画像、已确认阶段及已确认合集时长；
  - 不使用未确认画像、被过滤课程或额外推测的课程内容。
- 建议为 1–2 句、最多 80 个中文字符，直接给出基于课程事实的可执行下一步；多门课程只发送一条组合建议。
- 禁止输出 ID、链接、未审核事实、虚构课节、收益保证或结果承诺。
- SSE 顺序固定为：
  1. 主回答 `answer_delta`
  2. 可选引用和路线
  3. `course_cards`
  4. `course_recommendation_note`
  5. 可选 `answer_delta`（路线下一步引导）
  6. `message_end`
- `course_recommendation_note.content` 直接是建议正文，不添加“匹配理由：”或“专家建议：”前缀；新会话不写入 `recommendation_note`，旧字段仅兼容读取。
- 模型内部建议仍可保存为 `expert_insight` 供管理端兼容读取，但不新增 `expert_insight` SSE 事件；服务端只在最终卡片门禁通过后发送该独立建议。
- 专家建议与主回答共用同一个助手 `message_id`、反馈和终态，不创建第二条数据库消息。
- 历史会话按已有字段只读兼容；不为旧会话生成、回填或改写新的下一步建议。

### 4. 服务端安全与页面展示

- 增加跨 SSE 分片的课程 ID、路线 ID、阶段 ID 过滤，结构化卡片和路线事件不受影响。
- 课程/路线回答在发送前校验：
  - 正文提及的正式课程和路线必须属于最终结构化结果；
  - 不一致时使用基于已验证结果的安全回答替换。
- Streamlit 商业顾问页和课程测试页：
  - 直接显示课程卡片及 `redirect_url` 点击按钮；
  - 卡片后显示独立“专家建议”气泡；
  - 路线状态单独展示；
  - 原始 SSE 保留在折叠诊断区。
- 点击只打开服务返回的 `redirect_url`，继续由 `/r/{token}` 完成 PV、UV 和跳转。

  - 主回答模型的 `expert_insight` 和 `expert_course_ids` 草稿结构。
- 使用加法型数据库迁移；合集表为空时旧课程与路线仍可工作。
- 本地先 dry-run 真实样本，确认课程 ID、路线 ID、正式链接和新目录原子替换结果；本轮导入后目录统计为 `105` 门课程、`5` 条路线、`33` 个课程合集、`103` 条成员关系。
- jx 后续发布须单独授权：
  1. 备份 PostgreSQL、Redis 快照、Dify Dataset manifest、镜像及当前 App Key。
  2. 部署兼容新旧数据的服务代码和测试页。
  3. 在隔离 Dify 应用导入候选 DSL并完成契约测试。

## 测试与验收

- “我想学习AI写作”：
  - 只返回 AI 写作合集的 2 张卡片；
  - 正文无课程/路线 ID；
  - 卡片后只有 1 条无前缀综合下一步建议；
  - 不返回学习路线。
- 同会话“从零开始”：
  - 说明该合集当前属于高手进阶；
  - 不推荐公众号入门课程；
  - 本轮无卡片，因此无 `course_recommendation_note`；
  - 询问是否切换到更广路线。
- “AI智能体写作”返回自身一张卡片和一条综合专家建议。
- 明确查询某门课程，只要返回卡片，也必须追加一条专家建议。
- 路线等待确认、澄清、无匹配、停用或未审核课程被过滤时不发送专家建议。
- 多卡片建议只依据实际发送的最多 5 张卡；候选集合与最终卡片不一致时使用安全默认组合建议，禁止发送不一致的模型内容。
- 验证专家建议：
  - 不包含 ID、链接、被过滤课程、虚构内容或承诺；
  - 实时 SSE、消息历史、Streamlit 和管理端 `professional_insight` 内容一致；
  - 共用当前消息反馈；
  - 停止生成时不留下半条建议。
- 完成课程解析、推荐状态机、SSE 分片过滤、Dify 输出契约、历史重载、测试页浏览器和点击跳转回归；验证后再将可复用根因写入对应排障文档。

## 已确认约束

- 问题文件末尾空白“2、”仅为占位。
- 专家建议是一条针对全部已发送课程的综合消息，不是每张卡片一条。
- 只要本轮实际发送并通过最终门禁的课程卡片，包括明确查课，就发送一条综合下一步建议；无卡、待路线/阶段确认、解析失败时不发送。
- 专家建议复用主回答模型，不新增模型调用。
- 专家建议复用 `course_recommendation_note`，不恢复或新增 `expert_insight` SSE 事件。
- 不执行远端部署、正式数据写入、Git push 或发布；保留所有无关工作树文件。
