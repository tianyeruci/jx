# jx-now 统一改造执行计划（课程合集优先，咨询/OCR 继承）

## 1. 权威性与冲突裁决

本文件是以下三个专项计划的统一执行基线：

1. `PDF OCR 清洗与语义质量保障改造计划.md`
2. `商业咨询案例清洗与零召回审查.md`
3. `课程合集、课程卡片、路线误推荐与专家建议完整修复计划.md`

专项文件保留为来源和历史记录，不再分别驱动实现。若内容冲突，按“用户最新确认 > 本文件 > 第三专项 > 第二专项 > 第一专项”的顺序裁决；第三专项的业务优先级最高，但不能覆盖用户后来确认的 OCR 配置、当前 DSL 和测试发布顺序。

当前 DSL 唯一行为基线：

- `dify/商业顾问（当前使用版本）.yml`

`商业顾问_并发准确率响应优化版_Dify-1.13.3.yml` 只作为隔离候选，不整份替换当前 DSL；已验证的单项修复才可单独移植。

## 2. 已确认的不可变约束

- 用户允许在本计划执行期间启动子 Agent 并行推进审计、实现和测试；子 Agent 只能在明确分工范围内工作，所有合并、验证、发布和最终结论由主 Agent 统一负责。
- OCR 页数限制在服务器配置文件中设置，默认 10 页，允许 1–50 页；仅限制扫描型 PDF 的 PaddleOCR 路径，文字层 PDF 不受此页数门禁影响。
- 百炼 Batch 默认关闭（`BAILIAN_BATCH_ENABLED=false`）；除非单独获得明确批准，不得在测试流程中自动启动 Batch，以免长时间等待阻塞测试。课程目录自动流程仍按独立的成本上限和发布门禁执行。
- 测试页正式地址为 `http://112.74.37.111/ai-management-test/`；不得把内部容器地址或 HTTPS 内网地址当作用户验收入口。
- 文件清洗页面本轮必须逐一验收：`personal_business_consultation`、`wechat_public_account_cognition`、`zsxq_post`、`xiaobot_post`、`lead_magnet`、`course_route_catalog`。兼容保留的 `course_information`、`learning_route` 不在页面展示，也不纳入本轮端到端测试；页面已有的 `book` 策略不属于本轮新增六策略验收范围。
- OCR 任务超时默认 600 秒，必须满足 `>= max(600, max_pages*60)`；软超时为硬超时减 60 秒。OCR 使用独立 `ai_ocr` 队列、单并发、prefetch=1，离线模型清单必须校验 SHA-256。
- 当前 DSL 不得因本地生成而被视为线上已发布；线上变更必须经过导出/导入/发布、参数核对、真实调用和回滚证据。
- 不新增 HTTP、SSE 路径、请求字段、响应枚举或独立专家建议事件；课程专家建议复用现有 `course_recommendation_note`，与同一助手消息关联。
- 咨询案例只处理 DOCX/PDF；v2 使用共享背景、1–5 个决策单元、事实状态、E0–E3、背景充分度、来源覆盖和确定性 Markdown。隐私或证据不足进入 `review_required`，不得猜测或发布。
- 课程基线为 137 条源行、105 门课程、5 条路线；当前运行目录为 114/7。合集识别目标为 33 个，`AI写作课` 2 门/240 分钟，`AI智能体写作` 单独 1 门/120 分钟。
- 生产数据、Dify 数据库、持久卷和 Git 远端不在本地开发阶段直接修改；发布前必须备份、核对身份与隔离性，失败可回滚。

## 3. 交付范围

### 3.1 OCR 与清洗

- PDF 前两页类型分流；文字、扫描、混合类型分别处理，混合或无法判定进入复核。
- 200 DPI 首次 OCR，低置信、空页、关键事实冲突按页 300 DPI 重试；缺少置信度、关键数字/日期/否定/主体冲突禁止自动入库。
- OCR 诊断保留稳定错误码：`OCR_PAGE_LIMIT_REVIEW`、`OCR_LOW_CONFIDENCE_REVIEW`、`OCR_KEY_FACT_CONFLICT`、`PDF_TYPE_REVIEW_REQUIRED`。
- 普通 PDF、咨询 PDF、重试和维护任务全部按扩展名路由到 `ai_ocr`；非 PDF 保持原队列。

### 3.2 商业咨询 v2

- 新增严格 schema、来源块覆盖校验、确定性父子 Markdown（每个决策单元独立子块，硬上限 1200 字）。
- 保留历史 `sections` 结构兼容；仅在模型显式输出 `schema_version=consulting_case_v2` 时启用 v2 分支。
- DOCX/PDF 提取、脱敏、隐私复核、E0–E3 和 rerank 阈值矩阵通过影子清单和 A/B 脚本验证；不自动把一个策略的文章转成另一个策略。

### 3.3 课程合集、课程卡片与专家建议

- 加法迁移新增 `course_collection` 与 `course_collection_member`；保存稳定合集、讲数、分钟数、入口课程、成员顺序和警告。
- 合集优先于路线匹配；唯一命中才返回有界课程卡片，冲突时澄清，不把合集扩大成路线。
- 服务端校验专家建议的 `expert_course_ids` 必须与最终卡片 ID 和顺序一致；不一致、泄露 URL/ID 或候选被过滤时只保留卡片，省略专家建议。
- Streamlit 页面直接展示服务端卡片和签名 `redirect_url`，路线状态单独展示，历史消息重建同一条综合建议。

### 3.4 Dify

- 从当前 DSL 可重复生成 `dify/商业顾问_统一修复版_Dify-1.13.3.yml`，只添加 `expert_course_ids` 内部字段和服务端校验所需 parser 输出，不改变模式、变量、知识库 ID、rerank 模型或外部接口。
- 本地静态契约和 parser 回归通过后，jx 只能在隔离应用导入、发布并验证三类问题；验证前不切换正式应用 Key。

## 4. 分阶段执行顺序

### 阶段 A：开发与本地基线

1. 保留工作树中用户已有改动；核对 `docs/README.md`、功能索引、目录结构和当前 DSL SHA。
2. 完成 OCR、咨询 v2、课程合集、专家建议、测试页、迁移、发布脚本和文档索引改造。
3. 先运行全部本地测试组；普通失败只记录到 `var/reports/<run>/issues.jsonl`，安全门禁失败立即停止。按 TEST-005 拆分长组并保留每组终端证据。六种当前清洗策略必须逐一完成从上传、队列、模型/规则清洗、复核或发布、状态回读到精确清理的全链路验证；旧的两个兼容策略不在页面或本轮验收范围。

### 阶段 B：统一修复与本地回归

1. 等全部测试组结束后统一处理问题。
2. 从第一组开始完整重跑；通过条件为所有测试组通过、迁移升级到 head、Ruff、compileall、shell 语法和 DSL `--check` 全通过。

### 阶段 C：jx 发布与修改功能测试

1. 发布前生成 PostgreSQL、Redis、上传卷、镜像/应用 wheel、Dify Dataset manifest、当前 App Key 和环境配置快照；核对 API/Worker/Scheduler/OCR Worker wheel SHA 一致。
2. 仅发布到 jx 测试环境；先做健康检查和无报错 smoke，再用 `http://112.74.37.111/ai-management-test/` 依次测试本轮修改的 OCR/六种文件清洗策略、咨询、课程合集/卡片/专家建议、Dify 三路径。先完成修改功能测试，再统一修复该阶段问题并从本阶段第一项重跑。
3. 该阶段的问题全部记录，测试结束后统一修复；修复后从本阶段第一项重跑。

### 阶段 D：接口文档覆盖与收尾

1. 按测试页 9 个页签覆盖可操作功能；低层、只读、破坏性或页面没有控件的接口使用脱敏契约 runner 覆盖。
2. 所有接口测完后统一修复，再从头重跑；无新增接口时仍核对既有路径、SSE、错误结构和鉴权。
3. 只有全部接口和页面测试完成、问题统一修复并复测后，才更新功能与接口索引、Dify 绑定指南、清洗规范、课程合集规范、部署/回滚记录、测试验收记录和状态交接；追加已验证故障根因到排障文档。
