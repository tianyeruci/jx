一、目标

目前只有 jx 服务器可用于真实环境测试。我需要在 jx 上并行部署一套“隔离测试版 ai-management”，用于验证本次文档清洗修改，包括：

1. 内容模型策略的局部保留、辅助字段降级、重试和状态行为；
2. personal_business_consultation 的案例解决方案和方法提取；
3. 混合 PDF 的选择性 OCR；
4. 过期去重记录不再阻止重新入库；
5. 正常运行使用 realtime；四个指定策略做本地 Batch/Realtime parity，其中 `personal_business_consultation` 和 `zsxq_post` 在预算及隔离证据成立后做真实付费对照；
6. Dify 测试知识库中的文档、Metadata、索引和实际检索结果。

测试版必须和 jx 当前正在运行的正式 ai-management 在以下方面隔离：

- PostgreSQL 数据；
- Redis 数据及 Celery Broker/Result Backend；
- Celery 任务消费；
- 上传文件和转换产物；
- 审计材料和测试报告；
- Docker Compose 项目、容器和卷；
- API 端口和 Docker 网络别名；
- Dify 写入目标。

正式 ai-management 的 API、Worker、Scheduler、数据库、Redis DB、上传卷和正式知识库不得被测试版修改或消费。

二、数据库和 Redis 的确定边界

数据库和 Redis 都复用 Dify 当前创建并运行的 PostgreSQL、Redis实体，不另外部署 PostgreSQL 或 Redis 容器，但数据必须逻辑隔离。

1. PostgreSQL

- 测试版使用 Dify PostgreSQL 实例中的独立数据库和独立角色。
- 推荐数据库名和角色名均使用 `ai_management_cleaning_test`；创建前检查是否已存在。
- 如果同名对象已存在，不覆盖、不删除，先核实其归属和状态；无法证明属于本测试时停止并报告。
- 测试数据库执行当前代码要求的 Alembic 迁移。
- 禁止连接、迁移或写入 Dify 自身的 `dify` 数据库。
- 禁止连接、迁移或写入当前正式 ai-management 使用的 `ai_management` 数据库。
- 测试环境 `DATABASE_URL` 必须在容器内回读并证明：主机是 Dify PostgreSQL 服务，数据库名是专用测试数据库；报告只保存主机、端口、数据库名和角色名，不输出密码或完整 URL。

2. Redis

- 测试版继续使用 Dify Redis 实例的现有 TCP 端口 `6379`，但使用一个当前无人使用的独立 Redis 逻辑 DB。
- 当前正式 ai-management 使用 Redis DB 5，测试版严禁使用 DB 5。
- 测试 Redis DB 已固定为 6，启动或恢复前必须只读核对：
  - jx 所有运行容器实际使用的 Redis URL 中的 DB 编号；
  - Dify 和 ai-management 的服务器配置；
  - Redis `INFO keyspace` 或等价的各 DB 键数；
  - 现有运维脚本或定时任务是否引用候选 DB。
- 首次创建本测试环境时，DB 6 必须同时满足“没有其他运行服务/运维任务引用”和“当前键数为零”。不能只因为键数为零就认定未使用。
- 若已存在本任务隔离部署，DB 6 可能保留本测试数据。此时按第十节核验归属、引用和待处理队列，不要求清空、不把既有测试 Worker 的引用判成外部冲突；无法证明独占时停止新增负载并报告。
- 把已核实的 Redis DB 6 和引用/键归属证据记录到测试环境清单；冲突时不擅自改 DB 或另建 Redis。
- 测试 API、普通清洗 Worker、realtime Worker、publication Worker、按需 OCR Worker以及以后经批准才启动的 Batch Worker，必须全部连接这个测试 Redis DB。
- 因为当前 Celery 队列名是固定的，Redis DB 隔离是防止正式 Worker 和测试 Worker交叉消费的硬门禁。启动前后都要验证正式 Worker 看不到测试任务、测试 Worker 看不到正式任务。
- 测试完成后，只有在测试服务全部停止、再次证明该逻辑 DB 专属于本测试，并得到我的删除确认后，才可以精确清理该 DB。
- 禁止清理 DB 5、其他 Redis DB、整个 Redis 实例、RDB/AOF 或 Redis 持久卷。
