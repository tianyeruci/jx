# V2 全链路缺口修复、AI 管理补齐与服务器验收计划

## 一、目标与范围

不推倒重写，在当前 V2 基础上完成：

1. 修复摘要画像、学习路线、混合问题检索等 P0 缺陷。
2. 迁移到 Dify PostgreSQL/Redis，并保持逻辑隔离。
3. 补齐历史保留、AI 管理、知识库、会话审计和课程统计。
4. 冻结小程序后端所需 API/SSE 契约。
5. 完成模块化整理、自动化测试、容量测试、故障注入、部署和回滚演练。
6. 在隔离知识库完成约 1000 万中文字符真实索引与检索验收。

本次明确不做：

- 商业顾问聊天附件。
- 本地一键切换整个应用模型。
- Prompt 历史、审批和一键回滚。
- 正式管理前端、管理员账号和权限体系。
- 服务端 `Idempotency-Key`；幂等由小程序后端负责。
- 外部告警平台、仪表盘和通知闭环。
- 知识库本身的创建、重命名和删除管理。
- OCR、图片内容识别。
- 逐次课程点击事件表。

## 二、P0 业务问题修复

### 1. 摘要与用户画像自动入队

修复当前先判断、后计算 `enqueue_summary` 的顺序错误：

- 完成消息持久化并计算摘要条件。
- 数据库事务成功提交后，再发送 Celery 摘要任务。
- 达到轮数或字符阈值时自动入队。
- 同一会话只允许一个有效摘要任务。
- 摘要失败不得推进游标或删除原消息。
- Worker 重试时从最后成功游标继续，防止旧任务覆盖新摘要。
- 画像只接受用户明确表达的事实，不采纳模型猜测、课程点击或助手自述。

### 2. 用户历史与模型上下文分离

用户可见历史：

- 默认保留 7 天。
- 管理后台可调整为 1–365 天。
- 超期消息仅在已被摘要覆盖后删除。
- 会话所有消息均超期时，删除会话及会话摘要。
- 用户画像和路线进度长期保留，直到执行用户 AI 数据清除。
- 用户数据清除不删除课程 PV/UV 聚合和必要审计日志。

模型上下文：

- 使用当前会话摘要、用户画像、相关路线进度和有限的未摘要消息。
- 优先保留北京时间当天的原始消息。
- 当天过长时使用“已生成摘要＋最近消息”，不加载完整 7 天历史。
- 保留现有消息条数和字符预算上限。

维护任务固定在北京时间凌晨 2 点执行，时间不开放修改；任务运行时读取数据库中的保留天数。

新增接口：

- `GET /internal/v1/admin/settings/retention`
- `PUT /internal/v1/admin/settings/retention`

### 3. 学习路线状态机

路线流程调整为：

1. 判断是明确查课，还是需要路线推荐。
2. 明确查某课程时直接查询课程知识库，不使用画像和路线。
3. 目标型需求先检查课程推荐画像是否足够。
4. 信息不足时提问补全，不立即推荐课程。
5. 给出候选路线和推荐原因，不返回课程卡片。
6. 用户自然语言确认路线后，进入阶段确认。
7. AI 根据问题、画像和已有路线提出候选阶段，但不自动保存。
8. 用户明确确认阶段后，保存路线进度。
9. 返回当前阶段及下一阶段全部有效课程。
10. 用户明确确认当前阶段已完成后，才推进到下一阶段。

不接入小程序课程学习记录接口，不由 AI 自动写入阶段。

一名用户可拥有多条路线：

- 根据当前问题选择最相关路线。
- 多条路线都可能匹配时，先让用户选择。
- 只更新本轮确认的路线。
- 点击课程链接不得推进路线进度。

数据调整：

- 路线进度增加 `pending_route`、`pending_stage`、`active`、`completed` 状态。
- `current_stage_id` 在阶段确认前允许为空。
- 增加明确的 `confirm_route`、`confirm_current_stage`、`confirm_stage_completed` 操作。
- 只有模型返回的证据原文确实存在于本轮用户消息时，服务端才接受进度变更。

SSE 中继续使用 `learning_route`，增加：

- `state`
- `reason`
- `suggested_stage`
- `confirmation_required`

只有阶段已确认或属于明确查课时，才能发送 `course_cards`。到达最后阶段时只返回当前阶段课程。课程卡片之后才发送独立的 `expert_insight`。

### 4. 混合问题结构化拆分

修改商业顾问 Dify DSL：

- 增加问题拆分节点，输出严格 JSON：`general_query`、`course_query`、`question_type`。
- 普通问题只检索通用知识库。
- 明确课程问题只检索课程知识库。
- 混合问题分别检索两个知识库，再由最终回答节点合并。
- 空子问题不执行对应检索。
- 检索资源返回知识库类型和对应子问题，便于审计。

异常处理：

- JSON 解析失败时重试一次拆分节点。
- 再次失败则临时使用原问题检索两个知识库，记录 `mixed_query_split_fallback` 日志。
- 不允许因拆分失败直接返回空回答。

## 三、Dify PostgreSQL/Redis 逻辑隔离迁移

### PostgreSQL

使用 Dify PostgreSQL 实例，但：

- 创建独立数据库 `ai_management`。
- 创建独立角色，仅授予该数据库权限。
- 不读取、修改或迁移 Dify 自身业务表。
- 所有 AI 管理表通过 Alembic 创建。

### Redis

使用 Dify Redis 实例，但：

- 使用确认未占用的逻辑 DB 5。
- 所有业务键使用 `ai:` 前缀。
- Celery 使用独立队列名称。
- 禁止执行 `FLUSHALL` 或影响其他逻辑 DB 的操作。

迁移策略：

- 当前 AI 数据属于测试数据，不迁移到新数据库。
- 新数据库从空结构开始。
- 旧 AI PostgreSQL、Redis 和数据卷不删除，保留为回滚点。
- 上传文件卷继续独立使用。
- 迁移前备份 Dify PostgreSQL、Redis 配置及现有 AI 独立卷，并验证备份可读取。

Compose 移除 AI 自建 PostgreSQL/Redis 的运行依赖，API、Worker、Scheduler 接入 Dify 内部网络。

## 四、AI 管理能力

### 1. 输出风格 Prompt

增加四项配置：

- `business_answer`
- `business_expert_insight`
- `moments`
- `writing`

商业回答和专家见解共用商业顾问 Dify 应用，但使用不同变量；摘要画像不开放编辑。

接口：

- `GET /internal/v1/admin/style-settings`
- `PUT /internal/v1/admin/style-settings/{style_code}`

规则：

- 只保存当前版本，不保存历史正文。
- 文本最长 4000 字符。
- 只能影响语气、结构、篇幅、格式和表达方式。
- 不能覆盖安全、课程校验、业务流程和结构化输出规则。
- 朋友圈和写作的用户 `tone` 只能补充；冲突时管理员配置优先。
- 操作日志只保存编码、版本、长度和哈希。
- 操作人统一记录为 `admin`。

Dify 增加对应可选输入变量，未配置或服务回滚时使用原有默认风格。

### 2. 知识库文档管理

只管理：

- `general`：通用知识库。
- `course`：课程知识库。

接口：

- `GET /internal/v1/admin/knowledge-bases`
- `GET /internal/v1/admin/knowledge-bases/{kb_code}/documents`
- `POST /internal/v1/admin/knowledge-bases/{kb_code}/upload-batches`
- `GET /internal/v1/admin/knowledge-bases/{kb_code}/upload-batches/{batch_id}`
- `POST /internal/v1/admin/knowledge-bases/{kb_code}/upload-batches/{batch_id}/files/{file_id}/retry`
- `PATCH /internal/v1/admin/knowledge-bases/{kb_code}/documents/{document_id}/status`
- `DELETE /internal/v1/admin/knowledge-bases/{kb_code}/documents/{document_id}`

支持两种上传方式：

- `cleaned`：校验、提取、清洗、标准化、分块后上传。
- `raw`：保留原文件，由 Dify 原生解析和分块。

统一限制：

- Markdown、TXT、DOCX、PDF。
- 单文件最大 200MB。
- 每批最多 10 个文件。
- 每批总计最大 500MB。
- 流式写入临时文件并计算哈希，禁止整文件读入内存。
- 校验扩展名、MIME、文件头、路径和可解码性。
- 清洗模式 PDF 只处理可提取文字和普通表格，不启用 OCR；扫描件和图片型 PDF 返回明确不支持。
- 原样上传不承诺 OCR 能力。
- Nginx、应用和 Dify 上传限制同步调整，上传卷执行剩余空间检查。

原样上传固定使用已验证的高质量父子分块参数，本次不开放分块参数、文档改名和元数据编辑。

重复规则：

- 同名且内容相同：返回已有文档，不重复索引。
- 同名但内容不同：自动更新原 Dify 文档并重新索引。
- 内容相同但文件名不同：按新文档创建。
- Dify 中已有多个完全同名文档：返回 409，由管理员先处理。

永久删除要求提交完整 `confirm_name`，名称不匹配返回 409。Dify 删除失败时不得标记本地成功。

所有知识库读写接口同时要求内部 Token 和管理员 Token。Dataset ID、Dify Key 不进入响应。

### 3. 会话审计

完善管理员会话接口和只读页面，展示：

- 用户匿名标识和可用的用户名称。
- 会话、用户问题、AI 回复和状态。
- 通用/课程知识库检索资源。
- 学习路线、课程卡片和专家见解。
- Token 消耗、首 Token 耗时和总响应耗时。
- 反馈、停止、错误和 Dify 标识。
- 不展示聊天附件字段，因为本版本不支持聊天附件。

管理员支持按原始用户 ID 精确查询和按已保存名称模糊查询；原始用户 ID 只在服务端即时计算 HMAC，不持久化。

增加用户 AI 数据清除接口，删除该用户的会话、消息、摘要、画像、路线进度和缓存；不删除 PV/UV 聚合与必要审计日志。

### 4. 课程点击和日志

保留每日 PV/UV 聚合，不增加逐次事件表。

完善 `GET /internal/v1/admin/course-clicks`：

- 增加课程名称。
- 返回每日明细、按课程累计、查询范围总计。
- 支持课程和日期筛选。
- 不提供点击用户明细、排行榜和 Excel 导出。

继续提供后台事件日志、容器 JSON 日志和请求 ID 关联。

### 5. 临时 Streamlit

公网测试页只读：

- 风格配置。
- 知识库及文档状态。
- 上传批次状态。
- 会话审计。
- 课程统计。
- 日志和诊断。

不提供 Prompt 修改、上传、启停、替换、删除或保留策略修改按钮。管理写接口通过服务器内网命令和自动化测试验证。

验收完成后停止 UI 容器并移除 `/ai-management-test/` 临时 Nginx 入口。

## 五、小程序后端正式接口契约

### 用户接口

保留并正式定义：

- 三入口配置。
- 商业顾问聊天、停止、历史、消息、重命名、删除和反馈。
- 朋友圈、写作及停止生成。
- 课程签名跳转。

全部接口增加明确的 Pydantic 请求/响应模型和 OpenAPI 示例，禁止以无约束通用字典作为正式响应。

历史接口改为游标分页：

- 游标为不透明字符串。
- 默认 20 条，最大 100 条。
- 返回 `items` 和 `next_cursor`。
- 使用创建时间和唯一 ID 保证稳定排序。

### SSE 契约

每个事件统一包含：

- `schema_version`
- `request_id`
- `sequence`
- 事件业务数据

事件顺序：

1. 恰好一个 `request_started`。
2. 零个或多个 `status`。
3. 零个或多个 `retriever_resources`、`answer_delta`。
4. 可选 `learning_route`、`course_cards`、`expert_insight`。
5. 恰好一个终态：`message_end` 或 `error`。

停止生成通过 `message_end.status=stopped` 结束。终态之后不得再发送事件。

补充完整错误码、HTTP 状态、是否可重试及小程序后端处理规则。

### 重试与幂等

AI 服务本次不实现 `Idempotency-Key`：

- GET 查询可安全重试。
- 生成请求发送后，小程序后端不得自动重复提交。
- SSE 断开后先查询会话消息，确认是否已经落库。
- 无最终消息时由用户主动重新发起。
- 停止接口和相同反馈更新按已有资源状态处理。
- 文档明确残余风险：极端网络条件下仍可能重复调用模型。

小程序前端不得持有内部 Token、管理员 Token、Dify Key 或 Dataset ID。

### Dify 与知识库验收

- 更新三个用户应用 DSL 并执行契约测试。
- 执行 RAG 40 条和更新后的业务 E2E。
- 使用隔离测试知识库分阶段导入约 1000 万中文字符：
  1. 小样本验证格式、清洗和索引配置。
  2. 批量导入完整规模。
  3. 记录字符数、文件数、分段数、索引耗时、失败率和存储变化。
  4. 执行代表性检索和混合问题验证。
  5. 清理隔离测试知识库数据。

### 容量和故障

- 200 路模拟 Dify SSE 并发，验证服务自身连接、锁、内存和日志。
- 20 路真实 Dify 并发持续 10 分钟，记录首事件、首 Token、完成率和错误率。
- 同一会话只允许 1 路生成。
- Worker 处理中重启并验证任务恢复。
- 使用测试专用依赖代理对 AI 容器注入 PostgreSQL、Redis 和 Dify 超时/断连，不停止共享 Dify 基础服务。
- 验证数据库不可用、Redis 不可用、Dify 不可用、索引失败和外部删除补偿。
- 完成灰度、健康检查和回滚演练。
