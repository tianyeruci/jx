## 4. 未通过项与根因

## 4.1 课程跳转链路 `GET /r/{token}` 未跑通

### 现象

- `POST /internal/v1/business/chat` 的 `course` 用例和 `mixed` 用例都正常结束；
- 但都**没有返回** `course_cards` 事件；
- 因此拿不到 `course_cards[].redirect_url`；
- 也就无法完成：
  - `GET /r/{token}` 跳转验证；
  - “点击后 `course-clicks` 统计递增”的完整 E2E 验证。

### 证据

- `GET /internal/v1/admin/catalog` 返回：
  - `course_count=0`
  - `route_count=0`
- 服务器内直接查表结果：
  - `course_count=0`
  - `route_count=0`
- 但 `GET /internal/v1/admin/knowledge-bases/course/documents` 返回 `count=11`

### 根因

AI 管理服务的课程/路线推荐不是直接从 Dify 知识库文档列表发卡片，而是要经过本地 `Course` / `LearningRoute` 快照校验。

当前 `Course` 和 `LearningRoute` 本地表为空，`validate_recommendation()` 无法生成合法 `course_cards`，所以：

- 商业顾问接口本身能回答；
- 但不会发课程卡片；
- 也就不会有 `redirect_url`；
- 课程跳转链路自然无法跑通。

### 影响

明天小程序后端如果只接“普通问答”，不受此问题阻塞。  
如果要接“课程卡片点击跳转”，当前**不能宣称已跑通**。

## 4.2 批次状态接口 `GET /internal/v1/admin/knowledge-bases/{kb_code}/upload-batches/{batch_id}` 返回 500

### 现象

无论是：

- 成功上传样本批次；
- 失败上传样本批次；

调用该接口都返回 500。

### 服务器日志根因

根因已在 API 日志中确认：

```text
TypeError: Object of type datetime is not JSON serializable
```

触发链路是：

1. `knowledge_admin.upload_batch_status()`
2. 调用 `cleaning.get_cleaning_batch()`
3. `get_cleaning_batch()` 生成的 payload 中含 `updated_at` 等 `datetime`
4. `cache.set_json()` 内部直接执行：

```python
json.dumps(value, ensure_ascii=False)
```

5. 因没有 `default=str` 或预先序列化 `datetime`，最终抛出 500

### 影响

- 上传批次创建能成功；
- 文档上传、启停、删除也能工作；
- **但前端无法轮询上传批次状态**。

这会直接影响 AI 管理页的知识库上传体验。

## 4.3 失败文件重试接口 `POST /internal/v1/admin/knowledge-bases/{kb_code}/upload-batches/{batch_id}/files/{file_id}/retry` 返回 500

### 现象

本轮失败样本文件状态已经明确为：

- `status=failed`
- `stage=cleaning`
- `error_code=CLEANING_FAILED`
- `error_message=PDF不支持清洗入库：PDF读取失败:PdfStreamError`

也就是说，这个文件确实是一个“可用于重试接口测试”的失败文件。

但调用重试接口仍返回 500。

### 根因

不是“重试逻辑本身先失败”，而是路由 `retry_upload_file()` 在真正进入重试前，先调用了：

```python
payload = get_cleaning_batch(batch_id, session)
```

而 `get_cleaning_batch()` 又会命中 **4.2 同一个 datetime JSON 序列化错误**。

因此该接口被同一问题连带打坏。

### 影响

- 失败文件确实存在；
- 失败文件也确实可定位；
- 但前端目前**不能成功触发重试**。

## 5. 这轮测试里值得单独记下的坑

## 5.1 “接口 200” 不等于“业务链路跑通”

这轮里最典型的是：

- 商业顾问聊天接口本身是通的；
- 但由于本地课程/路线表为空，课程卡片链路没有真的跑起来。

所以后续验收要区分：

- 接口可调用；
- 接口有正确业务数据；
- 接口对应的完整链路可用。

## 5.2 知识库上传并不等于“上传批次状态接口也可用”

本轮已经证明：

- `POST upload-batches` 能通；
- `PATCH document status` 能通；
- `DELETE document` 能通；

但：

- `GET upload-batches/{batch_id}` 仍然会因为缓存序列化炸掉；
- `POST retry` 也会被同一个问题连带打坏。

所以知识库模块不能只测“上传成功”。

## 5.3 原样回写风格设置也会增加版本号

`PUT /internal/v1/admin/style-settings/{style_code}` 即使写回原值，也会让 `version += 1`。

这不是接口失败，但属于运维/测试时要知晓的副作用。

## 5.4 停止接口这轮只证明“能调”，没有充分证明“已中断”

本轮：

- 商业顾问 stop 返回 200；
- 工具 stop 返回 200；

但没有拿到足够强的证据证明“生成被及时中断，而不是刚好自然结束”。

因此这两条接口当前应标记为：

- **接口可调用：是**
- **中断效果已充分验收：否**

## 6. 建议的后续处理顺序（先修什么最值）

建议按这个顺序集中修复：

1. 修 `get_cleaning_batch()` / `cache.set_json()` 的 `datetime` 序列化问题  
   - 一次修复可同时恢复：
     - 批次状态查询
     - 失败文件重试

2. 补齐本地 `Course` / `LearningRoute` 数据  
   - 否则课程推荐卡片、`redirect_url`、课程点击 E2E 一直无法真正验收

3. 重新跑课程卡片与点击链路  
   - `business/chat` 返回 `course_cards`
   - `GET /r/{token}` 302
   - `GET /internal/v1/admin/course-clicks` 看到递增

4. 单独补做“stop 是否真的中断”的强证据测试  
   - 不能只看 stop 接口返回 200

## 7. 本次测试边界

- 本次只验证当前已部署 jx 环境，不代表本地开发环境或未来版本天然一致。
- 本次没有清理 Dify 知识库原有业务数据。
- 本次知识库上传/删除仅使用了 1 个临时成功文档和 1 个临时失败 PDF 样本。
- 本次测试的“失败样本 PDF”是为了验证失败链路，不代表真实业务文件。
