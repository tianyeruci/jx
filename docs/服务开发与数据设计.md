# 服务开发与数据设计

## 1. 边界

小程序后端是身份和会员权限的唯一判断方，通过 `X-User-Id` 传稳定用户 ID。AI 管理服务只校验 `X-Internal-Token`，再用 HMAC 生成本地 `user_hash` 和传给 Dify 的匿名 `user`。两个密钥必须不同。

服务是模块化单体，不建设独立 AI 网关、微服务、Prompt 平台、课程运营后台或动态清洗插件平台。模块边界用于方便测试和以后拆分，不意味着每个模块都要成为进程。

## 2. 运行组件

| 组件 | 责任 |
|---|---|
| API | FastAPI、SSE、商业对话、无状态工具、查询和上传入口 |
| Worker | 摘要画像、清洗入库、自动重试 |
| Scheduler | 7天数据清理、Dify 删除补偿、点击落库、卡住任务处理 |
| PostgreSQL | 会话、消息、画像、路线进度、课程和清洗事实 |
| Redis | 热数据缓存、会话锁、课程快照、Celery、点击统计 |
| Dify | 模型编排、知识检索、原生反馈和知识库 |

## 3. 商业对话链路

1. API 校验内部 Token 和稳定用户 ID。
2. 创建或校验本地逻辑会话，并获取 `ai:conversation-lock:{id}`。
3. 保存用户消息和待生成助手消息。
4. 构建 `画像 → 路线进度 → 摘要 → 摘要游标后的最近消息`。
5. 当天已有 Dify 段时复用其 `conversation_id`；跨日创建新段。
6. 每轮把本地上下文作为普通 `inputs` 调用 Chatflow。调用者不能传 Dify 会话 ID或覆盖上下文。
7. 转发回答增量、引用和状态；保存 Dify task/message/conversation ID、耗时和 Token。
8. 解析推荐决策节点的候选 JSON，用课程快照校验 ID、启用/审核状态、路线引用和当前阶段。
9. 由服务生成课程卡片、路线对象和签名跳转链接。
10. 达到摘要阈值后异步调用摘要画像 Workflow。

Dify Chatflow 的 LLM 节点没有开启 Memory。会话 ID 只用于 Dify 的会话归属、反馈和停止等原生能力，真正传给模型的历史由本服务控制。

## 4. 摘要与画像

达到 6 个未摘要用户轮次或约 6000 个中文字符时触发。Worker 记录旧摘要、旧游标和目标消息；写回时再次比较，旧任务不得覆盖已经前进的摘要。

画像只有商业画像：

- `confirmed`：有用户消息 ID 和连续原文证据的明确事实。
- `candidates`：推断、弱线索、冲突事实或路线进度候选。

即使 Workflow 错把无证据对象放进确认更新，服务也会降级为候选。已有确认事实与新值冲突时不自动覆盖。

## 5. 7天规则

- 活跃会话：凌晨删除超过7天的原始消息，摘要保留。
- 清理前会尝试把尚未摘要的旧消息纳入摘要；失败时标记 `summary_gap`，仍按保留规则删除原文。
- 连续7天没有活动的逻辑会话：删除会话、消息、摘要和所有 Dify 段；画像及其他路线进度不删除。
- Dify 没有公开的指定消息删除 API，因此使用按自然日分段；Dify 内的实际保留允许比7天多不足24小时。
- 删除 Dify 失败只进入补偿任务，不阻塞本地删除。

## 6. 课程、路线和进度

课程事实存 PostgreSQL，Redis 保存完整当前快照。模型只返回候选 ID：

- 卡片只包含启用且审核通过的课程。
- 正式链接始终从课程事实读取，模型输出的链接不会透传。
- 商业回答流会过滤模型正文中的 URL；可点击地址只通过课程卡片或检索引用提供。
- 路线中有不存在、停用或未审核课程时，整条路线不返回。
- 路线推荐只展示当前阶段的候选课程。
- 用户明确选择路线后创建进度；只有明确完成或跳过当前阶段，并提供当前输入原文证据时才推进。
- 点击卡片只统计，不改变学习进度。

课程发布先写 Dify 并确认索引和分块，再提交数据库事实和 Redis 快照。失败时清理本次新建的 Dify 文档，不发布半套目录。

## 7. 数据库表

迁移包含：

- `business_profile`
- `business_conversation`
- `business_conversation_segment`
- `business_message`
- `learning_route_progress`
- `course`
- `learning_route`
- `course_click_daily`
- `cleaning_batch`
- `cleaning_file`
- `cleaning_document`
- `external_deletion_task`

摘要直接保存在会话表。反馈使用 Dify 原生接口，因此没有反馈表；清洗策略是代码，因此没有策略表；首版没有 Outbox 和课程版本表。

## 8. Redis 一致性

- 画像、摘要、路线进度以 PostgreSQL 为准，写库后删除缓存。
- 课程快照用临时 Key 构建后原子替换。
- 缓存不可用时业务查询回源数据库。
- Redis RDB/AOF 不是核心事实的唯一持久化。
- 点击是允许少量误差的统计例外，凌晨写日汇总。

## 9. 已知部署前门禁

当前代码和离线测试不能代替以下真实环境验证：

- Dify 1.13.3 导入、模型插件安装和四个应用发布。
- 两个知识库真实 Dataset ID 绑定。
- 同一 `conversation_id` 后续普通 inputs 的实际更新行为。
- 流式、停止、反馈、会话删除、索引状态、父子分段和 Metadata。
- 模型供应商 RPM、TPM 和并发额度。
