# 小程序后端私网联调网络配置与验收记录

> 日期：2026-07-30  
> 环境：jx AI 管理服务  
> 范围：小程序后端到 AI 服务的私网回程路由、Docker 发布端口来源限制、服务器侧业务回归和回滚演练

## 1. 结论

服务器侧网络配置已经完成并验证：

- AI 服务继续绑定宿主机私网 TCP `8000`，应用容器仍加入 Dify 的 `docker_default` 网络。
- 小程序后端单主机地址使用 `/32` 精确路由经 `eth0` 和私网网关返回，不再命中 jx 的 Docker 默认网段。
- Docker `DOCKER-USER` 仅允许该小程序后端来源访问宿主机私网 TCP `8000`，其他从 `eth0` 进入的同目标流量被拒绝。
- 路由和防火墙配置均已持久化，实际撤销并恢复后状态一致。
- AI 健康、入口配置和商业顾问 SSE 通过；合成测试数据已精确清理。

本记录不把服务器本机回归等同于小程序后端真实端到端验收。调用方主机发起测试和云安全组核对仍需完成。

## 2. 修改前事实

- AI 服务、数据库、Redis 和 Dify 依赖均健康。
- API 已正确绑定宿主机私网地址的 TCP `8000`，无需修改 `.env` 或重建容器。
- SSH 主机 `eth0` 的私网地址与 AI 服务目标一致；TCP `8000` 的唯一宿主机监听者是 AI API 对应的 Docker 端口代理，唯一发布该端口的容器为 Compose `api` 服务，容器内进程为 `uvicorn ai_management.main:app --port 8000`，不存在其他服务争用。
- jx 的 `docker0` 使用 `172.17.0.0/16`，与小程序后端地址重叠；系统把回程流量发往 `docker0`。
- Docker 已为私网 TCP `8000` 创建端口转发，`DOCKER-USER` 当时没有来源限制。
- UFW 已启用且默认拒绝入站，但 Docker 转发链在 UFW forward 链之前处理，不能只依赖普通 UFW 入站规则约束该发布端口。

## 3. 实施内容

### 3.1 精确路由

- 新增独立 Netplan 文件：`/etc/netplan/60-ai-backend-route.yaml`。
- 为小程序后端增加 `/32` 路由，经 jx 私网网关从 `eth0` 返回。
- `netplan generate` 通过，生成的 systemd-networkd 配置包含该目标。
- 当前路由查询确认目标经私网网关和 `eth0`，源地址为 AI 服务器私网地址。

### 3.2 Docker 端口来源限制

- 新增脚本：`/usr/local/sbin/ai-management-private-firewall`。
- 新增并启用服务：`ai-management-private-firewall.service`。
- 服务在 Docker 启动后向 `DOCKER-USER` 安装专用链：
  - 允许小程序后端单主机来源访问宿主机私网 TCP `8000`；
  - 拒绝其他从 `eth0` 进入、原始目标为该私网 TCP `8000` 的流量。
- 规则使用连接跟踪的原始目标地址和端口，不依赖可能随容器重建变化的容器 IP。

### 3.3 未修改项目

- 未修改 AI 服务 `.env`、Token、镜像、应用代码、数据库、Redis 或 Dify 数据。
- 未重启 Docker、Dify、API、Worker 或 Scheduler。
- 未修改公网 `80/443` 和课程跳转路由。
- 未修改阿里云安全组。
