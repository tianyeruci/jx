## 2. DIFY-01：重新发布 DSL 后应用访问 Key 漂移

### 现象与影响

三个 DSL 重新导入并发布后，AI 管理服务配置中的旧应用访问 Key 不再对应当前 Dify 应用。若继续调用，会使应用参数读取或真实调用失败，不能把“DSL 已发布”误认为“服务已接入新应用”。

### 根因

`app-...` 是 Dify 的**应用访问 Key**，不是可公开写入文档的应用 UUID。将 DSL 重新导入为新应用或重新创建应用后，AI 服务的 `.env` 中对应 Key 不会自动更新；Dify 的普通发布动作本身不一定轮换 Key，但也不会替 AI 管理服务验证或同步映射。

### 本次处理

1. 先备份 AI 管理服务 `.env`，备份目录：`/opt/ai-management/backups/20260728-214753-app-key-sync`。
2. 在 jx 服务器内，从 Dify 的受控应用 Token 数据查询当前三个用户入口对应的 Key；不在终端、日志或文档中显示 Key。
3. 仅更新 AI 管理服务中三个用户入口的 Key，并强制重建 `api`、`worker`、`scheduler`；不修改 Dify 数据库业务数据和知识库数据。
4. 分别请求三个入口的 Dify `/parameters`，均得到 HTTP 200。
5. 后续重新导入并发布 `business_advisor.yml` 与 `summary_profile.yml` 后，再次备份 `.env` 至 `/opt/ai-management/backups/20260729-004456-app-key-sync`，仅同步商业顾问与摘要画像两个 Key，并重建 `api`、`worker`、`scheduler`。
6. 同步后以容器内当前配置验证 `/health/live`、`/health/ready`、商业顾问 `/parameters` 与摘要画像 `/parameters`，均成功。

### 下次预防与验证

- 只要发生“重新创建应用、导入 DSL、重新发布、轮换 Key”任一操作，都把“核对 AI 服务 Key 映射 + 三入口 `/parameters` 验证”列为发布必做项；映射变化时再同步和重建服务。
- 将 `app-...` 视为密钥：只存在服务器 `.env` 或受控密钥系统；文档仅记录应用别名、更新时间、验证状态和备份目录。
- 不要把 Dify 应用 UUID、应用名称和应用访问 Key 混用。小程序前端和小程序后端均不得持有这些 Key。

## 3. DIFY-02：Code 节点调用 Sandbox 返回 401

### 现象与影响

商业顾问工作流中，问题拆分节点成功后，`query_split_normalize` Code 节点失败；Dify 运行记录显示 Sandbox 服务返回 HTTP 401。下游分类、检索和回复无法继续。

### 根因

Dify API 使用的 `CODE_EXECUTION_API_KEY` 与 Sandbox 使用的 `SANDBOX_API_KEY` 不一致。二者必须是同一值；两者不一致时，Dify API 无法授权调用 Sandbox。

### 本次处理

1. 只对两个 Key 做不可逆散列后的比对，不输出任何原值。
2. 先备份 Dify 配置，备份目录：`/opt/ai-management/backups/20260728-215046-dify-sandbox-key-sync`。
3. 使 `SANDBOX_API_KEY` 与 `CODE_EXECUTION_API_KEY` 保持一致。
4. 仅强制重建 Dify `sandbox` 服务；未重启或删除 Dify PostgreSQL、Redis、API、Web、知识库或卷。
5. 再次比对两个 Key 的哈希，结果一致；随后 Code 节点已能执行。

### 下次预防与验证

- Dify 升级、迁移 `.env`、从备份恢复或轮换代码执行密钥后，必须进行该项哈希一致性预检。
- 401 先检查“API 到 Sandbox 的内部鉴权”，不要先怀疑知识库、模型或 AI 管理服务。
- 修改前必须备份 Dify `.env`；如果 Sandbox 重建后健康异常，恢复该备份并只重建 Sandbox。

## 4. DIFY-03：商业顾问 Workflow 分支变量缺失（已修复并已验证）

### 现象与影响

修复 Sandbox 后，商业顾问 Workflow 的问题拆分、分类和通用知识检索可以成功执行，但流程没有正常产生 `message_end`。Dify 运行记录显示决策节点失败，典型错误为：

```text
Variable #general_knowledge_mixed.result# not found
```

修复前，因此不能把商业顾问的真实 Dify 流程、混合检索、推荐决策或 SSE 全链路标记为验收通过。朋友圈和日常写作的应用参数可达不代表商业顾问这条链路完整通过。

### 根因

`business_advisor.yml` 的分类器只执行一个分支，但共用的 `recommendation_decision` 和最终回答节点同时引用了三个检索分支的变量：通用知识、混合问题通用知识、课程路线知识。未被本次分类路径执行的节点没有输出变量，Dify 不会为其提供空值，导致流程在分支汇合处失败。

### 本次本地修复

不能用“假定未执行变量为空”的提示词技巧掩盖问题。已改为分支局部链路，使每个节点只引用本分支已经执行的变量：

```text
通用问题：分类 → 通用检索 → 通用决策 → 通用回答
课程问题：分类 → 课程检索 → 课程决策 → 课程回答
混合问题：分类 → 混合通用检索 → 混合课程检索 → 混合决策 → 混合回答
```

混合分支已使用独立的课程检索节点 `course_knowledge_mixed`，避免共享节点接收多个上游分支后产生不确定的下游触发。三条分支的决策输出保持同一 JSON 契约，AI 管理服务可继续沿用现有解析逻辑。

### 当前验证边界

- **本地已验证**
  - `business_advisor.yml` 可通过 YAML 解析；
  - `general / course / mixed` 三条分支的回答节点只引用各自分支已执行的检索变量；
  - AI 管理服务的推荐决策解析逻辑不依赖固定节点 ID，只要求输出里存在约定 JSON。
- **服务器侧已验证**
  - 已重新导入修正后的 DSL，并完成发布；
  - 已重新绑定既定测试知识库；
  - 使用隔离测试用户 `dsl-verify-20260728-fb68dc87` 覆盖通用、课程、混合三类问题；
  - 三次请求都收到 `message_end`，无 `error` 终态；
  - 发布后最近 15 分钟 `api/worker/scheduler` 日志中，`Variable #... not found`、`Traceback`、`SUMMARY_FAILED`、`DIFY_UNAVAILABLE` 命中均为 0。

### 完成条件

1. 在本地修正 DSL，校验 YAML 和节点连接关系。
2. 导出当前 Dify 已发布版本并留存哈希/时间，再导入修正 DSL、绑定既定测试知识库并发布。
3. 用隔离测试用户分别覆盖通用、课程、混合三类问题；每次都必须收到最终 `message_end`，不得出现未定义变量、Code 节点 401 或 Workflow 失败。
4. 验证 SSE 的推荐决策、课程卡片、停止/反馈、后台日志和课程 PV/UV；保存脱敏的 request ID、运行时间和结果。
5. 上述证据齐全前，发布记录只能写“应用参数可达”，不得写“商业顾问 Dify E2E 已通过”。

### 回退原则

该问题位于 Dify DSL 逻辑，不应通过手工改 Dify 数据库解决。导入新 DSL 前保留当前发布版本的导出件；若新版本失败，直接在 Dify 控制台恢复上一已发布 DSL，再重新验证应用参数和最小对话。

## 5. DIFY-04：摘要画像 Workflow 输出 JSON 稳定性不足（已修复并已验证）

### 现象与影响

`summary_profile.yml` 原先把 `llm.text` 直接作为 `end.result` 输出。只要模型在 JSON 前后多说一句解释、包一层 fenced code block，或缺少某个数组字段，Worker 就可能把本轮摘要任务判为“输出格式无效”，从而重试或失败。

### 根因

当前服务端虽然已有 `extract_json_object` 容错，但原 DSL 没有在 Dify 内部先做一次结构归一化，导致：

- Dify 节点日志里看到的是原始漂移输出，不利于定位；
- 轻微格式漂移直接传给 Worker，异步任务稳定性受模型表现波动影响；
- `target_message_id` 只能依赖模型“听话原样返回”，而不是由工作流强制回填。

### 本次本地修复

已在 `summary_profile.yml` 中新增 `summary_normalize` Code 节点，位于 `llm -> end` 之间，执行逻辑为：

1. 优先解析纯 JSON；
2. 兼容 fenced JSON；
3. 兼容前后多余文本中的首个 JSON 对象；
4. 为 `confirmed_profile_updates`、`candidate_profile_updates`、`route_progress_candidates` 提供默认空数组；
5. 强制用 `start.target_message_id` 回填最终 `target_message_id`；
6. 若完全无法提取 JSON，则保留原始文本作为 `updated_summary` 的兜底值，并返回空候选数组。

### 当前验证边界

- **本地已验证**
  - `summary_profile.yml` 可通过 YAML 解析；
  - 新增 Code 节点对 4 类输入样本都能返回可解析 JSON：
    - 纯 JSON；
    - fenced JSON；
    - 前后带说明文字的 JSON；
    - 完全未成型的普通文本。
- **服务器侧已验证**
  - 已重新导入并发布 `summary_profile.yml`；
  - 使用当前 AI 服务配置直接调用摘要画像 Workflow；
  - `outputs.result` 可被解析为 JSON 对象；
  - `target_message_id` 已正确回填为 `msg-2`；
  - `confirmed_profile_updates`、`candidate_profile_updates`、`route_progress_candidates` 均保持数组结构。

### 下次预防与验证

- 只要 Workflow 输出将被后端代码当成结构化 JSON 消费，默认采用 `LLM -> Code 归一化 -> End`，不要直接把 `llm.text` 暴露给下游。
- `target_message_id`、任务游标、状态码等关键字段，尽量由流程变量强制回填，不依赖模型“原样复述”。
- 摘要类内部任务优先保证稳定和可恢复，再追求提示词最简。

## 6. 发布与测试工具类问题

### TOOL-01：Windows pytest 清理 SQLite 时被残留进程占用

**处理**：先列出命令行中明确包含 `-m pytest` 且工作目录属于 `jx-now` 的 `python.exe`，人工确认 PID 后逐个结束，再重跑。绝不批量结束所有 Python 进程，也不删除无法确认归属的 `.db` 文件。

**证据边界**：本次重新执行的完整测试曾因该锁和工具时间窗口受限，不能把历史 `43/43` 写成新的完整测试结果。

### TOOL-02：wheel 构建入口冲突

**处理**：当 `python -m build --wheel` 报 `build.__main__` 不可用或类似模块冲突时，使用：

```powershell
python -m pip wheel --no-deps --no-build-isolation --wheel-dir dist .
```

随后对实际 wheel 做 SHA256，并在上传前后核对一致。不要为修复构建临时问题而把本机虚拟环境目录或构建缓存提交到仓库。

### TOOL-03：测试客户端的中文 HTTP Header

HTTP 请求头不是传递中文显示名的可靠通道，Python 标准库 `urllib` 还会在发送非 Latin-1 值时直接报错。

**处理**：`X-User-Name` 仅作为可选展示字段；自动化测试默认不传，或使用 ASCII 合成名称。`X-User-Id` 必须稳定且由小程序后端保存/传递，服务端以它进行身份和会话归属判断。

### TOOL-04：Windows PowerShell 远端 heredoc 的结束标记失效

本次在 Windows PowerShell 下，把带 CRLF 的 heredoc 直接传到远端 `bash` / `python` 时，出现过结束标记 `PY` 未被正确识别、脚本主体已执行但尾部额外报错的情况。

**处理**：

- 优先把完整脚本通过标准输入管道传给远端解释器：
  - `@'...shell...'@ | ssh jx bash -s --`
  - `@'...python...'@ | ssh jx \"cd /opt/ai-management && docker compose ... exec -T api python -\"`
- 如果只是做统计或简单校验，改用单行 `python -c`，避免 heredoc 结束标记受 CRLF 影响。

## 7. 下次联调最小检查清单

1. 导入/发布 DSL 后，先确认每个应用绑定的是隔离测试知识库，再同步受控 Key，逐一验证 `/parameters`。

7. 每次更新本文件时标注“已修复 / 待验证 / 待修复”，避免把局部恢复误写成全链路通过。
