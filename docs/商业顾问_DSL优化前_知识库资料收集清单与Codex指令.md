# 商业顾问 DSL 后续优化：知识库资料收集清单 + Codex 执行指令

> 目的：**只收集后续优化 DSL 所需要的真实知识库资料。当前阶段不修改 DSL、不调参数、不重构工作流、不提出最终优化方案。**
>
> 适用范围：Dify 1.13.3「商业顾问」当前 DSL，重点关注三类知识：
>
> 1. 活动（`record_type = event`）
> 2. 方法论（`record_type = methodology`）
> 3. 咨询案例 / 咨询会议总结（`record_type = consulting_case`）
>
> 收集原则：以“知识库里实际存了什么、清洗流程实际生成了什么”为准，不先假设字段应该怎么设计。

---

# 一、为什么当前阶段先收集这些资料

当前 DSL 已经直接依赖知识库中的若干 metadata 和正文检索结果。

例如当前 DSL 对三类资料已有明确假设：

- 活动：
  - `record_type = event`
  - 读取 `event_status`
  - 读取 `event_start_ts`
  - 读取 `event_end_ts`
  - 读取 `registration_start_ts`
  - 读取 `registration_deadline_ts`
  - 读取 `registration_url`
  - 读取 `source_title`
  - 读取 `event_id`
  - 读取 `delivery_mode`
  - 读取 `city`
  - 读取 `activity_summary`
  - 读取 `source_status`
- 方法论：
  - 至少依赖 `record_type = methodology`
  - 其余内容主要依靠正文 / chunk 语义检索
- 咨询案例：
  - 至少依赖 `record_type = consulting_case`
  - 其余内容主要依靠正文 / chunk 语义检索

因此，现在最需要确定的是：

> **真实知识库的清洗流程、最终正文、chunk、metadata 字段、字段类型和值，到底是什么。**

如果这些事实不明确，继续修改 DSL 很容易建立在错误假设上。

# 三、第一类：活动资料需要收集什么

## 3.1 必须提供：活动入库前的原始资料样本

至少提供 3～5 条真实活动样本。

最好覆盖：

1. 正常、正在报名；
2. 正常、未来才开始报名；
3. 延期；
4. 取消；
5. 已完成；
6. 如果有，再补一条字段不完整的异常样本。

每条原始活动至少说明：

```text
原始资料来源：
原始标题：
原始正文：
原始发布时间：
原始活动时间：
原始报名开始时间：
原始报名截止时间：
原始状态：
原始报名链接：
```

如果原文中没有某项，不要补造，直接写“无”。

---

## 3.2 必须提供：活动清洗规则 / 清洗提示词 / 清洗代码

需要把“原始活动资料 → 入库记录”的实际处理方式给出来。

至少包括：

```text
1. 活动资料由什么程序 / Prompt 清洗？
2. 清洗 Prompt 的完整内容是什么？
3. 如果是代码处理，涉及哪些关键函数？
4. 状态字段是如何生成的？
5. 活动开始 / 结束时间是如何提取的？
6. 报名开始 / 截止时间是如何提取的？
7. 时间最后保存成什么格式？
8. 时区如何处理？
9. 空字段如何处理？
10. 延期、取消、已完成如何判断？
11. 一个活动会生成一条记录还是多条记录？
12. 更新活动时，是覆盖旧记录还是新建一条？
```

如果是自动化流程，例如：

```text
抓取
→ LLM 清洗
→ Python 标准化
→ metadata
→ Dify 入库
```

请把每一步的输入输出说明出来。

---

## 3.3 必须提供：活动最终清洗后的正文

这里不是原始活动正文，而是**真正存入 Dify、用于向量检索的正文**。

每条样本都要提供：

```text

```

如果 Dify 又把正文切成多个 chunk，还要继续提供：


重点不是文档看起来是否完整，而是：

> 用户问“最近有什么活动”“XX 活动怎么报名”时，向量检索实际看到的文本是什么。

# 四、第二类：方法论资料需要收集什么

当前 DSL 对方法论的 metadata 假设比较少，只明确使用：

```text
record_type = methodology
```

所以方法论资料的重点不是“列很多假想字段”，而是确认：

> **方法论最后存入知识库的正文到底是什么，以及用户问题实际拿什么文本进行语义匹配。**

---

## 4.1 必须提供：方法论原始资料样本

至少 3 条。

建议覆盖：

1. 产品 / 产品结构；
2. 定价；
3. 营销 / 获客 / 转化；
4. 如果实际知识库还有经营、管理等，再加 1～2 条。

每条提供：

```text
原始资料标题：
原始资料来源：
原始正文：
```

如果原始文档很长，不一定发全文。

但至少要覆盖：

```text
开头
核心方法
关键步骤
案例 / 示例
结论
```

---

## 4.2 必须提供：方法论清洗规则

需要知道方法论入库前有没有做：

```text
摘要
重写
去口语
结构化
标题生成
标签生成
知识点拆分
问答生成
```

需要提供：

```text
清洗 Prompt：
清洗代码：
输出格式：
```

如果完全没有清洗，也明确说明：

> 原文直接进入 Dify。

---

## 4.3 必须提供：最终入库正文和 chunk

每条方法论至少提供：

```text
最终文档标题：
最终正文：
Dify chunk 1：
Dify chunk 2：
...
```

需要重点观察：

- 用户会搜索的关键词是否存在于 chunk；
- 方法论名称和适用场景是否被切散；
- 一个 chunk 是否只有结论，没有问题背景；
- 一个 chunk 是否过长或过短；
- 标题是否会参与检索。

当前阶段只收集，不做判断结论。

---

## 4.4 必须提供：方法论完整 metadata

当前 DSL 已知必须有：

```text
record_type = methodology
```

除此之外，把实际存在的全部字段给出来。

尤其如果已有以下字段，必须保留：

```text
topic
category
methodology_type
applicable_scenario
business_stage
industry
product_type
source_title
source_id
version
updated_at
```

**如果没有，不要新增。**

我们现在的目标是知道真实 schema。

---

## 4.5 建议提供：每条方法论“它本来应该回答什么问题”

不是为了现在调 DSL，而是帮助理解这条资料的检索语义。

例如：

```text
方法论：
价值定价

它应该被哪些问题找到：
- 我的会员产品怎么定价？
- 9800 和 12800 哪个价格更合适？
- 怎么判断客户愿意付多少钱？
```

每条列 3～5 个即可。

这个信息后续判断“知识库正文是否保留了足够检索语义”很有价值。

## 5.3 必须提供：清洗后的咨询案例正文

2. 定价；

每条提供：

需要保留案例正文实际结构。

例如实际是：


就原样给。

如果实际只是连续文本，也原样给。

## 5.4 必须提供：咨询案例最终 metadata



## 5.5 必须确认：结果和建议有没有被混淆

这一项特别重要。

请确认咨询案例清洗时：

```text

```

和：


是不是分开的。

需要给真实样本确认是否可能出现：

> 顾问在会上建议“预计提升转化率”

> “最终转化率提升”

如果清洗阶段已经混在一起，后续 DSL 很难靠 Prompt 完全修复事实边界。

当前阶段只收集这个事实，不修改流程。

# 七、哪些资料是“必须”、哪些是“最好有”

## P0：必须提供

没有这些，后续 DSL 优化仍然会依赖猜测。

### 活动

- 3～5 条原始活动；
- 活动清洗 Prompt / 代码；
- 清洗后的最终正文；
- Dify 实际 chunk；
- 完整 metadata；
- 状态枚举；
- 四类时间字段的定义、类型、单位、时区；
- 真实 Dify Retrieval Result 1～2 条。

### 方法论

- 3 条原始方法论；
- 清洗方式；
- 最终正文；
- 实际 chunk；
- 完整 metadata。

### 咨询案例

- 3～5 条咨询会议 / 案例样本；
- 总结 / 清洗 Prompt；
- 最终案例正文；
- 实际 chunk；
- 完整 metadata；
- 一场会议如何变成案例的规则。

### 全局

- Dataset 数量和三类资料分别在哪；
- metadata 是文档级还是 chunk 级；
- `record_type` 全部实际枚举。

这些会明显提高后续判断质量：

- 活动字段为空的异常样本；

# 十、给 Codex 的任务边界

这一阶段 Codex 的职责只有：

> **帮我们从项目代码、清洗 Prompt、配置文件和样本中，把上述资料收集齐并整理出来。**

不是让 Codex 优化 DSL。

Codex 当前不能：

- 修改 DSL；
- 修改知识库 schema；
- 修改清洗逻辑；
- 调检索参数；
- 给出最终 DSL 优化方案；
- 重构项目。

Codex 可以：

- 找到活动清洗代码；
- 找到方法论入库代码；
- 找到咨询会议总结 / 案例清洗代码；
- 找到 Prompt；
- 找到 metadata schema；
- 找到字段生成规则；
- 抽取脱敏真实样本；
- 整理成 Markdown / JSON；
- 标记缺失资料；
- 标记代码与实际数据之间明显不一致的地方，但暂不修复。
