# 部署、备份、回滚与常见故障

当前完整发布、备份和回滚流程见 [V2 从开发到服务器部署与回滚手册](V2从开发到服务器部署与回滚手册.md)。只修改 `ai_management/` 并希望快速刷新测试页时，见 [jx 快速代码测试部署操作手册](jx快速代码测试部署操作手册.md)。`本地到线上部署联调实战手册.md` 仅作为历史排坑参考。

## 2026-08-03 当前安全状态

本次 OCR 方案导致 jx 主机出现内存压力、Swap 抖动和磁盘 I/O 阻塞。OCR worker、OCR timer、OCR 镜像构建和 OCR 大包传输目前全部暂停。服务器已恢复，但 Dify/ai-management 核心服务不得通过本次排障重启、重建或清理数据。

后续任何大文件传输或构建前，先执行：

```bash
bash /opt/ai-management/scripts/jx_resource_guard.sh check --phase=preflight
```

检查失败时停止本次任务；不要执行无速率限制的 `scp -r`，不要并行传输/构建，不要执行 `docker system prune` 或删除 Docker 持久卷。

## 部署

1. 使用独立 PostgreSQL 数据库或 Schema。
2. Redis 使用独立 DB 或确保 `ai:` Key 前缀不冲突。
3. `.env` 不提交 Git；四个 App Key 和知识库 Key 分开配置。
4. 执行 `alembic upgrade head`。
5. 启动 API、Worker 和 Beat。
6. 测试环境可加 `--profile test` 启动 Streamlit：

   ```powershell
   docker compose -f docker-compose.ai.yml --profile test up -d --build
   ```

当前 jx 测试环境复用 Dify PostgreSQL 容器中的独立 `ai_management` 数据库，并使用 Dify Redis 的隔离 DB 5；AI 上传文件仍使用精确卷 `ai-management_ai_uploads`。不要按旧结构假设 Compose 会创建独立 PostgreSQL/Redis，更不能执行 `down -v` 或整库 Redis 清理。

### OCR 按需运行时（当前暂停）

jx 的扫描 PDF OCR 不使用核心 API/普通 Worker 镜像内的在线安装，而使用 `jx-now-ai-management-ocr:<release-id>` 离线镜像。上述是后续设计目标；当前必须保持 `PDF_OCR_ENABLED=false`，不构建或启动 OCR 镜像/worker/timer。恢复前必须重新确认资源门禁、传输完整性、镜像构建上下文和服务隔离。

发布前除 `.env`、数据库/Redis、上传卷、Dify 存储和旧镜像外，还要保留 OCR 镜像 ID、离线锁文件、模型 manifest、systemd service/timer 和 `var/reports/v2/<release-id>-deploy/`。回滚时恢复 `.env`、Compose、旧镜像和 systemd 文件；不删除未确认归属的 `var/ocr-runtime`、旧 OCR 镜像或上传卷。已确认属于本次失败传输的、不完整 OCR 临时目录，必须先留存大小/哈希/进程证据，再只清理精确目录。Worker 启动失败只允许保持任务排队并报警，不能用手工清 Redis 或删除文件“修复”。

## 网络和鉴权

- 安全组只允许小程序后端和运维入口访问 API。
- 即使同一 VPC，也必须使用 `X-Internal-Token`。
- 小程序前端不得获得 Dify Key、内部 Token 或真实 Dataset ID。
- `/r/{signed_token}` 是例外公开入口，只能跳转当前已启用审核课程。
- 知识库管理接口不经 Dify 临时 `/ai-service/` 桥接。调用方 `172.17.28.83` 只访问 jx 私网 `172.30.157.197:8000`，同时使用 `X-Internal-Token`/`X-Admin-Token`；主机防火墙和阿里云安全组仅允许此精确 `/32`。Dify 上传路径的 `403` 阻断规则保持不变。执行与回滚命令见 [V2 部署回滚手册 5.2](V2从开发到服务器部署与回滚手册.md#52-私网-8000-直连知识库管理接口) 和 [DEPLOY-022](troubleshooting/deployment.md#deploy-022知识库管理接口应走私网-8000-直连而非-dify-网关)。

## 备份

- PostgreSQL：上线前备份；至少每日备份会话、画像、课程和清洗状态。
- Redis：可以开启 RDB/AOF，但恢复业务事实仍以 PostgreSQL 为准。
- Dify：备份应用 DSL、Prompt、知识库源文件和 Dify 自身数据库/对象存储。
- 临时上传文件不是长期备份；成功立即删、失败24小时删。

## 回滚

- 应用：保留上一镜像，回滚 API、Worker 和 Scheduler 到同一 build。
- 数据库：只使用已经验证的 Alembic downgrade；不运行 `git reset --hard` 或直接删表。
- Dify：保留上一版导出的 DSL；应用回滚与 API Key 无需更换，但 Prompt/变量必须与服务版本匹配。
- 课程：首版没有一键课程版本回退。发布前保留上一份 Markdown；需要回退时以原稳定 ID 重新发布上一份资料。

## 常见故障

### `/health/ready` 返回 503

查看返回的 `database`、`redis` 和 `dify_apps_configured`。开发环境允许 Redis 不可用时进程继续，但生产不允许。

### 会话一直 409

Redis 锁默认有 TTL。先确认是否仍有生成任务，不要直接删除所有 Redis Key；只检查对应 `ai:conversation-lock:{id}`。

### 清洗一直 processing

确认 Worker 正在监听 `cleaning` 队列。凌晨任务会把超过1小时的任务自动重试一次，第二次仍失败改成终态。需要立即处理时可使用单文件重试接口。

### 扫描 PDF 提示 OCR 已禁用

先核对脱敏配置回读：`PDF_OCR_ENABLED`、`AI_OCR_IMAGE`、模型根目录和 manifest 路径；再查看 `systemctl status jx-ocr-autoscaler.timer`、`journalctl -u jx-ocr-autoscaler.service` 和 OCR 镜像启动日志。若模型校验、Paddle 导入或共享库检查失败，保持 OCR 关闭并让任务进入复核/失败；不要在运行容器内临时 `pip install`。按完整部署手册重新生成/上传离线包并构建 OCR 镜像。

### Dify HTTP 成功但文件失败

这是正常的失败判断：创建成功不等于索引成功。查看阶段是 `dify_indexing`、`metadata` 还是零分块。

### 历史课程推荐正文提到课程但没有卡片

该故障仅适用于 ADR-036 前的课程推荐链路。当前商业顾问新聊天不生成候选 JSON、课程卡片或路线状态；若新 SSE 出现相关事件，应视为回归并核对已发布 Dify 应用与服务版本。
