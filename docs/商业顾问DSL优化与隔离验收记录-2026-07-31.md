# 商业顾问 DSL 优化与隔离验收记录（2026-07-31）

## 1. 范围与已确认约束

本轮只优化商业顾问 DSL，不改变小程序/AI 管理服务输入、输出或其他功能：

- 使用独立 Dify 测试应用做 A/B，不替换当前生产应用；
- 保留现用 DSL 的全部 Start 输入、后端消费的 `decision_json` 语义、环境变量名和知识库绑定；
- 保留 `qwen-plus` 与 `qwen3-rerank`，不把更换模型或召回器混入本轮变量；
- “3000～5000”按活跃用户理解，不错误等同于同时请求数；
- 最低运行态压力验收为 20 个不同会话持续 10 分钟；
- 准确率是硬门槛：固定场景 0 次 LLM，正常请求最多 2 次计划内 LLM，仅格式错误允许 1 次显式修复。

会话状态仍由 AI 管理服务注入。根据 ADR-004，本轮不引入 Dify Conversation Variables，也不让 Dify 与服务端形成双状态源。

## 2. 审计结论

### 2.1 三个版本的事实差异

| 版本 | 固定路径 | 正常路径 | 格式失败路径 | 关键判断 |
|---|---:|---:|---:|---|
| `dify/dsl/business_advisor.yml` | 无完整快速路径 | 约 4 个模型型节点 | 未形成同等显式门禁 | 适合作为仓库历史基线，不是本轮直接优化起点 |
| `dify/商业顾问（当前使用版本）.yml` | 0 LLM | 2 LLM | 3 LLM | 已有确定性快速路由、证据压缩、JSON 门禁与显式修复，是当前最可靠起点 |
| `dify/商业顾问_优化版_Dify-1.13.3.yml` | 0 LLM | 2 LLM | 节点重试可能额外放大 | 改了环境变量名，移除了当前版的证据压缩和格式门禁，直接喂原始检索结果；不适合整份替换 |

因此，“其他智能体优化版”并不比现用版本全面更优。若直接替换，可能造成外部配置不兼容、上下文膨胀、格式错误失去显式修复，以及隐藏重试放大尾延迟。

### 2.2 外部案例中实际采用的经验

- 跨境电商案例：采用“确定性固定场景前置分流”和“只检索相关分支”；没有照搬宽泛关键词、硬编码链接或无依据的模型自由补全。
- 情感回复案例：采用“检索证据先压缩再生成”“风险/修复按需触发”“分支局部闭环”；图片分支和大段领域代码不适用于本项目。
- 学生成绩案例：只保留“结构化结果”和“长链路阶段反馈”的思想；SQL、图表、Iteration 不适用于商业顾问对话主链路。

## 4. 实际优化内容

### 4.1 模型调用与尾延迟

- 固定问候、感谢、结束语、明确转人工和明确个人退款/订单/支付/登录/发票问题保持 0 LLM；
- 正常问题仍为“1 次检索规划 + 1 次分支回答”，没有为了看起来更智能而增加模型节点；
- 格式修复仍是显式条件分支，仅解析失败时增加 1 次 LLM；
- 所有 LLM 节点关闭隐藏节点重试，避免一次可见请求在限流/失败时被静默放大；
- `question_split.max_tokens=400`，回答和格式修复节点 `max_tokens=1800`，防止无上限输出占用并发槽位。

### 4.2 证据长度与准确率

- 继续保留现用版本的证据压缩，不采用“原始检索数组直接进入 Prompt”；
- 只保留课程、路线、状态、价格、链接等允许字段，剔除无关 Metadata；
- 通用分支上限 8000 字符、课程分支上限 9500 字符；混合分支分别限制通用与课程证据；
- 修复“第一条检索结果超过总预算时整段证据变空”的边界：先逐字段裁剪，再加入预算；
- 保留 `course_id`、`route_id` 等后端需要核验的标识；
- 不调整 `top_k`、阈值、知识库 ID 和 `qwen3-rerank`，避免在没有真实召回 A/B 的情况下把准确率风险混入本轮。

### 4.3 路由误判

- 明确个人售后问题直接进入人工核实，省掉无意义的检索与生成；
- “不需要人工”“微信营销”“加微信率”“企业微信运营”等不会因包含“人工/微信”误入人工分支；
- 泛化的退款政策咨询仍进入商业分析，不会被个人售后规则截断。

### 4.4 回答排版与信息结构

本次增量只修改 `final_answer` 的排版契约，没有修改输入参数、管理员风格配置、
知识库绑定、业务路由、课程/路线候选、卡片/链接生成或服务端消费契约。

- 三个主回答节点和三个格式修复节点共享同一套跨端排版规则；
- 简单答复、澄清和转人工仍保持 1～3 个短段落，不强行章节化；
- 复杂通用回答使用 `【结论】`、`【关键判断】`、`【建议行动】`；
- 复杂课程回答使用 `【建议】`、`【匹配依据】`，证据充分时可增加 `【开始方式】`；
- 复杂混合回答使用 `【结论】`、`【业务建议】`、`【学习建议】`；
- 章节之间空一行，并列项使用短列表，有顺序的行动使用编号步骤；
- 复杂回答通常限制为 400～800 个中文字符，不为凑长度扩写；
- 明确禁止 HTML、Markdown 表格、代码围栏、`#` 标题和依赖 emoji 的层级；
- 严格 JSON 中使用 `\n` 转义换行，解析后保留真实空行；
- 不新增 LLM/Code/Answer 节点，不提高回答节点 `max_tokens=1800`。

`business_output_style` 仍由 AI 管理服务控制语气和措辞。DSL 仅提供最低排版，
所以这不是把管理员配置写死，也不会替代后台风格设置。

## 6. 隔离运行态验收

导入候选 DSL 后，必须核对：

1. 应用名称与现用生产应用明显区分；
2. 四个知识检索节点仍绑定预期通用库/课程库；
3. `qwen-plus` 和 `qwen3-rerank` 凭据可用；
4. Start 输入和四个 `WECHAT_*` 环境变量名未变化；
5. 发布的是隔离应用，生产 App Key 映射未修改。

API Key 只放进当前进程环境变量，不写入仓库或报告：

```powershell
$env:DIFY_EVAL_BASE_URL = 'https://<Dify-host>/v1'
$env:DIFY_BASELINE_APP_API_KEY = '<现用应用 Key>'
$env:DIFY_CANDIDATE_APP_API_KEY = '<隔离候选应用 Key>'
python scripts/evaluate_dify_chatflow_ab.py `
  test_data/rag/business_dsl_optimization_cases.jsonl `
  --mode all `
  --concurrency 20 `
  --duration 600 `
  --output var/reports/business-dsl-ab-2026-07-31.json
```

验收门槛：

- 候选 28 条准确率与排版用例必须全部通过，且原有 24 条业务准确率不得低于基线；
- Tracing 证明固定场景 0 LLM、正常路径不超过 2、仅格式修复路径可为 3；
- 20 个不同会话持续至少 600 秒，建立至少 20 个 Dify conversation；
- 负载阶段无请求失败；同时报告首字和总耗时 P50/P95，不能只报平均值；
- 若准确率下降，即使响应更快也不通过；若准确率相同，再比较首字 P95、总耗时 P95 和吞吐。

## 7. 并发结论边界

DSL 优化只能减少单请求的模型次数、上下文大小和不必要分支，不能单独保证 3000～5000 活跃用户容量。最终容量还取决于：

- Dify API/Worker 数量与队列；
- Redis/Celery、数据库连接池和 Sandbox；
- 模型服务限流、并发配额及平均生成时长；
- AI 管理服务自身 Worker、HTTP 连接池和 SSE 长连接；
- 高峰到达率，而不是用户总数。

因此当前可下结论是“候选 DSL 的单请求资源边界更清晰，静态契约与本地路径测试通过”；运行态容量结论必须等隔离 A/B 和持续负载证据。
