# V2 从开发到服务器部署与回滚手册

> 适用对象：获授权的开发与运维人员。  
> 目标环境：jx 测试服务器，Linux x86_64、Bash、Docker Engine/Compose v2、Python 3.11、PostgreSQL 15、Redis 6、Dify 1.13.3。  
> 当前目录：本地仓库 `D:\work\projectc\jx-now`；服务器项目目录 `/opt/ai-management`。  
> 风险：本流程会写服务器文件、Docker 镜像、PostgreSQL、Redis 和隔离 Dify 测试数据。未取得发布授权、未完成备份验证或发现停止条件时，必须停止发布。

本手册使用占位符，不得把 Token、密码、`.env`、真实用户数据或完整日志粘贴到终端记录、聊天或 Git。

## 1. 发布原则与当前基线

当前已部署版本：

- 核心镜像：`jx-now-ai-management:0.2.0-c499193`。
- UI 镜像：`jx-now-ai-management-ui:0.2.0-3cfa83c`。
- 数据库迁移：`8d4e0f2c1a77 (head)`。
- 当前已验证备份目录：`/opt/ai-management/var/backups/20260727-c178371`。

每次发布遵守以下规则：

1. 先本地测试，再构建 wheel；wheel 上传前后必须核对 SHA256。
2. 核心和 UI 分别构建、分别打不可变镜像标签；不要覆盖后又无法区分的可变标签。
3. 先验证备份可恢复，再迁移；迁移失败立即停止，不执行临时手工 SQL。
4. API、Worker、Scheduler 必须使用同一个核心镜像版本。
5. PostgreSQL、Redis、上传卷和旧回滚镜像不得在发布期间删除。
6. 服务运行后以“健康、迁移、任务、日志、接口、用户可见功能”验证，不能只看容器是 Up。
7. Streamlit 固定监听回环；临时浏览器测试经 Dify 已有 Nginx 的 `/ai-management-test/` 路径转发，复用既有 80/443，不新增端口、UFW 或云安全组规则。

## 2. 发布前条件与停止条件

必须具备：

- 小程序后端维护窗口、服务器 Docker 权限、SSH 别名 `jx服务器`。
- 已评审的源码提交、已填写的变更说明、已确认的回滚负责人。
- 服务器 `.env` 已存在且配置完整；仅检查键名，不输出值。
- 目标 Dify 应用与 Dataset 已确认是隔离测试环境；写入型测试不使用正式知识库。
- 充足的磁盘空间，能同时保存备份、旧镜像和新镜像。
- 若需浏览器测试 Streamlit：Dify 的 `docker-nginx-1` 正常运行、80/443 已可访问、测试内容仅为合成或隔离数据；不使用真实用户问题、文件或生产数据。

出现以下任一情况立即停止：服务器当前健康异常、数据库/Redis/Dify 已不可用、必需配置缺失、另一个发布/构建/迁移正在执行、备份或恢复验证失败、迁移缺乏兼容/回滚结论、测试将写入正式 Dataset、需要删除卷或覆盖真实数据。

## 3. 本地 Windows PowerShell：完成开发和构建

在 `D:\work\projectc\jx-now` 执行。先确认只包含本次应发布的改动；现有的业务资料目录不应被误加入提交。

```powershell
rtk git status --short
rtk git diff --check
python -m pytest -q tests
python -m ai_management.cli test_data/courses/测试课程与路线.md --dry-run
```

预期：pytest 正常退出，课程 dry-run 不发布远端数据且能输出课程/路线校验结果。若 Windows 上 pytest 收尾报 `test_ai_management.db` 被占用，不要删除任意数据库文件或结束无关进程。只检查并终止命令行明确包含 `-m pytest` 且工作目录属于本仓库的残留进程，然后重跑：

```powershell
Get-CimInstance Win32_Process -Filter "Name = 'python.exe'" |
  Where-Object { $_.CommandLine -match '-m pytest' -and $_.CommandLine -match 'jx-now' } |
  Select-Object ProcessId, CommandLine

# 确认上一步输出后，逐个替换为实际 PID；不要批量结束所有 python.exe。
Stop-Process -Id <confirmed_pytest_pid>
python -m pytest -q tests
```

构建 wheel 并保存发布变量。若本机没有 `build`，先在隔离虚拟环境安装它；不要向仓库写入密钥。

```powershell
$releaseSha = (git rev-parse --short HEAD).Trim()
$releaseId = "$(Get-Date -Format yyyyMMdd-HHmmss)-$releaseSha"
python -m build --wheel
$wheel = Get-ChildItem .\dist\jx_now_ai_management-0.2.0-py3-none-any.whl |
  Sort-Object LastWriteTime -Descending |
  Select-Object -First 1
$wheelHash = (Get-FileHash $wheel.FullName -Algorithm SHA256).Hash.ToLower()
"release_id=$releaseId"
"wheel=$($wheel.Name)"
"sha256=$wheelHash"
```

只上传 wheel 和已评审的发布所需文件。当前离线构建还依赖服务器已有的 `Dockerfile.offline`、`Dockerfile.ui-offline`、`wheelhouse/`、`ui-wheelhouse-linux/`、`scripts/`、`test_data/` 和 `migrations/`；它们变化时必须随同提交并在服务器复核。

```powershell
$remoteStage = "/tmp/jx-now-$releaseId"
ssh jx服务器 "mkdir -p $remoteStage"
scp $wheel.FullName "jx服务器:$remoteStage/$($wheel.Name)"
ssh jx服务器 "sha256sum $remoteStage/$($wheel.Name)"
```

服务器打印的 SHA256 必须与本地 `$wheelHash` 一致；不一致即停止并重新上传一次，仍不一致则排查文件/网络后再处理。

## 4. 服务器 Bash：预检和备份

登录服务器后执行；后续命令均在 `/opt/ai-management`。先设置不含密钥的变量：

```bash

export RELEASE_ID="<yyyyMMdd-HHmmss-git-short-sha>"
export CORE_IMAGE="jx-now-ai-management:0.2.0-${RELEASE_ID##*-}"

cd "$APP_DIR"
test "$(pwd -P)" = "$APP_DIR"
mkdir -p "$BACKUP_DIR" "$REPORT_DIR"
```

```bash
docker compose -f docker-compose.ai.yml -f docker-compose.ui.yml config --services
docker compose -f docker-compose.ai.yml -f docker-compose.ui.yml ps

docker system df

  grep -Eq "^[[:space:]]*${key}=.+" .env || missing_keys="$missing_keys $key"
done
test -z "$missing_keys" || { printf 'missing config keys:%s\n' "$missing_keys"; exit 1; }

# 在 API 容器内检查，避免依赖宿主机的 AI_BIND_ADDRESS 绑定值。
docker compose -f docker-compose.ai.yml exec -T api python -c "import urllib.request; print(urllib.request.urlopen('http://127.0.0.1:8000/health/live', timeout=10).read().decode())" > "$REPORT_DIR/health-live-before.json"
```

不要运行 `env`、`printenv`、`docker compose config` 全量输出或 `cat .env`。上述检查只会输出缺失键名。

进入维护窗口后，停止会产生业务写入的服务，保留数据库和 Redis：

```bash
upsert_env() {
  key="$1"
  value="$2"
  if grep -q "^${key}=" .env; then
    sed -i "s|^${key}=.*|${key}=${value}|" .env
  else
    printf '%s=%s\n' "$key" "$value" >> .env
```

### 5.1 可选：经 Dify 现有 Nginx 路径发布 Streamlit（不新增端口）

这是 jx 测试服务器的临时测试方式：浏览器访问 `http(s)://<服务器公网IP>/ai-management-test/`，流量走已经对外的 Dify Nginx 80/443；Streamlit 仍保持 `127.0.0.1:8501`。先在本地 Windows PowerShell 上传受版本控制的 Nginx 片段与补丁脚本：

```powershell
scp .\dify\nginx\ai-management-test.location jx服务器:/tmp/ai-management-test.location
scp .\scripts\configure_dify_nginx_streamlit_proxy.py jx服务器:/tmp/configure_dify_nginx_streamlit_proxy.py
```

再在服务器 Bash 执行。只重载 Nginx，不重启 Dify API、Web、数据库或 AI 核心服务；先备份两个 Nginx 配置文件，以便立即恢复。

```bash
cd /opt/ai-management
export NGINX_DIR=/opt/dify/docker/nginx
export GATEWAY_BACKUP_DIR="/opt/ai-management/var/backups/$(date +%Y%m%d-%H%M%S)-streamlit-nginx"
mkdir -p "$GATEWAY_BACKUP_DIR"
cp -a "$NGINX_DIR/conf.d/default.conf" "$NGINX_DIR/conf.d/default.conf.template" "$GATEWAY_BACKUP_DIR/"
test ! -e "$NGINX_DIR/conf.d/ai-management-test.location" || cp -a "$NGINX_DIR/conf.d/ai-management-test.location" "$GATEWAY_BACKUP_DIR/"

install -m 0644 /tmp/ai-management-test.location "$NGINX_DIR/conf.d/ai-management-test.location"
python3 /tmp/configure_dify_nginx_streamlit_proxy.py --mode enable \
  --template "$NGINX_DIR/conf.d/default.conf.template" \
  --active "$NGINX_DIR/conf.d/default.conf"

docker compose -f docker-compose.ai.yml -f docker-compose.ui.yml --profile test up -d --no-deps --force-recreate test-ui
docker exec docker-nginx-1 nginx -t
docker exec docker-nginx-1 nginx -s reload
curl --fail --silent --show-error -o /dev/null -w '%{http_code}\n' http://127.0.0.1/ai-management-test/
```

预期：UI Docker 端口仍为 `127.0.0.1:8501`，Nginx 校验成功，服务器路径返回 HTTP `200`。浏览器随后直接打开 `http(s)://<服务器公网IP>/ai-management-test/`；无需增加 8501 的 UFW 或云安全组规则。若 Nginx 校验失败，不执行 reload，按第 7.3 节恢复备份。

先启动依赖和新 API，执行迁移；成功后重建核心三服务及 UI。若迁移不是向后兼容的，必须使用已评审的维护窗口方案，不能直接套用本节。

预期：`ready` 为 200，所有依赖状态为 true，UI 状态为 200、绑定为 `127.0.0.1:8501`；如启用临时浏览器测试，Dify Nginx 的 `/ai-management-test/` 也返回 200。三份严重错误计数为 0。然后按 [V2小程序后端集成与全链路测试指南.md](V2小程序后端集成与全链路测试指南.md) 执行服务功能测试。

## 7. 回滚与故障处理

### 7.1 何时回滚

出现以下情况应回滚核心服务：迁移未到 head、`ready` 非 200、Dify/Redis/数据库核心能力异常、Worker 未消费任务、严重日志持续出现、关键小程序路径或管理接口失败。若迁移已写入且没有经评审的 downgrade，先停止并由负责人决定数据库恢复方案；不得盲目降级或删除表。

### 7.2 仅应用镜像回滚

这适用于数据库迁移仍向后兼容且问题位于应用代码。替换成该次发布前创建的实际标签：

```bash
cd /opt/ai-management
set -euo pipefail
export ROLLBACK_CORE_IMAGE="jx-now-ai-management:rollback-<release-id>"
export ROLLBACK_UI_IMAGE="jx-now-ai-management-ui:<previous-ui-tag>"

sed -i "s|^AI_IMAGE=.*|AI_IMAGE=${ROLLBACK_CORE_IMAGE}|" .env
sed -i "s|^AI_UI_IMAGE=.*|AI_UI_IMAGE=${ROLLBACK_UI_IMAGE}|" .env
docker compose -f docker-compose.ai.yml up -d --no-deps api worker scheduler
docker compose -f docker-compose.ai.yml -f docker-compose.ui.yml up -d --no-deps test-ui
docker compose -f docker-compose.ai.yml exec -T api python -c "import urllib.request; print(urllib.request.urlopen('http://127.0.0.1:8000/health/ready', timeout=10).read().decode())"
```

当前已知回滚标签和备份位置见 [V2部署检查点-2026-07-27.md](V2部署检查点-2026-07-27.md)。回滚后保留故障镜像和 `$REPORT_DIR`，不要覆盖它们。

### 7.3 关闭临时 Nginx 测试路径

测试结束或发现异常访问时，使用本次 `$GATEWAY_BACKUP_DIR` 恢复原 Nginx 配置。只删除本次创建的精确 location 文件；不要删除 Dify 的 `default.conf`、证书或其他配置。

```bash
cd /opt/ai-management
export NGINX_DIR=/opt/dify/docker/nginx
export GATEWAY_BACKUP_DIR="<this-test-streamlit-nginx-backup-directory>"
cp -a "$GATEWAY_BACKUP_DIR/default.conf" "$NGINX_DIR/conf.d/default.conf"
cp -a "$GATEWAY_BACKUP_DIR/default.conf.template" "$NGINX_DIR/conf.d/default.conf.template"
rm -f "$NGINX_DIR/conf.d/ai-management-test.location"
docker exec docker-nginx-1 nginx -t
docker exec docker-nginx-1 nginx -s reload
curl --fail --silent --show-error -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8501/ai-management-test/
```

预期：Nginx 校验成功，`/ai-management-test/` 不再由网关转发；Streamlit 仍只在服务器回环地址提供本地诊断。若页面期间发生可疑操作，保留日志和 request ID，轮换 `INTERNAL_API_TOKEN`、`ADMIN_API_TOKEN`，再按本手册重新验证。

### 7.4 常见问题排查顺序

| 现象 | 先检查 | 处理原则 |
| --- | --- | --- |
| `/health/ready` 返回 503 | JSON 中 database、redis、Dify 配置与 reachable 字段 | 先修依赖/网络/配置，不反复重启掩盖问题。 |
| Streamlit 路径无法访问 | `ui-http-status.txt`、`ui-binding.txt`、`test-ui` 日志、`docker exec docker-nginx-1 nginx -t` | 先确认 UI 为 `127.0.0.1:8501` 且 Nginx 路径本机 200，再确认 UI 已加入 `docker_default`、location 已 include、WebSocket 头未被移除。不要开放 8501。 |
| Worker/Beat 无 JSON 日志或不消费 | `worker`/`scheduler` 容器、队列、任务名 | 确认核心三服务版本一致、任务名已注册，再查 Redis。 |
| 课程点击未落库 | Redis 当日计数、`course_click_daily`、夜间维护日志 | 计数先进入 Redis，维护任务以绝对值幂等落库；不要手工累加数据库。 |
| Dify 调用失败 | `ready`、Dify DNS/网络、应用 Key、Dify 运行日志 | 不输出 Key；确认目标是正确测试应用和 Dataset。 |
| 迁移失败 | `$REPORT_DIR/alembic-upgrade.txt`、当前迁移、备份恢复验证 | 停止发布；先用回滚镜像恢复应用，数据库恢复需单独授权。 |

## 8. 本次避免重复踩坑清单

- `docker compose` 默认找不到配置：本项目文件名不是默认 `compose.yml`，必须显式传入 `-f docker-compose.ai.yml`，涉及 UI 时再加 `-f docker-compose.ui.yml`。
- UI 与核心不是同一镜像：发布核心不自动更新 UI；两者必须各自有镜像标签、构建验证和回滚标签。
- UI 入口文件必须来自已安装 wheel：`Dockerfile.ui-offline` 已负责暂存，不能以本地旧源码替换。
- 不要打印 `.env`：只检查键是否存在；Docker Compose 输出也可能包含环境变量，避免全量打印。
- Streamlit 临时页面不需要新增公网端口：通过 Dify 已有 80/443 Nginx 路径转发，UI 本身始终保持 `127.0.0.1:8501`。结束后恢复 Nginx 配置并删除精确 location 文件。
- 不要假设“容器 Up”代表服务正常：至少检查迁移、ready、UI、JSON 日志、管理双 Token 和一个用户可见路径。
- Windows pytest 文件锁：只处理已确认的残留 pytest 进程，不要结束所有 Python，也不要删除未确认的数据库文件。
