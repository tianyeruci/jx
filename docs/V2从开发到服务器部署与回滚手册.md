### 0.1 仅修改 Chatflow 访问配置（不改代码）

适用于只轮换或修正服务器 `.env` 中的 Dify Chatflow 访问配置，例如商业顾问的 `DIFY_BUSINESS_APP_API_KEY`，以及朋友圈、写作、摘要应用对应的访问 Key。此类变更不需要重新构建 wheel、迁移数据库或发布 Dify DSL，但必须重建读取该 `.env` 的核心服务。

Docker 容器创建时会固化 `env_file` 的值；`docker compose restart` 只重启原容器，不会重新读取修改后的 `.env`。jx 服务器上按以下步骤操作：

```bash
cd /opt/ai-management

# 修改 .env 前执行；备份目录名按实际日期/时间记录
BACKUP_DIR="/opt/ai-management/backups/$(date +%Y%m%d-%H%M%S)-chatflow-env"
mkdir -p "$BACKUP_DIR"
cp -a .env "$BACKUP_DIR/env.backup"

# 用编辑器只修改目标键；不要在终端回显 Token 或完整 .env
# vi .env

# DIFY_BUSINESS_APP_API_KEY 及其他 Chatflow App Key 变更：重建核心三服务
docker compose -f docker-compose.ai.yml \
  up -d --no-deps --force-recreate api worker scheduler

# 验证容器和 AI 服务状态
docker compose -f docker-compose.ai.yml ps api worker scheduler
docker compose -f docker-compose.ai.yml exec -T api \
  python -c "import urllib.request; print(urllib.request.urlopen('http://127.0.0.1:8000/health/ready', timeout=10).read().decode())"
```

预期 `/health/ready` 返回 `"status":"ready"` 且 `"dify_reachable":true`，随后再实际调用一次目标 Chatflow。不要执行 `docker compose down -v`，不要打印 `env`、`printenv`、完整 `docker compose config` 或 `.env`。

若需要回滚，只恢复本次备份的 `.env`，再用同一条 `--force-recreate` 命令重建 `api`、`worker`、`scheduler`；不要删除数据库、Redis 或上传卷。若修改的是 `DIFY_BASE_URL`、知识库地址或知识库 Key，需按实际消费者扩大重建服务范围，并遵循本手册完整发布前的备份与验证要求。

### 0.2 jx 指定 Markdown 目录的个人商业咨询模型清洗

适用于只检查 `/opt/ai-management/tmp/pdf-markdown-refine/output/` 中已清洗的 Markdown，不进入业务数据库、不启动 Celery、不发布 Dify。脚本使用 API 服务镜像中的运行时依赖，但通过一次性容器直接调用模型；输入只读，运行产物写入宿主机独立目录。

```bash
cd /opt/ai-management
INPUT_DIR=/opt/ai-management/tmp/pdf-markdown-refine/output
RESULT_ROOT=/opt/ai-management/var/jx-consultation-model-cleaning
mkdir -p "$RESULT_ROOT"

# 先确认文件数量和目录权限；不要把文件正文回显到终端记录
find "$INPUT_DIR" -maxdepth 1 -type f -name '*.md' -printf '%f\n' | sort | wc -l
test -r "$INPUT_DIR"
test -w "$RESULT_ROOT"

# --no-deps 不启动 API/Worker 依赖；.env 只由 Compose 注入，不打印其内容。
# 脚本文件通过只读挂载，避免必须先重建镜像；镜像中的 ai_management/
# knowledge_cleaner/ 必须与本次已发布代码和 Prompt 版本匹配。
docker compose --env-file .env -f docker-compose.ai.yml run --rm --no-deps \
  --user "$(id -u):$(id -g)" \
  -v "$INPUT_DIR:/app/jx-input:ro" \
  -v "$RESULT_ROOT:/app/jx-results" \
  -v /opt/ai-management/scripts/jx_consultation_model_cleaning.py:/app/scripts/jx_consultation_model_cleaning.py:ro \
  --entrypoint python api \
  /app/scripts/jx_consultation_model_cleaning.py run \
  --input-dir /app/jx-input \
  --output-root /app/jx-results \
  --max-cost-yuan "${MAX_COST_YUAN:-5}"
```

命令退出后先列出运行标记和 `run_id`，再查看日志与结果文件：

```bash
docker compose --env-file .env -f docker-compose.ai.yml run --rm --no-deps \
  --user "$(id -u):$(id -g)" \
  -v "$RESULT_ROOT:/app/jx-results" \
  -v /opt/ai-management/scripts/jx_consultation_model_cleaning.py:/app/scripts/jx_consultation_model_cleaning.py:ro \
  --entrypoint python api \
  /app/scripts/jx_consultation_model_cleaning.py list-runs \
  --output-root /app/jx-results

RUN_ID='consultation-model-cleaning-YYYYMMDD-HHMMSS-XXXXXXXX'
RUN_DIR="$RESULT_ROOT/runs/$RUN_ID"

# 每行一个 JSON；模型返回后以及每次验证都会立即写一行。
sed -n '1,240p' "$RUN_DIR/run.log"

# 只看失败、降级和关键验证位置
grep -E '"phase": "(semantic_validation|model_privacy_validation|final_markdown_validation|dify_boundary_validation|fallback)"|"status": "FAIL"|"reason_code"|"error_code"' "$RUN_DIR/run.log"

# 看每个文件最终选了模型还是源 Markdown，以及降级原因
python3 -m json.tool "$RUN_DIR/manifest.json"

# 看 item_id 与真实输入文件名的私有映射；只在服务器本地查看
python3 -m json.tool "$RUN_DIR/input-map.json"

# 看某个文件的完整模型返回值、通过校验的模型 Markdown、最终选中 Markdown
ITEM_ID='item-001-XXXXXXXXXXXX'
python3 -m json.tool "$RUN_DIR/model/$ITEM_ID.json"
sed -n '1,240p' "$RUN_DIR/validated/$ITEM_ID.md" 2>/dev/null || true
sed -n '1,240p' "$RUN_DIR/final/$ITEM_ID.md"
```

判断规则：`manifest.json` 中 `selected=model` 表示模型结果通过全部验证；`selected=source_markdown_fallback` 表示发生了降级，结合同一项的 `error_code`、`error_message` 和 `audit.source_markdown_fallback.reason_code` 定位原因；`selected=none` 且 `status=excluded` 表示模型明确排除，未执行源 Markdown 降级；`status=failed` 表示源 Markdown 本身没有通过硬门禁。`model/<item_id>.json` 保存完整模型返回值，普通日志只保存该文件路径和返回文件 SHA-256，避免正文扩散；不要把这个 JSON、`source/` 或 `input-map.json` 粘贴到聊天、工单或 Git。

运行产物按 `RUN_MARKER.json` 识别，确认已完成分析后只清理指定运行目录：

```bash
docker compose --env-file .env -f docker-compose.ai.yml run --rm --no-deps \
  --user "$(id -u):$(id -g)" \
  -v "$RESULT_ROOT:/app/jx-results" \
  -v /opt/ai-management/scripts/jx_consultation_model_cleaning.py:/app/scripts/jx_consultation_model_cleaning.py:ro \
  --entrypoint python api \
  /app/scripts/jx_consultation_model_cleaning.py cleanup-run \
  --output-root /app/jx-results \
  --run-id "$RUN_ID" \
  --confirm "DELETE_$RUN_ID"
```

该清理命令只删除匹配 `RUN_MARKER.json` 的单个运行目录，不删除输入目录、其他运行目录、数据库、Redis、上传卷或 Dify 数据。若需要保留审计证据，应先复制脱敏后的 `manifest.json` 和关键日志摘要；原始 `run.log`、模型 JSON、源快照和输入文件名映射属于受保护本地数据。

## 1. 发布原则与当前基线

当前 V2 发布基线（2026-07-28）：

- 核心镜像：`jx-now-ai-management:0.2.1-v2-20260728-r2`。
- UI 镜像：`jx-now-ai-management-ui:0.2.1-v2-20260728`。
- 数据库迁移：`d07f4fe0c0a1 (head)`。
- 当前已验证备份目录：`/opt/ai-management/backups/20260728-v2`。
- AI 数据库为 Dify PostgreSQL 内独立的 `ai_management` 数据库/角色；Redis 使用 Dify Redis DB 5。旧 AI 独立卷及旧镜像只用于回滚，不可删除。

每次发布遵守以下规则：

1. 先本地测试，再构建 wheel；wheel 上传前后必须核对 SHA256。
2. 核心和 UI 分别构建、分别打不可变镜像标签；不要覆盖后又无法区分的可变标签。
3. production 先验证同目标备份完整、可读且恢复工具可用，再迁移；test 不要求备份、临时数据库/schema 或恢复演练。任一环境迁移失败立即停止，不执行临时手工 SQL。
4. API、Worker、Scheduler 必须使用同一个核心镜像版本。
5. PostgreSQL、Redis、上传卷和旧回滚镜像不得在发布期间删除。
6. 服务运行后以“健康、迁移、任务、日志、接口、用户可见功能”验证，不能只看容器是 Up。
7. Streamlit 固定监听回环；临时浏览器测试经 Dify 已有 Nginx 的 `/ai-management-test/` 路径转发，复用既有 80/443，不新增端口、UFW 或云安全组规则。
8. 重新创建、导入或发布 Dify 应用后，必须在不输出值的前提下核对 AI 服务的应用访问 Key 映射，并逐一验证三个用户入口的 Dify `/parameters`；只有映射变化时才同步配置、重建服务。Dify 控制台发布不会替 AI 服务完成该项核对。
9. 含 Dify Code 节点的应用发布前，必须确认 API 的 `CODE_EXECUTION_API_KEY` 与 Sandbox 的 `SANDBOX_API_KEY` 哈希一致；两者不一致会导致 Code 节点 401。

## 3. 本地 Windows PowerShell：完成开发和构建

在 `D:\work\projectc\jx-now` 执行。先确认只包含本次应发布的改动；现有的业务资料目录不应被误加入提交。

```powershell
rtk git status --short
rtk git diff --check

python -m ai_management.cli test_data/courses/测试课程与路线.md --dry-run
```

预期：pytest 正常退出，课程 dry-run 不发布远端数据且能输出课程/路线校验结果。若 Windows 上 pytest 收尾报 `test_ai_management.db` 被占用，不要删除任意数据库文件或结束无关进程。只检查并终止命令行明确包含 `-m pytest` 且工作目录属于本仓库的残留进程，然后重跑：

```powershell
Get-CimInstance Win32_Process -Filter "Name = 'python.exe'" |
  Where-Object { $_.CommandLine -match '-m pytest' -and $_.CommandLine -match 'jx-now' } |
  Select-Object ProcessId, CommandLine

# 确认上一步输出后，逐个替换为实际 PID；不要批量结束所有 python.exe。
Stop-Process -Id <confirmed_pytest_pid>
python -m pytest -q tests
```

构建 wheel 并保存发布变量。优先使用已验证的 `pip wheel` 入口，避免本机同名或不完整 `build` 包导致 `python -m build` 无法启动；不要向仓库写入密钥。

```powershell
$releaseSha = (git rev-parse --short HEAD).Trim()
$releaseId = "$(Get-Date -Format yyyyMMdd-HHmmss)-$releaseSha"
python -m pip wheel --no-deps --no-build-isolation --wheel-dir dist .
$wheel = Get-ChildItem .\dist\jx_now_ai_management-0.2.1-py3-none-any.whl |
  Sort-Object LastWriteTime -Descending |
  Select-Object -First 1
$wheelHash = (Get-FileHash $wheel.FullName -Algorithm SHA256).Hash.ToLower()
"release_id=$releaseId"
"wheel=$($wheel.Name)"
"sha256=$wheelHash"
```

只上传 wheel 和已评审的发布所需文件。当前离线构建还依赖服务器已有的 `Dockerfile.offline`、`Dockerfile.ui-offline`、`wheelhouse/`、`ui-wheelhouse-linux/`、`scripts/`、`test_data/` 和 `migrations/`；它们变化时必须随同提交并在服务器复核。

```powershell
$remoteStage = "/tmp/jx-now-$releaseId"
ssh jx服务器 "mkdir -p $remoteStage"
scp $wheel.FullName "jx服务器:$remoteStage/$($wheel.Name)"
ssh jx服务器 "sha256sum $remoteStage/$($wheel.Name)"
```

服务器打印的 SHA256 必须与本地 `$wheelHash` 一致；不一致即停止并重新上传一次，仍不一致则排查文件/网络后再处理。

```bash

docker compose -f docker-compose.ai.yml -f docker-compose.ui.yml ps
df -h "$APP_DIR"
docker system df

missing_keys=''
for key in $required_keys; do
  grep -Eq "^[[:space:]]*${key}=.+" .env || missing_keys="$missing_keys $key"

test -z "$missing_keys" || { printf 'missing config keys:%s\n' "$missing_keys"; exit 1; }

grep -Eq '^REDIS_URL=.*@redis:6379/5([?].*)?$' .env || { echo 'REDIS_URL must target redis DB 5'; exit 1; }
```

### 5.2 私网 `8000` 直连知识库管理接口

知识库上传和其状态、条目、重试、复核接口不经过 Dify Nginx。调用方 `172.17.28.83` 应以 `http://172.30.157.197:8000` 作为 Base URL，直接请求本接口文档的 `/internal/v1/...` 路径。ai-management API 仍加入本机 Dify 的 `docker_default` 网络，供其访问 Dify、PostgreSQL 和 Redis；外部内网请求不使用该容器别名或网络，而是经宿主机私网 `:8000` 发布进入 API 容器。这样不会触发 Dify `:80` 的 Web 默认路由、`/ai-service/` 规则或 Docker NAT 来源转换。

jx 必须保持以下最小网络边界：API 仅发布到 `172.30.157.197:8000`；`AI-MGMT-8000` 只允许 `172.17.28.83/32`；到调用方的路由必须经 jx 私网网关和 `eth0` 返回。Dify Nginx 的上传 `403` 规则保持原状，不因本链路修改。验证命令只读且不会创建上传批次：

```bash
docker inspect ai-management-api-1 --format '{{json .NetworkSettings.Ports}}'
iptables -C AI-MGMT-8000 -s 172.17.28.83/32 -j ACCEPT
ip route get 172.17.28.83

# 调用方以正确双 Token 发起不含 files 的 POST 时预期为 422，
# 说明请求已到达 ai-management；实际上传才应携带 multipart files。
curl -sS -o /dev/null -w '%{http_code}\n' \
  -X POST http://172.30.157.197:8000/internal/v1/admin/knowledge-bases/general/upload-batches \
  -H 'X-Internal-Token: <redacted>' \
  -H 'X-Admin-Token: <redacted>'
```

预期：端口绑定和精确防火墙规则均存在、回程使用 `eth0`，无文件探针为 `422`；错误 Token 为 `401`。若连接超时或被拒绝，先核查两端阿里云安全组是否只允许 `172.17.28.83 → 172.30.157.197:8000`，再核查调用方实际源地址；不要改动 Dify Nginx、放宽为网段或取消双 Token。详见 [DEPLOY-022](troubleshooting/deployment.md#deploy-022知识库管理接口应走私网-8000-直连而非-dify-网关)。

先启动依赖和新 API，执行迁移；成功后重建核心三服务及 UI。若迁移不是向后兼容的，必须使用已评审的维护窗口方案，不能直接套用本节。

## 8. 回滚与故障处理

### 7.1 何时回滚

当前已知回滚标签和备份位置见 [V2部署检查点-2026-07-27.md](V2部署检查点-2026-07-27.md)。回滚后保留故障镜像和 `$REPORT_DIR`，不要覆盖它们。

### 7.3 关闭临时 Nginx 测试路径

测试结束或发现异常访问时，使用本次 `$GATEWAY_BACKUP_DIR` 恢复原 Nginx 配置。只删除本次创建的精确 location 文件；不要删除 Dify 的 `default.conf`、证书或其他配置。

```bash
cd /opt/ai-management
export NGINX_DIR=/opt/dify/docker/nginx
export GATEWAY_BACKUP_DIR="<this-test-streamlit-nginx-backup-directory>"
cp -a "$GATEWAY_BACKUP_DIR/default.conf" "$NGINX_DIR/conf.d/default.conf"
cp -a "$GATEWAY_BACKUP_DIR/default.conf.template" "$NGINX_DIR/conf.d/default.conf.template"
rm -f "$NGINX_DIR/conf.d/ai-management-test.location"
docker exec docker-nginx-1 nginx -t
docker exec docker-nginx-1 nginx -s reload
curl --fail --silent --show-error -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8501/ai-management-test/
```

预期：Nginx 校验成功，`/ai-management-test/` 不再由网关转发；Streamlit 仍只在服务器回环地址提供本地诊断。若页面期间发生可疑操作，保留日志和 request ID，轮换 `INTERNAL_API_TOKEN`、`ADMIN_API_TOKEN`，再按本手册重新验证。

### 7.4 常见问题排查顺序

| 现象 | 先检查 | 处理原则 |
| --- | --- | --- |
| `/health/ready` 返回 503 | JSON 中 database、redis、Dify 配置与 reachable 字段 | 先修依赖/网络/配置，不反复重启掩盖问题。 |
| Streamlit 路径无法访问 | `ui-http-status.txt`、`ui-binding.txt`、`test-ui` 日志、`docker exec docker-nginx-1 nginx -t` | 先确认 UI 为 `127.0.0.1:8501` 且 Nginx 路径本机 200，再确认 UI 已加入 `docker_default`、location 已 include、WebSocket 头未被移除。不要开放 8501。 |
| 可信内网后端上传知识库返回 403/404 | 调用 Base URL、`ai-management-api-1` 的 `172.30.157.197:8000` 发布、`AI-MGMT-8000` 来源规则、到 `172.17.28.83` 的回程路由 | 使用 `http://172.30.157.197:8000/internal/v1/...` 直连；不要经 Dify `:80` 或 `/ai-service/`。无文件且双 Token 正确的 POST 应为 `422`，不是网关 `403`。 |
| Worker/Beat 无 JSON 日志或不消费 | `worker`/`scheduler` 容器、队列、任务名 | 确认核心三服务版本一致、任务名已注册，再查 Redis。 |
| 课程点击未落库 | Redis 当日计数、`course_click_daily`、夜间维护日志 | 计数先进入 Redis，维护任务以绝对值幂等落库；不要手工累加数据库。 |
| Dify 调用失败 | `ready`、Dify DNS/网络、应用 Key、Dify 运行日志 | 不输出 Key；确认目标是正确测试应用和 Dataset。 |
| Dify Code 节点返回 401 | Dify API 的 `CODE_EXECUTION_API_KEY` 与 Sandbox 的 `SANDBOX_API_KEY` 的哈希 | 先备份 Dify `.env`，使两者一致后只重建 Sandbox；不重启或删除 Dify 数据库、Redis、知识库或卷。 |
| 商业顾问未收到 `message_end`，Dify 提示变量不存在 | Dify Workflow 运行记录、分类器路径、下游节点引用 | 不用提示词默认值掩盖未执行变量；将检索、决策和回答改为分支局部链路，导出当前 DSL 后重新导入、发布并逐分支验收。 |
| 迁移失败 | `$REPORT_DIR/alembic-upgrade.txt`、当前迁移、备份恢复验证 | 停止发布；先用回滚镜像恢复应用，数据库恢复需单独授权。 |

## 9. 本次避免重复踩坑清单

- `docker compose` 默认找不到配置：本项目文件名不是默认 `compose.yml`，必须显式传入 `-f docker-compose.ai.yml`，涉及 UI 时再加 `-f docker-compose.ui.yml`。
- UI 与核心不是同一镜像：发布核心不自动更新 UI；两者必须各自有镜像标签、构建验证和回滚标签。
- UI 入口文件必须来自已安装 wheel：`Dockerfile.ui-offline` 已负责暂存，不能以本地旧源码替换。
- 不要打印 `.env`：只检查键是否存在；Docker Compose 输出也可能包含环境变量，避免全量打印。
- Streamlit 临时页面不需要新增公网端口：通过 Dify 已有 80/443 Nginx 路径转发，UI 本身始终保持 `127.0.0.1:8501`。结束后恢复 Nginx 配置并删除精确 location 文件。
- 不要假设“容器 Up”代表服务正常：至少检查迁移、ready、UI、JSON 日志、管理双 Token 和一个用户可见路径。
- Windows pytest 文件锁：只处理已确认的残留 pytest 进程，不要结束所有 Python，也不要删除未确认的数据库文件。
- 本机 `python -m build` 若报 `build.__main__` 不可用或同名模块冲突，直接使用第 3 节的 `python -m pip wheel --no-deps --no-build-isolation --wheel-dir dist .`；无论使用何种构建入口，wheel 上传前后都必须核对 SHA256。
- Dify 的 `app-...` 是应用访问 Key，不是可公开记录的应用 ID；导入/发布或轮换后须同步受控配置并验证 `/parameters`，任何情况下均不粘贴 Key。
- Code 节点的 Sandbox 401 通常是 API 与 Sandbox 的代码执行 Key 不一致；只比较哈希，先备份，再只重建 Sandbox。
- 分类器的未执行分支不会产生空变量；共享下游节点不得引用所有分支变量。必须把决策与回答设计成分支局部链路，并逐分支验证终态事件。
