# AI 管理页文档清洗操作说明

更新时间：2026-08-06

适用对象：

- AI 管理页运营人员
- AI 管理页测试人员
- 需要人工复核清洗结果的业务人员

## 1. 入口与范围

当前测试页路径：

```text
/ai-management-test
```

普通文档清洗策略默认服务 `general` 知识库；`course_route_catalog` 专门写入 `course` 知识库，并同时更新课程/路线权威数据库和 Redis 快照。

当前页面支持：

- 查看可用清洗策略
- 上传多个文件创建批次
- 查看批次、文件、条目状态
- 重试失败文件
- 重试失败条目
- 对待复核条目执行人工复核

## 2. 上传前先确认

1. 选择正确知识库：当前一般使用 `general`
2. 选择正确策略
3. 确认文件格式受支持
4. 公共 Metadata 只填写已允许字段

当前正式策略：

- 最近活动清洗策略（`recent_activity`，实时千问，仅使用 `BAILIAN_API_KEY`）
- 微信公众号认知分享
- 个人商业咨询案例总结
- 知识星球帖子
- 小报童帖子
- 资料钩子
- 书籍

当前页面验收只覆盖 `general` 策略：最近活动、个人商业咨询、微信公众号认知分享、知识星球帖子、小报童帖子、资料钩子；书籍保持独立通用知识策略。`course_information`、`learning_route`、`course_route_catalog` 仅保留为后端显式历史管理兼容，不在页面展示，也不纳入本轮测试。

选择“最近活动清洗策略”时，一个活动生成一个逻辑文档并写入受控活动 Metadata。状态只允许正常、取消、延期；延期无新日期时不要把原日期当成新日期。活动策略固定实时调用千问，不使用 Provider Batch。该策略的清洗成功只证明测试页→服务→Worker→Dify 入库链路；要证明商业顾问可查询，还必须完成新版 Chatflow 的 App Key 切换和正负向 SSE 验收。

页面上传的内容不得包含课程/学习路线目录资料，也不得投放到商业顾问 `general` 知识库。若确有历史目录维护需求，走受控的显式管理入口；它不是本页面能力，也不会让新聊天恢复课程推荐或路线处理。

## 3. 页面操作顺序

### 3.1 查询策略

先点“获取策略列表”，确认当前知识库下有哪些策略可用。

### 3.2 上传文件

上传时填写：

- `knowledge_base_code`
- `strategy_code`
- `upload_mode`
- `common_metadata`
- 文件列表

约束：

- `.txt` 按文本读取
- 其它支持格式按 Markdown 清洗链路处理
- 单批次和单文件大小受服务端限制
- 不支持的扩展名会直接失败
- 同名或同内容命中时，文件会以 `excluded/duplicate_noop` 终态记录原因，不进入知识库；必须先在批次文件区用完整原文件名确认并删除源文件及其分片，去重保护释放后才能重新上传。

扫描 PDF 说明：jx 测试服务器已配置离线 OCR，但 OCR Worker 是按需资源。上传扫描 PDF 后，页面可能先显示排队/处理中；systemd 会在 `ai_ocr` 队列有任务时启动 Worker，队列清空并空闲 10 分钟后停止。文字层可用的 PDF 不会重复 OCR。页数超限、低置信度、隐私/质量告警或 Dify 回读失败时，文件进入 `review_required`/`failed`，不会自动发布；只有所有门禁通过才会自动发布。

运营人员不需要打开新代码窗口或在容器中安装 OCR 软件。若长时间停留在排队/处理中，交给运维核对 `jx-ocr-autoscaler.timer`、`journalctl -u jx-ocr-autoscaler.service` 和 OCR 镜像启动日志；不要自行清 Redis、删除上传文件或修改数据库。

### 3.3 看批次结果

批次需要重点看这些字段：

- `status`
- `progress`
- `all_succeeded`
- `all_processed_without_error`
- `file_counts`
- `item_counts`

判断原则：

- `status=completed` 代表批次终态已稳定
- `all_succeeded=true` 代表所有文件都成功
- `all_processed_without_error=true` 代表没有失败文件、没有待复核文件、没有 mixed 文件

### 3.4 看文件结果

每个文件重点看：

- `status`
- `outcome`
- `stage`
- `error_code`
- `error_message`
- `source_deleted_at`

常见情况：

- `succeeded`：文件下全部条目成功
- `failed`：文件级失败
- `review_required`：文件下全部条目都待人工复核
- `mixed`：同一文件下既有成功也有失败或待复核

### 3.5 看条目结果

进入文件条目列表后，重点看：

- `status`
- `stage`
- `metadata`
- `chunking`
- `dify_document_id`
- `remote_parent_count`
- `remote_child_count`

条目详情页还要看：

- `cleaned_markdown`
- `audit`
- `warnings`

## 4. 什么时候要人工复核

出现以下情况时不要直接当成功：

- `status=review_required`
- `retryable=false`
- `error_code=TOPIC_REVIEW_REQUIRED`
- `warnings` 提示存在主题不稳定或内容冲突
- 清洗正文明显缺失关键信息
- Metadata 中主题、来源标题不正确

## 5. 如何复核

复核接口支持三种动作：

- `approve`
- `replace_and_approve`
- `exclude`

建议使用方式：

- 内容基本正确，只需要补少量 Metadata：`approve`
- Markdown 正文需要人工修订后再入库：`replace_and_approve`
- 这条内容不该入库：`exclude`

复核时必须带：

- `expected_revision`
- `reason`

如果是 `replace_and_approve`，还必须上传新的 Markdown 文件。

## 6. 如何重试

### 6.1 文件重试

适合：

- 文件级失败
- 文件下存在失败条目

效果：

- 重新提交整个失败文件，或重新触发该文件下失败条目

不适合：

- 纯待复核文件

说明：

- 如果文件下全部条目都是 `review_required`，文件重试会返回 `409`；
- 这不是系统故障，而是强制要求先做人工复核。

### 6.2 条目重试

适合：

- 单条目失败

效果：

- 只重放这一条，不影响同文件下其它已成功条目

不适合：

- `status=review_required` 的条目

说明：

- 待复核条目必须先走复核接口；
- 选择 `approve` 或 `replace_and_approve` 后，系统会自动重新提交条目，不需要再额外点一次“重试”。

## 7. 成功与失败的判定口径

不要把“接口返回 200”当成成功。

条目真正成功，至少要满足：

1. Dify 文档创建成功
2. 索引完成
3. 父子块结构校验通过
4. Metadata 写入并回读成功

文件真正成功时：

- 文件状态为 `succeeded`
- 成功源文件已经删除

## 8. 需要特别注意的地方

- 成功文件源文件会删除，失败文件会暂存一段时间。
- 同名或同内容任一命中都不会入库；系统保留 `excluded/duplicate_noop` 审计记录。不能靠再次上传覆盖，必须精确删除原上传源文件（含其全部 Dify 分片），确认批次聚合已收敛后再上传。
- 书籍类大文件在 Markdown 成品超过 `10MB` 时会自动拆分。
- `exclude` 不是“失败”，它会把条目标记为排除，并同步刷新文件与批次统计。
- 页面根路径不是 `/`，测试页路径是 `/ai-management-test`。
- 验收或测试产生的临时知识库文档，结束后要删除，避免污染测试知识库。
- 如需保留 Dify 文档、只把测试页的清洗批次和上传状态恢复为空，使用 [jx 文档清洗本地状态归零操作说明](jx文档清洗本地状态归零操作说明.md) 中的受控脚本；不要直接删表、清空 Redis DB 或删除整个上传卷。
- 模型调用模式由 `BAILIAN_BATCH_ENABLED` 和候选数/估算输入 Token 阈值共同控制，默认关闭（`false`）。未明确开启或未达到阈值时新任务显示为“实时调用（realtime）”；四个内容模型策略在显式开启且达到阈值时显示并使用百炼 Batch；已有任务不改模式。实时模式仍受 RPM/TPM 限流和实时 Worker 并发限制；Batch 为异步任务，只在存在活动供应商任务时轮询。测试流程不得无明确授权自动启动百炼 Batch。
- Batch 与实时模式使用独立价格快照：Batch 使用 `CLEANING_PRICE_*`，实时使用 `CLEANING_REALTIME_PRICE_*`；课程自动门禁按实际模式价格估算，快照缺失/过期/超上限会整源阻断，不发布部分条目。
- `course_route_catalog` 默认由 `COURSE_CATALOG_AUTO_PUBLISH=true` 控制上传即处理：结构解析先固定名称、链接、稳定 ID、路线归属和顺序，模型只补语义字段；价格、模型契约、隐私或 Dify 回读任一失败都会整源阻断。关闭该开关时才显示结构审核/语义审核工作簿入口；普通名称冲突不得由模型猜名。
- `SAVE_CONVERSION_MARKDOWN=true` 只在测试服务器保存“转换后、策略处理前”的 PDF/DOCX Markdown 到专用目录；不提供 HTTP 下载，生产环境必须关闭。环境变量变化后必须重建 API 和清洗 Worker。

## 9. 在 jx 查看 PDF/DOCX 转换 Markdown

该产物是“格式转换后、清洗策略处理前”的原始 Markdown，仅用于测试服务器排查。它可能包含尚未脱敏的正文，不提供页面或 HTTP 下载。

### 9.1 开启保存

确认没有正在执行的清洗任务后登录服务器：

```bash
ssh jx-server
cd /opt/ai-management
cp -a .env ".env.bak-conversion-markdown-$(date +%Y%m%d-%H%M%S)"

CORE_IMAGE="$(docker compose -f docker-compose.ai.yml images -q api)"
APP_UID="$(docker run --rm --entrypoint id "$CORE_IMAGE" -u)"
APP_GID="$(docker run --rm --entrypoint id "$CORE_IMAGE" -g)"
case "$APP_UID" in ''|*[!0-9]*) echo '无法读取镜像 UID' >&2; exit 1;; esac
case "$APP_GID" in ''|*[!0-9]*) echo '无法读取镜像 GID' >&2; exit 1;; esac
install -d -o "$APP_UID" -g "$APP_GID" -m 0700 \
  /opt/ai-management/var/conversion-markdown

upsert_env() {
  key="$1"
  value="$2"
  if grep -q "^${key}=" .env; then
    sed -i "s|^${key}=.*|${key}=${value}|" .env
  else
    printf '%s=%s\n' "$key" "$value" >> .env
  fi
}

upsert_env SAVE_CONVERSION_MARKDOWN true
upsert_env CONVERSION_MARKDOWN_ROOT /app/var/conversion-markdown
upsert_env CONVERSION_MARKDOWN_HOST_ROOT /opt/ai-management/var/conversion-markdown
upsert_env CONVERSION_MARKDOWN_RETENTION_DAYS 7

unset SAVE_CONVERSION_MARKDOWN CONVERSION_MARKDOWN_ROOT
unset CONVERSION_MARKDOWN_HOST_ROOT CONVERSION_MARKDOWN_RETENTION_DAYS

docker compose -f docker-compose.ai.yml -f docker-compose.ui.yml \
  --profile test up -d --no-deps --force-recreate api worker
```

只需重建 API 和清洗 Worker；数据库、Redis、Dify、模型 Worker、发布 Worker、Scheduler 和测试页不需要重启。环境变量在容器启动时读取，所以只修改 `.env` 而不重建 Worker 不会生效。

核对两个容器加载结果：

```bash
docker compose -f docker-compose.ai.yml exec -T api python -c \
  'from ai_management.config import get_settings; s=get_settings(); print(s.save_conversion_markdown, s.conversion_markdown_root, s.conversion_markdown_retention_days)'

docker compose -f docker-compose.ai.yml exec -T worker python -c \
  'from ai_management.config import get_settings; s=get_settings(); print(s.save_conversion_markdown, s.conversion_markdown_root, s.conversion_markdown_retention_days)'
```

两处都应输出：`True /app/var/conversion-markdown 7`。

开关开启后只对新上传或正式重试的 PDF/DOCX 生效，不会回填历史任务。文件名格式为：


查看文件列表：

### 9.3 立即清理或关闭保存

保持开关开启、只立即删除当前产物：

```bash
cd /opt/ai-management
docker compose -f docker-compose.ai.yml exec -T api python -c \
  'from ai_management.cleaning import maintain_conversion_markdown_artifacts; print(maintain_conversion_markdown_artifacts(delete_all=True))'
```

关闭保存并在 API 启动时删除遗留产物：

```bash
cd /opt/ai-management
if grep -q '^SAVE_CONVERSION_MARKDOWN=' .env; then
  sed -i 's|^SAVE_CONVERSION_MARKDOWN=.*|SAVE_CONVERSION_MARKDOWN=false|' .env
else
  printf '%s\n' 'SAVE_CONVERSION_MARKDOWN=false' >> .env
fi
unset SAVE_CONVERSION_MARKDOWN

docker compose -f docker-compose.ai.yml -f docker-compose.ui.yml \
  --profile test up -d --no-deps --force-recreate api worker
```

关闭后，新任务不再写产物；API 启动和夜间维护都会精确清理专用目录中的遗留文件。开启状态下，文件跨服务重启保留，超过 `CONVERSION_MARKDOWN_RETENTION_DAYS`（默认 7 天）后由夜间维护删除。

## 10. 在 jx 一次性转换 PDF 并清洗 Markdown 表格

本节用于在 jx 服务器上独立调试 PDF 的标题、目录、段落、换行和表格输出。它使用一次性 OCR 容器，不修改 API、Worker、数据库、Redis、Dify 或 Compose 配置；正式上传链路仍按统一清洗流程自动转换和执行最终无表格门禁。

### 10.1 准备和检查

脚本与 PDF 约定放在以下临时目录：

```text
/opt/ai-management/tmp/pdf/                 # 输入 PDF
/opt/ai-management/tmp/pdf-markdown-refine/ # 脚本、输出和运行材料
/opt/ai-management/tmp/pdf-markdown-refine/output/ # Markdown 输出
```

已登录 jx 服务器后执行：

```bash
cd /opt/ai-management/tmp/pdf-markdown-refine
ls -lh /opt/ai-management/tmp/pdf
ls -lh /opt/ai-management/tmp/pdf-markdown-refine/pdf_markdown_refine.py
docker image ls | grep jx-now-ai-management-ocr
```

当前最后一次 JX 回归使用的离线镜像是：

```bash
OCR_IMAGE='jx-now-ai-management-ocr:quick-20260805-020249-034af4811733'
docker image inspect "$OCR_IMAGE" >/dev/null
```

如果该标签不存在，用 `docker image ls` 中实际存在的 `jx-now-ai-management-ocr:<tag>` 替换；不要为此在线拉取镜像，也不要使用已经退役的 Dify PDF→Markdown Workflow。

先确认脚本支持当前参数：

```bash
docker run --rm --entrypoint python \
  -v /opt/ai-management/tmp/pdf:/data/input:ro \
  -v /opt/ai-management/tmp/pdf-markdown-refine:/data/work:rw \
  "$OCR_IMAGE" \
  /data/work/pdf_markdown_refine.py --help
```

### 10.2 批量或单文件转换

批量处理输入目录中的 PDF：

```bash
docker run --rm --entrypoint python \
  -v /opt/ai-management/tmp/pdf:/data/input:ro \
  -v /opt/ai-management/tmp/pdf-markdown-refine:/data/work:rw \
  "$OCR_IMAGE" \
  /data/work/pdf_markdown_refine.py \
  --input-dir /data/input \
  --output-dir /data/work/output \
  --ocr-dpi 200
```

注意：2026-08-09 jx 当前实际脚本的 `--help` 只包含 `--force`，没有 `--clean-tables`；不要把本地较新 CLI 的参数直接复制到服务器。只有服务器脚本的 `--help` 明确列出该参数时，才可以在命令末尾追加 `--clean-tables`。服务器当前版本如需单独清洗 Markdown 表格，使用 10.3 的共享函数命令；正式上传链路仍由服务自动执行统一表格清洗。

只处理一个文件时，把 `--input-dir /data/input` 替换为：

```bash
--input "/data/input/<文件名>.pdf"
```

重跑并覆盖已有 Markdown 时增加：

```bash
--force
```

输出文件为原 PDF stem 对应的 `.md`，查看方式：

```bash
find /opt/ai-management/tmp/pdf-markdown-refine/output \
  -maxdepth 1 -type f -name '*.md' -printf '%TY-%Tm-%Td %TH:%TM  %f\n' | sort

sed -n '1,240p' '/opt/ai-management/tmp/pdf-markdown-refine/output/<文件名>.md'
```

脚本会自动判断文字型 PDF 或扫描 PDF：文字型使用 `pdfplumber`，扫描型使用 `RapidOCR + pypdfium2`。`--ocr-dpi` 允许 `120..300`，默认 `200`。命令结束时打印 JSON，其中包含 `status`、`backend`、页数、表格计数和清洗告警。

### 10.3 单独清洗 Markdown 文件

仓库没有另一个独立的 Markdown 表格 shell 脚本；统一实现是 `knowledge_cleaner.markdown_table_cleaner.clean_markdown_tables()`。如只需清洗一个已有 Markdown，可在同一 OCR 镜像中执行：

```bash
mkdir -p /opt/ai-management/tmp/markdown

docker run --rm --entrypoint python \
  -v /opt/ai-management/tmp/markdown:/data/md:rw \
  "$OCR_IMAGE" \
  -c 'from pathlib import Path; from knowledge_cleaner.markdown_table_cleaner import clean_markdown_tables; src=Path("/data/md/input.md"); dst=Path("/data/md/output.md"); result=clean_markdown_tables(src.read_text(encoding="utf-8")); dst.write_text(result.markdown, encoding="utf-8"); print(result.as_dict())'
```

将待处理文件放为 `/opt/ai-management/tmp/markdown/input.md`，结果为 `/opt/ai-management/tmp/markdown/output.md`。`result.as_dict()` 会输出 `tables_converted`、`tables_demoted`、`rows_skipped` 和 `issues`。

### 10.4 处理边界

- 如果当前脚本的 `--help` 支持 `--clean-tables`，该参数会把可靠表格转换为带表头语义的句子；否则使用 10.3 的共享函数命令。
- 坏行会跳过并按表聚合内部审计，不会因此丢弃整份 PDF。
- 表头重复、列数不一致或复杂 `rowspan/colspan` 无法可靠对齐时，保留线性单元格文本，不猜测列关系。
- Markdown 代码围栏中的表格原样保留。
- 输出可能包含尚未脱敏的源正文，只用于受控测试，不得直接作为正式知识库发布结果。
- 不要通过 `docker exec` 修改正在运行的 API/Worker 容器，也不要为调试临时修改生产 `.env`。

### 10.5 2026-08-09 jx 覆盖实测

使用服务器实际存在的镜像 `jx-now-ai-management-ocr:20260807-1455-route-collections`、`--ocr-dpi 200 --force`，处理 `/opt/ai-management/tmp/pdf` 中的 5 个 PDF，5/5 成功，均使用 `pdfplumber`，共 344 页；其中 2 个文件各识别到 4 个表格，输出均为非空 Markdown。

覆盖规则是按输出文件名覆盖同名 `.md`，不会删除输出目录中与本批次无关的旧文件。本次运行前已有 3 个旧 Markdown，运行后输出目录共 8 个 Markdown，旧文件仍保留。
