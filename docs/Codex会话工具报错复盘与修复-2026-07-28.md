## 2. 最终结论

故障不是项目文件损坏，也不是用户必须把本地文件作为附件上传。完整链路上有三个独立问题，外加一个排查期间引入并已纠正的配置问题。

### 2.1 Codex 运行时的 Code Mode 工具序列化缺陷

桌面端内置运行时为 `0.146.0-alpha.3.1`。模型原本要调用 Code Mode 的自定义 `exec` 工具，但写入会话历史的记录变成：

```json
{"type":"custom_tool_call","name":"exec","namespace":"exec"}
```

运行器把命名空间和工具名拼接为 `execexec`，返回：

```text
unsupported custom tool call: execexec
```

非法记录随后进入 JSONL 会话历史。继续或分叉会话时，服务端回放这些记录，又因 Responses API 不接受该字段而返回：

```text
Unknown parameter: input[...].namespace
```

OpenAI Codex 官方仓库已有同类回归报告：从 `0.142.0` 升级到 `0.143.0` 后，旧会话因 `input[...].namespace` 无法继续，降级后恢复。

参考：<https://github.com/openai/codex/issues/31754>

### 2.2 Windows 默认未开启稳定的 unified exec

官方配置文档说明：

- `features.code_mode.enabled` 仍是开发中功能，默认关闭。
- `features.unified_exec` 是稳定的 PTY 执行工具，但 Windows 默认不启用。
- `features.shell_tool` 是稳定的默认 shell 工具。

参考：<https://developers.openai.com/codex/config-reference/>

进一步验收发现，桌面运行时还启用了独立开关 `code_mode_host = true`。
`code_mode.enabled = false` 只关闭 Code Mode 功能配置，并不会关闭桌面端
Code Mode 主机/执行器。只关闭前者后，桌面恢复的旧会话仍会收到故障的
自定义 `exec` 工具。

因此，本机的正确规避方案不是单纯关闭 Code Mode，而是同时关闭 Code Mode
功能配置及其桌面主机，并开启稳定原生执行通道：

```toml
[features]
unified_exec = true
code_mode_host = false

[features.code_mode]
enabled = false
```

这样会话使用稳定的原生执行通道，保留命令、文件和 SSH 能力，同时绕开产生 `execexec` 的 Code Mode 自定义工具通道。

### 2.4 排查期间引入的错误配置

排查中曾写入：

```toml

enabled = false
```

但当时漏掉 `unified_exec = true`。结果是新会话只剩会话管理和协作工具，不能执行命令、读取本地文件或发起 SSH。

第一次纠正时只加入了 `unified_exec = true`，但遗漏了桌面端独立的
`code_mode_host` 开关；命令行对照测试通过，桌面旧会话在重启后仍失败。
第二次验收由此定位到桌面主机层。现在已纠正为“开启稳定原生执行通道，同时
关闭 Code Mode 功能配置和桌面主机”的完整组合。

## 3. 为什么路径以前可用、后来要求上传附件

用户输入：

```text
D:\work\projectc\jx-now\文件清洗样本\公众号\阿猫投资学*20260101-20260531.txt
```

磁盘上的真实文件名是：

```text
阿猫投资学_20260101-20260531.txt
```

`*` 在 Windows 文件名中不是合法字符，它表示 shell 通配符：

- 原生 shell 可展开 `*`，所以这种写法可以匹配文件。
- 附件选择器和 `LiteralPath` 把路径当作字面值，不展开 `*`，所以会认为文件不存在。
- 没有本地执行工具时，模型只能看到用户消息中的路径字符串，无法自行解析通配符，于是错误地要求上传附件。

策略文件同理：

```text
01*公众号详细清洗策略.md
```

实际匹配：

```text
01_公众号详细清洗策略.md
```

`code_mode.enabled = false`、`unified_exec = true`，桌面旧会话仍生成
`{"name":"exec","namespace":"exec"}`。功能列表显示
`code_mode_host = true`，说明桌面主机层仍在暴露故障工具。使用相同运行时显式
关闭 `code_mode_host` 后，原生 shell 再次成功执行 `Get-Location`。因此最终配置
加入 `code_mode_host = false`，不能省略。

桌面应用进程会缓存启动时的功能配置，因此上述全局配置必须在完整退出并重新打开 Codex 后，才会进入桌面会话。重启后的验收只需在新会话执行一次 `Get-Location`，再对上述两个文件做“只解析文件名、不读取正文”的测试。

## 6. 后续处理原则

- 不把“关闭工具”当作工具报错的修复方案；每次必须同时检查替代执行通道是否可用。
- 按“配置加载 → 工具暴露 → 序列化 → 执行器 → Shell → 路径解析 → 历史回放”逐层验收。
- 更新 Codex 后先检查官方问题 `#31754` 的状态；确认上游修复并实测后，才考虑重新开启 Code Mode。
- 路径需要稳定复现时优先使用真实文件名；需要批量匹配时才使用 `*`。
- 每次会话历史修复都先备份、再修改、最后全库复扫。
