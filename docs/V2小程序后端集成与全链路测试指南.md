# V2 小程序后端集成与全链路测试指南

> 目标：用现有 API、Python 脚本和 Streamlit 页面，模拟“小程序后端调用 AI 管理服务并由服务调用 Dify”的完整链路。  
> 不新增模拟客户端代码；本指南中的命令只在隔离测试 Dify 应用、测试知识库和授权测试服务器执行。

## 1. 安全前提与测试范围

### 1.1 测试环境要求

- 使用隔离的 Dify 四应用和两个测试 Dataset；不要在正式知识库运行 `--write-knowledge`、清洗上传或课程发布测试。
- 所有密钥只存在于服务器 `.env` 或调用方的受控密钥存储。命令中只引用环境变量，不打印它们。
- 由小程序后端保存 `X-Internal-Token`；小程序前端只调用自身后端。
- 选择专用测试用户 ID，例如 `miniapp-e2e-<日期>-<随机值>`；测试结束后删除该用户创建的商业会话。
- 写入型测试会改变测试会话、测试点击累计、测试知识库和后台事件日志；运行前记录开始时间和预期影响。

### 1.2 测试访问方式

运维测试页仅监听服务器回环地址。先在本地 PowerShell 打开 SSH 隧道，并保持该窗口运行：

```powershell
ssh -N -L 127.0.0.1:8501:127.0.0.1:8501 jx服务器
```

在浏览器打开 `http://127.0.0.1:8501`。页面提供商业顾问、朋友圈顾问、日常写作、课程与路线、文件清洗、诊断、点击统计和日志页签；测试页调用 API，不直连 Dify/数据库。

自动化脚本在服务器 API 容器内运行，避免把内部 API 暴露到公网。服务器 Bash 先准备：

```bash
set -euo pipefail
cd /opt/ai-management
export COMPOSE='docker compose -f docker-compose.ai.yml -f docker-compose.ui.yml'
export REPORT_DIR="/opt/ai-management/var/reports/v2/manual-$(date +%Y%m%d-%H%M%S)"
mkdir -p "$REPORT_DIR"
```

以下所有 `docker compose` 示例可将 `$COMPOSE` 展开为完整命令；不输出 `.env`。

## 2. 小程序后端的调用范式

小程序后端应执行以下流程：

1. 在自身系统完成登录、会员和频率授权。
2. 从服务端密钥存储取内部 Token，不下发给小程序前端。
3. 选择稳定、不可变的业务用户 ID 写入 `X-User-Id`。
4. 调用 AI 管理服务，流式接口按 SSE 边界解析后再转发给小程序前端。
5. 保存服务返回的本地 `conversation_id`、`message_id`、`task_id`，用于续聊、停止、反馈和删除；不要保存或传入 Dify `conversation_id`。

典型请求头：

```http
X-Internal-Token: <仅小程序后端持有>
X-User-Id: <稳定业务用户ID>
X-Request-Id: <调用方生成的可选追踪ID>
```

商业顾问新会话和续聊请求：

```json
POST /internal/v1/business/chat
{
  "query": "我想系统学习 AI 工具，应从哪里开始？",
  "conversation_id": null
}
```

续聊时将 `conversation_id` 替换成此前 `message_end` 返回的本地会话 ID。SSE 必须等到空行后再解析一个事件；至少处理以下事件：

| SSE 事件 | 后端处理 |
| --- | --- |
| `request_started` | 保存本地 `conversation_id` 和 `request_id`。 |
| `status` | 转发加载/任务状态；其中可能含可停止的 `task_id`。 |
| `answer_delta` | 顺序追加并转发增量文本。 |
| `course_cards`、`learning_route`、`expert_insight` | 按结构化数据渲染，不从回答正文猜测课程链接。 |
| `message_end` | 保存消息 ID、task ID、状态、耗时、Token 用量；只有成功终态才标记完整回答。 |
| `error` | 显示稳定错误码和可重试提示；此前文本视为部分内容。 |

接口全表、请求模型、鉴权边界与错误结构见 [V2交接文档-2026-07-27.md](V2交接文档-2026-07-27.md) 和 [API与SSE说明.md](API与SSE说明.md)。

## 3. 测试顺序与通过标准

按本节顺序执行。任何“写入型”步骤失败时，记录 request/task/batch ID、时间、脱敏错误和容器日志路径，再停止后续同类测试；不要盲目重复造成重复数据。

### 3.1 服务与三个入口预检

在服务器执行：

```bash
curl --fail --silent --show-error http://127.0.0.1:8000/health/live | tee "$REPORT_DIR/live.json"
curl --fail --silent --show-error http://127.0.0.1:8000/health/ready | tee "$REPORT_DIR/ready.json"

$COMPOSE exec -T api python - <<'PY'
import json, os, urllib.request
request = urllib.request.Request(
    'http://127.0.0.1:8000/internal/v1/entry-config',
    headers={'X-Internal-Token': os.environ['INTERNAL_API_TOKEN']},
)
with urllib.request.urlopen(request, timeout=10) as response:
    body = json.loads(response.read().decode())
print(json.dumps({'http_status': response.status, 'entry_count': len(body.get('entries', []))}))
PY
```

通过标准：`live` 为 `ok`，`ready` 为 200 且所有依赖为 true，入口数量为 3（商业顾问、朋友圈顾问、日常写作）。在 Streamlit 的“诊断”页再次确认存活、就绪和入口配置可读取。

### 3.2 商业顾问：新会话、续聊、推荐、反馈、重命名、跳转、删除

该脚本模拟小程序后端，使用专用测试用户、读取真实 SSE、提交 like/dislike、重命名会话、打开课程签名跳转、读取点击统计并删除测试会话：

```bash
$COMPOSE exec -T api python scripts/live_business_lifecycle.py \
  | tee "$REPORT_DIR/business-lifecycle.json"
```

通过标准：有 `message_end`、课程卡片来自服务端返回、课程跳转为 HTTP 302、反馈与重命名为 2xx、点击统计包含测试课程、会话删除后不再出现在该测试用户列表中。

再通过 Streamlit 的“商业顾问”和“课程与路线测试”页手工确认：

- 新会话、选择历史会话、续聊均可用。
- 课程卡片只展示已启用且审核通过的课程；不要把模型回答里的普通 URL 当作可点击课程链接。
- 用户同一会话并发请求时应得到 HTTP 409 `CONVERSATION_BUSY`；不同会话可独立生成。

### 3.3 停止生成

```bash
$COMPOSE exec -T api python scripts/live_stop_check.py \
  | tee "$REPORT_DIR/stop-generation.json"
```

通过标准：停止接口 HTTP 200，最终 `message_end_status` 为 `stopped`，测试会话已删除。若未返回 task ID 或停止失败，保存对应 request ID 并检查 API/Worker/Dify 日志，不要直接删除 Redis 全部 Key。

### 3.4 朋友圈与日常写作 Workflow

在 Streamlit 的“朋友圈顾问”“日常写作”页分别输入最小请求并点击运行：

- 朋友圈：填写 `request`，可选 `source_material`、`audience`、`tone`、`constraints`。
- 写作：填写 `request`，可选 `source_text`、`audience`、`tone`、`format`、`constraints`。

通过标准：各自返回 `request_started`、`status`、至少一个 `answer_delta` 和 `message_end`；无须在商业会话列表出现历史，也不得产生课程卡片、课程点击或商业反馈。记录任务 ID 后可使用页面“停止任务”验证 Workflow 停止。

### 3.5 课程跳转、PV/UV 和后台日志

在生命周期脚本前后，通过 Streamlit 的“点击统计”和“日志”页记录测试课程的 PV/UV 与后台事件。

通过标准：同一测试用户对同一有效签名链接连续打开两次，PV 增加 2，UV 最多增加 1；无效、过期或停用课程 Token 不计数且不跳转。后台日志使用双 Token，缺 `X-Admin-Token` 必须返回 401。

课程点击是每日汇总：实时数可先来自 Redis，夜间维护再以绝对值幂等写入 PostgreSQL；不要用“再次手工加数据库值”的方式修复差异。

### 3.6 Dify 契约、知识库和 RAG

`dify_contract_check.py` 会调用四个 Dify 应用和两个知识库。带 `--write-knowledge` 时，会在**通用测试知识库**创建临时文档，等待索引、验证 Metadata 与分块，再尝试删除该文档。

```bash
$COMPOSE exec -T api python scripts/dify_contract_check.py --write-knowledge \
  | tee "$REPORT_DIR/dify-contract.json"
```

通过标准：商业 Chatflow 连续两轮均有 `message_end`，三个 Workflow 成功，两个知识库均能检索，临时文档索引、Metadata 和清理均成功。还应在 Dify 控制台人工确认第二轮 Start inputs 已使用动态摘要标记；脚本会将这一项标记为人工检查。

执行 40 条 RAG 评测，报告先输出到容器临时目录，再复制到服务器持久报告目录：

```bash
$COMPOSE exec -T api ai-rag-eval test_data/rag/golden_questions.jsonl \
  --top-k 5 --output /tmp/rag.json
api_container="$($COMPOSE ps -q api)"
docker cp "${api_container}:/tmp/rag.json" "$REPORT_DIR/rag.json"

$COMPOSE exec -T api python scripts/evaluate_business_e2e.py \
  test_data/rag/business_e2e_cases.jsonl \
  --base-url http://127.0.0.1:8000 \
  --output /tmp/business-e2e.json
docker cp "${api_container}:/tmp/business-e2e.json" "$REPORT_DIR/business-e2e.json"
```

通过门槛：关键问题 Hit@5 ≥ 90%，全量 Recall@5 ≥ 80%，并人工抽检至少 10 条完整回答；业务 E2E 所有案例通过。当前检查点中的历史结果为课程 Recall@5 约 96.38%、Critical Hit@5 100%、业务 E2E 6/6；重新运行后必须以新报告为准。

### 3.7 文件清洗：成功、失败、重试和补偿

使用 Streamlit“文件清洗”页，上传本地合成样本，目标选择隔离知识库：

- 成功样本：`test_data/cleaning/普通测试文档.md`。
- 失败样本：`test_data/cleaning/空文档.md` 或与策略不匹配的文件。
- 策略先选择页面展示的 `test_markdown`；仅在获得业务样本和授权后测试正式策略。

通过标准：每个文件都有独立状态与阶段；成功文件完成 Dify 索引并具备非零分块和正确 Metadata；失败文件显示稳定错误码/阶段；自动重试最多一次；仅对可重试失败使用单文件重试。若远端已创建而本地失败，必须确认补偿删除任务和后台事件，而不是只看 HTTP 上传成功。

此项目前属于待补齐的完整 E2E 证据。运行后保存 batch ID、file ID、Dify document ID（如页面可见）、状态截图和脱敏日志；不要把源文件或完整内容写入报告。

### 3.8 并发与故障注入

以下是正式灰度前的必做项，当前不应将其标记为已完成：

```bash
$COMPOSE exec -T api sh -lc 'python scripts/stream_load_test.py \
  --token "$INTERNAL_API_TOKEN" --concurrency 20 --duration-seconds 600' \
  | tee "$REPORT_DIR/stream-load.json"
```

额外人工场景：

1. 同会话两次并发请求，第二次必须为 409；不同会话可并发。
2. 客户端断开后检查 Dify 停止、本地消息终态与锁释放。
3. 在隔离维护窗口分别模拟 Dify 超时/限流、Redis 短暂不可用、PostgreSQL 短暂不可用、Worker 重启和清洗中断。
4. 验证 `/health/ready`、后台系统事件和 JSON 容器日志能准确反映故障与恢复。

不要在正式用户流量或正式 Dataset 上进行上述故障注入。

## 4. 清理、报告与测试结论

每轮测试结束后：

1. 删除该轮专用测试用户的商业会话；生命周期和停止脚本会自行清理各自创建的会话。
2. 确认 `--write-knowledge` 创建的临时文档已删除；失败时记录 document ID 并在隔离 Dataset 中补偿删除。
3. 不清零课程每日 PV/UV、后台事件或 Redis 数据来“美化”测试结果；将前后值与测试用户说明写入报告。
4. 保存 `$REPORT_DIR` 中的原始脱敏报告、健康 JSON、日志路径、Dify App/Dataset 版本和截图；Git 仅提交脱敏摘要。

测试报告应将每项标为“通过、失败、阻塞、未执行”之一。不得用“容器正常”替代全链路通过，也不得把旧的 43/43 或历史 RAG 指标标记为本次重新执行结果。

当前完整离线 pytest 的历史记录为 43/43；本地 Windows 上曾出现残留 pytest 子进程锁住 `test_ai_management.db` 并导致测试收尾超时。处理方式见 [V2从开发到服务器部署与回滚手册.md](V2从开发到服务器部署与回滚手册.md)，然后再以新的退出码和报告作为本次证据。
